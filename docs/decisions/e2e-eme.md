# The ClearKey (EME) decisions (ADR-104 to ADR-105)

Architecture decision records for the stretch goal "EME tests using ClearKey": the page parameter that hands the player a key (`clearKey`, [CONTRACTS.md](../CONTRACTS.md) section 6), the spec [`tests/e2e/eme.spec.ts`](../../tests/e2e/eme.spec.ts) (PB-EME-001) with its helpers in [`tests/e2e/eme`](../../tests/e2e/eme), and [`tools/eme-probe.ts`](../../tools/eme-probe.ts), the measurement every number below comes from and which anyone can run again. The encrypted stream itself is ADR-049 in [media.md](media.md); the support library the spec stands on is [e2e.md](e2e.md). They are written so each one can be defended in a review: what the situation was, what was chosen, what was rejected, what it costs, and how I would argue for it.

**Where the numbers come from.** One machine: Apple M2 Pro (12 cores, shared with other work: the load average was between 13 and 17 during the final runs), macOS 27.2, Node 22.11.0, Playwright 1.64.1, Shaka Player 5.3.3, Chromium 156.0.8078.4 (the headless shell Playwright runs by default) and WebKit 27.2 natively; Firefox 157.0, Linux WebKit 27.2 and Linux Chromium 156.0.8078.4 in the Playwright image through `npm run docker:pw` (3 CPUs), two workers, on 2026-11-04 (UTC), with the code of the branch `p3/eme` as committed when this record was written. The content hash of `vod-cmaf-clearkey` is `f1d6817ae45923e9bad0afba463d325a8050c35c158ea071d28927f5c1cd024a`, the one it had before this work: **the encryption layout was not changed**. Nothing was measured on a CI runner, on x64 hardware, in a headed browser, or with another version of any engine. The specs assert behaviour, not these numbers.

## ADR-104: What the lab proves with ClearKey, and what it does not

**Context.** The owner's stretch goal is "EME tests using ClearKey". Encrypted Media Extensions is the browser API through which a player hands a license to a content decryption module (CDM) that decrypts what the player appends through Media Source Extensions. Clear Key (`org.w3.clearkey`) is the one key system that the EME specification itself defines and asks of every implementation: its license is a JSON Web Key set that carries the keys in the clear, so it needs no license service, no vendor module, no account and no network, and it protects nothing. Every commercial system (Widevine, PlayReady, FairPlay) needs a licensed CDM and a license service, which a public repository can neither ship nor reproduce. The lab has one encrypted stream, `vod-cmaf-clearkey` (CENC `cenc` AES-CTR with a public throw-away key, ADR-049), and until this work it had only been checked by ffmpeg's own decryption: no browser had ever played it, and the media agent had flagged two risks (no `pssh` box, whole-sample VP9 encryption with no clear header).

**Decision.** The lab claims exactly the following, and PB-EME-001 makes each part able to fail:

1. **The origin serves a protected stream.** Read from the bytes, with none of the media pipeline's own code: the manifest names the protection in every `AdaptationSet` (the generic scheme with `cenc:default_KID` equal to the key id of `StreamInfo.drm`, and the ClearKey system id) and contains the key in none of five spellings (hex in both cases, base64 with and without padding, base64url); every init segment has the protected sample entry (`encv` or `enca`), a `tenc` box and the key id, and not the key.
2. **The stream plays with its key, through EME and MSE.** A first frame, 3 s of media time, no error of any severity, and `loadMode` `media-source`; and the key exchange is observed, not assumed: a session opened with `keyids`, a license handed to it (`MediaKeySession.update`), the CDM reporting the key `usable`. The key comes from the catalog (`StreamInfo.drm`), never from the spec, and reaches the player as the page parameter `clearKey=<key id>:<key>` which sets Shaka's `drm.clearKeys` before anything loads.
3. **The key is what makes it play**, with two controls in the same spec: with the right key id and a different key (one hex digit changed) the same stream gets the same exchange (the license is accepted, the key is `usable`) and never presents a frame, the media clock stays at 0; and without any key the player refuses the stream at load with an error of the DRM category (Shaka 6012, `NO_LICENSE_SERVER_GIVEN`).
4. **Who decrypts is measured, asserted per engine and reported** (ADR-105), because the answer is not the same in every engine.

**What it does not prove.** Any commercial DRM; a CDM's robustness levels, hardware-secure decoding, HDCP or output protection; a license server round trip, its failures, license renewal, expiry or persistent sessions (the license is a `data:` URI the player builds: nothing is requested); key rotation, several keys or several periods; pattern (`cbcs`) or subsample encryption (the stream encrypts whole samples under `cenc`); encrypted live or HLS (the stream is DASH VOD); resistance to an attacker (the key is public and the IVs are counters: the stream is a fixture); any device. A pass says that the lab's own encrypted stream, its manifest and the player's EME path work together in an engine; it does not say that protected playback works for a service.

**Alternatives considered.** A fake CDM or a stub of `requestMediaKeySystemAccess` (it would test the stub). A commercial test license service (an account, terms, a network and a vendor name; not reproducible offline; nothing the repository could ship). Asserting a first frame only (ADR-105 shows an encryptor that fails after its first frame). A ClearKey license endpoint in the service, named in the manifest (it would exercise a license request, at the price of an endpoint whose only job is to hand the public key to anyone who has the manifest, which is the opposite of what the spec asserts about the manifest; the strategy's own assumption for this area is "a local key, no network"). `qa.configure()` after `open()` to hand over the key (it races the page's own load; the page parameter is applied at boot, before anything loads, and a malformed one is reported through `paramProblems` instead of silently playing without a key).

**Consequences.** The key travels in the page URL. It is public, but a browser repeats the page URL in some of its own console messages (Firefox prints it in a warning about `requestMediaKeySystemAccess`), and a failing test attaches the console: the page therefore takes the parameter out of the address bar (`history.replaceState`) as soon as it has read it, reports it in `qa.info()` only (its `params.clearKey` and the `drm.clearKeys` of `configOverrides`), and a unit test pins the one place where a rejected configuration would have echoed it into an event. The spec's own failure messages name the form in which a key leaked ("the manifest contains the key written as base64") and never print it; the support library's `open()` still prints the page URL when a page fails to boot, so a boot failure of an EME page prints the public key once. The page parameter is a contract (`PlayerPageParams.clearKey`, section 6) with its own unit tests (validation, round trip, no echo of a refused value). The spec is also an oracle of the lab's encryptor (mutation 6 in ADR-105): a wrong counter-block layout in `cenc.ts` turns it red, which ffmpeg's decryption and the media unit tests also catch, but now with a real browser's CDM as a second, independent reader.

**Defending it.** "The claim is narrow and every word of it can fail. I do not say 'DRM tested': I say that a CENC-encrypted stream the lab made plays in the engines whose own ClearKey module decrypts it, that the key is what makes it play (a wrong key with the right key id gets as far as the decryption and produces nothing), that the manifest never carries the key, and, for the one engine where the browser does not do the decrypting, that the player does. What I did not test is listed next to what I did, because a reviewer who knows EME will ask."

## ADR-105: What each engine does, as measured, and how the spec stays honest about it

**Context.** The brief expected trouble and said that an honest "this does not work in engine X because Y" is an acceptable result. `tools/eme-probe.ts` plays the stream in one engine with the instrument of the spec (an init script that watches `SourceBuffer.appendBuffer`, `MediaKeySession.generateRequest` and `update`, and reports through a binding: no spec evaluates anything in the page) and prints one table. The same measurements, with the exact outputs, are what the spec annotates on every run (`eme-decryptor`, `eme-wrong-key`, `eme-no-key` in the result).

| EME API | yes | yes | yes | **no: `navigator.requestMediaKeySystemAccess` does not exist** |

| Who decrypts | the browser's ClearKey CDM (the init segments reach MSE still `encv`/`enca`, license applied, key `usable`) | the browser's ClearKey CDM (the same) | **the player, in JavaScript** (the init segments reach MSE as `vp09`/`mp4a`; license applied, key `usable`) | none |

**What was found, each with its evidence.**

1. **The risks the media agent flagged did not materialise, so the stream is unchanged.** Chromium and Firefox decrypt a whole VP9 sample with no clear header and play it; no `pssh` box is needed, because Shaka opens the EME session itself from the configured pair (`keyids` init data) and the license is a JWK set it builds, so the browser never has to find an init data in the stream. `ffmpeg -decryption_key` was the oracle of ADR-049; two browsers' CDMs now agree with it.
2. **In WebKit the player decrypts, not the browser.** Shaka 5.3.3 treats ClearKey in Apple browsers as unreliable (`AppleBrowser.hasWorkingClearKeySupport()` returns `false`, `lib/device/apple_browser.js`), so `ClearKeyWebCryptoDecryptor` (`lib/media/clearkey_webcrypto_decryptor.js`, chosen in `lib/media/media_source_engine.js`) decrypts every segment with WebCrypto AES-CTR and rewrites the init segment (`encv` becomes the real format, `sinf` becomes a `free` box) before it appends anything. The EME exchange still happens (a session, the license, a `usable` key), but the browser's CDM decrypts nothing: WebKit's playback proves the player's fallback and the lab's `senc`/`tenc` framing, not WebKit's ClearKey. Whether WebKit's own CDM would decrypt this stream if the player let it was **not measured**: that needs a patched player, and the lab tests the player as shipped.
3. **Playwright's Linux WebKit has no EME at all**, which is a documented gap and not a failure of the lab. The spec does not skip it blindly: it opens the page, **waits for the documented error** (`MISSING_EME_SUPPORT`) and only then skips, with a reason that starts `documented gap in <environment>:` as the library's gaps do. If the engine ever gets EME the wait fails with the player's timeline and the evidence is what has to change, instead of a skip that nobody revisits.
4. **Firefox's ClearKey module shares keys between the pages of a context, and the first key given for a key id wins.** The `sharing` rows of `tools/eme-probe.ts` (Firefox 157.0, the Playwright image): a page with a wrong key next to an open page that has the right key **plays**; a page with the right key next to an open page that has a wrong key **fails**; a page with a wrong key in another context of the same browser, or after the page with the right key was closed, fails like a page that is alone. The first version of the spec ran its controls in the test's own context and turned red on exactly this (a first frame under a wrong key). I did not read Firefox's source: the behaviour is consistent with one key table per context in which an entry is kept until the page that created it goes away. Chromium and WebKit do not share (the same rows).

**Decisions.**

- **Each control runs in a browser context of its own** (`newIsolatedContext`, with the project's device settings, because the user agent decides which device class the player picks). The positive run has the test's own context. Contexts are closed when the test has passed; after a failure they stay open so that the diagnostics can still read their pages (the second and third player attach as `qa-events-2.json`, `-3`).
- **The oracle of the wrong-key control is what a viewer gets, not what the engine says**: no `firstframe` event, startup time null, no frame presented, media clock at 0, after a window that a working player would have used to present its first frame: the first segment of each track was delivered (the server's log), then 30 animation frames of the page (`observeFrames`, a negative observation whose positive control is the first step of the same test). It never asserts an error code or a decoded-frame count: the table shows they differ between engines and between runs of one engine (WebKit's decoder counted one frame in 3 of the 9 runs read since the assertion became "presented", and in 2 of the first 10 runs of the first version of the spec, which asserted zero decoded frames and turned red twice). The codes and the count are annotated in the result, so a report shows what each engine said. The control is valid only if it differs from the positive run in the key alone, so the spec also asserts that the license was handed over and the key reported `usable` with the wrong key.
- **A first frame proves nothing about decryption.** Mutation 6 below: an encryptor with the IV in the wrong half of the counter block still decrypts the first sample correctly (the IV of sample 0 is 0, where both layouts give the same counter block), so Chromium presented a first frame at the very moment it reported the decode error of the samples after it. The positive step therefore asks for 3 s of media time and no error of any severity, not for the first frame.
- **The engine's decryptor is asserted** (`DOCUMENTED_DECRYPTOR` in `tests/e2e/eme/evidence.ts`: Chromium and Firefox `browser`, WebKit `player`). A spec that said only "it plays" would pass in all three and claim EME for all three. The assertion is the measurement, so a change in either direction (Shaka starts trusting Apple's ClearKey, or stops trusting Chromium's) fails with a message that names the table, instead of silently changing what the test proves. This is the one place a spec knows the engine's name, as a documented difference with its evidence, not as a skip.
- **The catalog row is not widened.** PB-EME-001 stays `chromium, firefox`: macOS WebKit also passes the spec, but its pass is the player's, so the row says so and the orchestrator decides whether WebKit belongs to it. The spec runs in every project that `test:release` runs, so it states what happens in each (pass with the decryptor `player`; documented gap in Linux WebKit).

**Mutations.** All in Chromium on this machine; each reverted and checked with `git diff`. The attachments of a failure are the library's (`qa-events.json`, `qa-metrics.json`, `qa-info.json`, `page-console.json`, `session-detail.json`, `request-log.json`, with `-2` for the second player), and the player's timeline is in the message.

The unit tests of the helpers were mutated too: removing the pass-through of `appendBuffer` in the init script, and ignoring `enca` in `isProtectedInit`, fail four of their tests; removing the redaction of the boot configuration fails the test that keeps the key out of the timeline.

**Stability.** Two workers, the specs of `tests/e2e` in one run (PB-EME-001 next to PB-ENV-001, PB-VOD-001 and PB-VOD-002; in the image Firefox and Linux WebKit ran together), other agents' load on the machine (the load average was above 12 for the whole session), the final version of the spec: Chromium 5 runs of 5 passed (PB-EME-001 in 4.6 to 6.1 s); macOS WebKit 3 of 3 (6.0 to 6.3 s); Firefox in the Playwright image 3 of 3 (6.0, 6.9 and 12.0 s); Linux WebKit in the image 3 of 3 skipped, each time after the documented error was seen (0.5 to 2.3 s); Chromium in the image 2 of 2 (4.8 and 6.5 s). The design estimate for an EME test is 12 s: the slowest run, Firefox under load, took 12.0 s. No test failed in any of these runs; the failures of the first version of the spec (a wrong key that played in Firefox because the control shared a context, and WebKit's decoded frame, twice) are the reasons for two of the decisions above. Earlier versions of the spec passed further runs (Chromium 5 of 5, WebKit 6 of 6, Firefox 3 of 3, Linux Chromium 2 of 2) that are not counted here, because the init script was sent differently then.

**Alternatives considered.** Changing the stream (a `pssh` box, a subsample map, a clear VP9 header): the measurement says it is not needed, and a layout nobody needs is a layout that can be wrong. Making Shaka use WebKit's CDM (a patched or configured player: the lab tests the player as shipped). Adding `webkit` to the catalog row (see above). Skipping Linux WebKit before running (a skip that cannot notice the gap closing). One browser process per control (a context is enough: the other-context rows behave as if the page were alone). Asserting the engine's error for the wrong key (the table: it differs by engine and by run).

**Consequences.** The evidence is one version of each engine; `DOCUMENTED_DECRYPTOR` and the Linux WebKit gap are statements about Playwright 1.64.1's builds and Shaka 5.3.3's device rules, and `tools/eme-probe.ts` is how they are taken again. Headed Chrome, Safari proper, Firefox on other platforms and other Firefox builds were not measured. Playback in WebKit is a test of the player's fallback, which is worth testing because a viewer on Safari gets exactly that path, and it is not a test of Apple's CDM. The spec needs a context per control and the `diagnostics` of a failure read pages in contexts the test opened itself, which is why they are left open after a failure. The wrong-key control relies on `observeFrames` for engines that stall without an error: its window is half a second of page frames, and it can only be too short in the harmless direction (a pass it should not have given), never produce a false failure; mutation 1 shows it is long enough to notice a key that works.

**Defending it.** "I expected the stream to need changes and measured instead of guessing: two engines decrypt it with their own module, one engine plays it only because the player decrypts it, and one has no EME. Each of those is a line in a table that a person can regenerate with one command, and a spec that asserts it. The control I trust most is the wrong key with the right key id, because it gets as far as the decryption; and when Firefox showed me that a wrong key can play next to a right one, I changed the test's isolation instead of its assertion."
