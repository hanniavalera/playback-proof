# The end-to-end support library decisions (ADR-070 to ADR-079)

Architecture decision records for what every Playwright spec of the lab stands on: [`tests/e2e/support`](../../tests/e2e/support) (the typed handle on `window.__qa`, the fixtures, the documented gaps, the waits on the server's log, the assertions, the failure diagnostics, the CPU throttle), the traceability check [`tools/check-specs.ts`](../../tools/check-specs.ts) (`npm run specs:check`), and the first three specs, [`env.spec.ts`](../../tests/e2e/env.spec.ts) (PB-ENV-001) and [`vod-start.spec.ts`](../../tests/e2e/vod-start.spec.ts) (PB-VOD-001, PB-VOD-002), which prove that they work end to end. They are written so each one can be defended in a review: what the situation was, what was chosen, what was rejected, what it costs, and how I would argue for it. The lab-wide decisions this builds on are ADR-001 (the browser matrix), ADR-003 (a session per test) and ADR-005 (tests wait on events, with a cursor) in [DESIGN_DECISIONS.md](../DESIGN_DECISIONS.md), ADR-030 to ADR-037 in [codecs.md](codecs.md) (the capability probe and the documented gaps) and ADR-060 in [player.md](player.md) (the hook). The contract of the fixtures and of the attachments is [CONTRACTS.md](../CONTRACTS.md) section 7.

**Where the numbers come from.** One machine: Apple M2 Pro (12 cores, shared with other work: the load average was between 4 and 5 during the runs), macOS 27.2, Node 22.11.0, Playwright 1.64.1, Chromium 156.0.8078.4 and WebKit 27.2 natively, Firefox 157.0 and Linux WebKit 27.2 in the Playwright image through `npm run docker:pw` (4 CPUs, `--ipc=host`), two workers, on the date of the commit named where a figure is quoted. Nothing was measured on a CI runner, on x64, or on a GitHub macOS runner. The specs and the unit tests assert behaviour, not these numbers.

## ADR-070: A typed `PlayerHandle` over `window.__qa`, not `page.evaluate` in the specs

**Context.** The player page exposes one object, `window.__qa` ([`src/shared/qa.ts`](../../src/shared/qa.ts)), and the specs run in another process. Everything that crosses the page boundary is serialised: a predicate function cannot be passed in, the page's content-security policy forbids `eval`, a timeout in the page is not the timeout of the test, and what the page throws arrives wrapped by Playwright with its own prefix and, in Firefox, the page's stack frames in the message. About forty specs will drive the player. If each one writes `page.evaluate(() => window.__qa.waitFor(...))`, the boundary, the argument marshalling, the default timeout and the error clean-up are repeated forty times, a misspelt event name fails after fifteen seconds instead of at compile time, and a change to the hook is a change to every spec.

**Decision.** `PlayerHandle` ([`player.ts`](../../tests/e2e/support/player.ts)) has one method per method of the hook, typed with the hook's own types (`QAEvent`, `QAMetrics`, `QAInfo`, `FrameMeasurement`): `open`, `cursor`, `events`, `metrics`, `info`, `waitFor`, `waitForMediaTime`, `load`, `play`, `pause`, `seek`, `seekToLiveEdge`, `selectVariantByHeight`, `setAbr`, `configure`, `measureFrames`, `unload`. Every wait passes an explicit timeout (15 s unless the spec says otherwise: below the 45 s of a test, so a stuck wait fails as itself, with the event timeline the hook puts in the message, and not as "Test timeout"). The one filter that can cross the boundary is the `detail` the hook already understands (`{ reason: 'abr', height: 720 }`: shallow strict equality on the event's `detail`). `open()` navigates to `playerUrl({ manifest: <the session's>, ...params })` and fails at once, with the page's own words, when the page could not use a parameter (`paramProblems`: a typo must fail the test, not quietly change what is measured), when the player did not boot (with what the browser console said) or when Shaka reports the browser as unsupported. Nothing in a spec evaluates code in the page.

**Alternatives considered.** Raw `page.evaluate` in the specs (above). `expect.poll` over `metrics()` (ADR-060: polling cannot tell "the seek finished" from "the seek has not started"). A wrapper generated from the `QAHook` interface (seventeen methods: the generator would be longer than the file, and the hand-written methods carry the defaults and the error clean-up). Passing predicates as strings (an `eval` in disguise, refused by the page's policy and by the lint rule).

**Consequences.** The handle is a second place to change when the hook changes, but the compiler finds it: each call is typed against `QAHook`. A spec cannot express "wait until this arbitrary condition holds in the page"; it waits for an event with a `detail`, or for a request in the server's log (ADR-074). The round trip of each call is a few milliseconds. The handle keeps what the browser console said (errors, warnings, uncaught page errors, the last 200) because that is where a blocked script or a refused request shows, and the hook does not see those.

**Defending it.** "The page boundary is the most error-prone line in a browser test, so it is written once, typed, with a timeout on every wait and an error that reads like a sentence. A spec reads `await qa.waitFor('seeked', { since })` and cannot get the boundary wrong, because it does not see it."

## ADR-071: One session per test, created by a fixture, deleted after it, also when it failed

**Context.** [ADR-003](../DESIGN_DECISIONS.md) gives every test its own world: a live clock, fault rules, a token bucket and a request log, so that tests run in parallel and cannot disturb each other. The service keeps at most 500 live sessions and garbage-collects them only after their time to live (900 s by default). A suite that creates sessions in the spec and forgets one in a failing path leaks it, and a few hundred leaked sessions end in 503s that look like a product failure.

**Decision.** The `newSession(request)` fixture creates the session with the test title as its label (the label is what the service prints in its logs and what `session-detail.json` shows), remembers it, and deletes it in its teardown, which runs whatever the outcome of the test. A session that is already gone (expired) is not an error; any other failure of the delete is recorded as an annotation of the test, not as a failed test. The value it returns is the session's `SessionInfo` plus the `ServiceClient` it lives on (`TestSession`), so that `waitForRequest(session, ...)` needs no second argument. `service` is a worker-scoped client on the project's `baseURL`. A test that needs a second world calls `newSession` again; two sessions are numbered `-2` in the diagnostics.

**Alternatives considered.** One session per worker, reset between tests (the log cursor, the fault rules and the live clock would leak from one test into the next, and a failing test would leave its state for the following one). One session per file (the same, with the order of the tests as a hidden input). `service.createSession` in the spec with `try`/`finally` (correct, repeated forty times, and wrong the first time someone forgets it).

**Consequences.** One HTTP round trip per test (a few milliseconds). The log and the counters of a failed test are still there when the diagnostics read them, because the diagnostics are torn down before the sessions are (ADR-079). A spec that deletes its own session loses its diagnostics for it (recorded in `diagnostics-problems.json`).

**Defending it.** "A test either owns its world or it is a shared-state test in disguise. Creating the world in a fixture and deleting it in the same fixture makes the lifetime a property of the framework, not of the discipline of forty authors."

## ADR-072: Documented gaps are resolved from committed evidence, and a skip carries its reason

**Context.** Two engine and OS pairs could not run the playback suites by the evidence of the probe: Linux WebKit (its MSE playback fails intermittently with `MediaError 4: Failed to push buffer` on the probe's page, while `isTypeSupported` answers `true`) and Firefox on the macOS host (it does not start). [ADR-001](../DESIGN_DECISIONS.md) and [ADR-031](codecs.md) decided that the lab does not trust `isTypeSupported`; the probe decodes real media and its results are committed per environment in [`docs/results/codec-matrix`](../results/codec-matrix) (`docker-linux-arm64`, `local-darwin-arm64`, `gha-linux-x64`, `gha-macos-arm64`). The strategy says a documented gap is skipped with its reason and that a silent skip is a bug, and [ADR-034](codecs.md) asks the shared fixture to skip only with a reason built from the evidence. A `test.skip(browserName === 'webkit')` in a spec is a claim without evidence that nobody revisits when the browser is fixed.

**Decision.** [`gaps.ts`](../../tests/e2e/support/gaps.ts) turns the committed result file of `detectEnvId()` into decisions, with `capabilitiesFromEngine`, `selectStreams` and `explainNoStream` of the probe library. An **engine gap** (no stream of any kind plays) skips every test of that engine, in the auto fixture `documentedGap`, before the body runs and before any browser is launched. A **stream gap** (the flavour of one stream did not decode in every attempt: an intermittent flavour counts as not playing, ADR-032) skips the test that asks for that stream, in `newSession` and `streamFor`, which also chooses the stream (`pickStream`: CMAF first, the open-codec WebM as the DASH fallback). The reason is built from the evidence and starts with `documented gap in <environment>:`, names every flavour with its verdict (`cmaf-vp9-aac intermittent 2/5 ([play] NotSupportedError ...)`) and points at `docs/CODEC_MATRIX.md`; a browser that does not start gives the browser's own complaint (`Failed to launch the browser process: Could not find profile folder.`). **Without a committed file for the environment (a new CI runner) nothing is documented, so nothing is skipped**: the specs run, and PB-ENV-001 is the one that fails, loudly, with the evidence (ADR-077). Linux WebKit is the one engine for which the lab decided against its own probe, and that decision is one constant, `RUN_SPECS_IN_LINUX_WEBKIT`, **committed as `true`**: the specs run in Linux WebKit whatever the matrix says, as an experimental engine (an `experimental-engine` annotation on every one of its tests, so that the flake tracking follows it apart from the others). The experiment behind it is quoted in the comment of the constant: the real player page, which adds every SourceBuffer before it fetches, passed 80 of 80 runs in a fresh browser process each (`vod-dash` and `vod-hls`, muted and unmuted, and `live-dash`, in the Playwright image; `docs/results/player-smoke/experiments`, ADR-067 in [player.md](player.md)), where the probe's page plays 2 of 5 and 9 of 20. `false` returns Linux WebKit to the evidence, which says gap in `docker-linux-arm64` and `gha-linux-x64`.

**Alternatives considered.** A skip list in the config or in each spec (no evidence, no reason, no way to notice that the gap closed). `isTypeSupported` at run time (it says `true` for everything in Linux WebKit). Running the probe in every worker (a fresh browser process for each of several attempts per case, and an intermittent engine would flip its own verdict between two runs: a committed result is a decision, a fresh probe is a sample). `test.fixme` (it asks a person to remember).

**Consequences.** A gap is changed in one place, by committing a new probe result, and `git log` says when and why. A launch failure is a documented gap only where the committed result records it (Firefox on the macOS host); anywhere else a browser that does not start fails the test with the browser's own error, an environment failure as ADR-034 says. Stale evidence can hide a regression (an engine that used to fail and now plays keeps skipping until someone re-probes: the skip says what it was based on, and `npm run codec-matrix` re-probes) or, the other way round, make a test fail loudly where it used to be skipped (the intended signal of ENV-001). Today the only engine gap is Firefox on the macOS development host (the GitHub macOS runner's Firefox plays: `gha-macos-arm64` says `ok 5/5`), and the unit test over the committed files pins it, for both settings of the constant: with `false` the three gaps are Linux WebKit in the two Linux environments and that Firefox. The experiment did not cover WebM, live over HLS or long sessions, and one image on one architecture is what it measured, so a failure of the experimental engine there is data for the experiment and not a regression of the player; and the constant overrides the whole evidence for Linux WebKit, which is why the spec for the open-codec stream also runs there. The probe stays honest about the same engine: its matrix still reads intermittent, and the two statements are both on the record.

**Defending it.** "A gap is a fact about an environment, so it lives in the evidence of that environment and is read by the fixture; the spec says what it needs and never which browser it is. When the browser is fixed, the evidence changes in one commit and the skips disappear by themselves."

## ADR-073: Failure diagnostics are attachments with fixed names, read within a deadline, and they never replace the failure

**Context.** A red test in CI is read by someone who was not there, from a report, after the page is closed and the session is deleted. The first things they need are the player's own timeline, the metrics, the configuration, what the server saw, and the faults that were applied; failure triage (Phase 8) clusters failures from exactly these. If they are not captured at the moment of the failure, they are gone.

**Decision.** The auto fixture `diagnostics` runs when a test ends with a status other than the expected one (failed, timed out, interrupted) and attaches, as `application/json`: `qa-events.json` (the whole timeline), `qa-metrics.json`, `qa-info.json` (configuration letter, overrides, load mode, page parameters as applied, user agent), `page-console.json` (what the browser console said), `session-detail.json` (the session, its fault rules with their ids, the counters) and `request-log.json` (every request the server saw). The names and shapes are a contract ([CONTRACTS.md](../CONTRACTS.md) section 7); a second player or session gets `-2`. Every read is independent and has a five-second deadline, so that a page whose main thread is stuck, which is exactly the failure that needs them, costs five seconds and not the rest of the attachments; what could not be read is listed in `diagnostics-problems.json` with the reason. Storing an attachment is best effort. The fixture is torn down before the page and the sessions are (ADR-079). It was checked on a failure of the assertions (an origin that answers 503 to the manifest) and on a test timeout (a wait that outlives a four-second test): both end with the six documents attached.

**Alternatives considered.** Playwright's trace alone (it is kept too, `retain-on-failure`, but it is a binary that needs the viewer and does not contain the server's side). Printing the data to the console (lost in a CI log, impossible to parse). Attaching on every run (thousands of kilobytes of noise from green tests). A shape of one combined `diagnostics.json` (a consumer that wants the log has to know where in the document it is: fixed names let triage fetch what it needs by name).

**Consequences.** The page console is a sixth document beyond the five the brief named: it is where a blocked script, a refused request or an uncaught error shows, which the hook's timeline cannot see. A long soak makes `qa-events.json` large (the timeline grows with every rung change and stall; the soak is a Phase 7 concern). The log is the service's last 5,000 requests. A read that outlives its deadline is abandoned, not cancelled: the pending call is released when the page closes.

**Defending it.** "When a test fails, the question is always the same: what did the player think happened, what did the server see, and which faults were on. I attach exactly that, under names that never change, so a person and the triage tool open the same files."

## ADR-074: Waits are on events with a cursor; the one polling primitive lives in lab code, and one primitive lets time pass

**Context.** ADR-005 and ADR-060 decided that a test waits on the player's events, never on the clock. Some things are not player events: "the server has been asked for segment 7", "the manifest was refreshed five times". The only place that can tell is the server's request log, and it has no push channel. And some things are not events at all: a paused player must not advance the media clock, no event must happen in a window. Nothing positive ends such a window, so something has to say "this long was enough", and a spec that says it with a timer is the flaky test the rule exists to prevent.

**Decision.** Player waits go through the hook (cursor, `since`, `detail`). Server waits are `waitForRequest` and `waitForRequests` ([`waiting.ts`](../../tests/e2e/support/waiting.ts)) over `ServiceClient.waitForLog`, which polls the in-memory log every 25 ms and is the only polling in the lab (lab code, a documented interval, its own unit tests). A request that has started counts (an entry is listed from the moment it arrives, ADR-083), so "segment 7 was asked for" does not wait for its answer. The failure of a log wait names the predicate and the last twelve entries. `requestLogCursor` gives the `since` that selects only what happens from now on. `playFor` waits on the media clock. ESLint forbids `waitForTimeout`, `setTimeout`, `Atomics.wait` and any `requestAnimationFrame` call in everything under `tests/e2e`; the support library has one deadline, an `AbortSignal.timeout` in the diagnostics (ADR-073), which abandons a read and synchronises nothing. **The one way to let time pass is `observeFrames(n)` of the player handle**: it resolves after `n` animation frames of the page (`requestAnimationFrame`, 1 to 600), so the window is measured by the page's own frame clock and not by a timer, and it is bounded by that clock (Playwright's `waitForFunction` timeout rejects it when the page does not paint). It is the only file the lint rule lets call `requestAnimationFrame` (`player.ts`), so a spec cannot write a frame loop of its own. It was checked with a paused and a playing player in every engine of the lab (Chromium, `chromium-cpu4x`, macOS WebKit and, in the Playwright image, Firefox and Linux WebKit): 30 frames took 480 to 550 ms (about 60 frames a second, also under the CPU throttle), the media clock of a playing player advanced 0.45 to 0.51 s over them and that of a paused player 0.000 s, with no `playing` event after the pause.

**Alternatives considered.** `waitForTimeout` (banned). `expect.poll` on `metrics()` or on the log (it hides the order of events, adds its own interval and gives a failure that says "expected, received" with no history). A push channel from the service (a stream of log entries over a socket: more machinery in the service and in the client than a 25 ms poll of an in-memory array costs). A `sleep(ms)` helper for negative observations (the one thing the rule forbids, with a better name). Measuring the window in media time (for a paused player the media clock is the thing under test). A window counted in `timeupdate` events (a paused element fires none).

**Consequences.** A log wait can add up to 25 ms. A negative observation is a weaker statement than a positive one: "the clock stayed put for 30 frames" proves what happened in half a second of this page, so a spec waits for the positive event first (`pause()` resolves on `paused`), observes, and gives the observation its positive control (resume, observe the same number of frames, see the clock move) or it cannot fail. The default cursor of `waitFor` is 0, the whole history, which cannot miss an event but can be satisfied by an old one: a second seek must take a cursor first. With `autoplay: false` the first frame can be presented at load (Firefox paints the first frame of a paused video; Chromium waits for play), so a spec that takes its cursor after `loaded` can miss it: wait for `firstframe` from the start. A scratch spec that called every method of the handle in every engine found this, intermittently, in Firefox. `observeFrames` assumes a visible page: a background tab would not paint, and the call would reject after its timeout instead of observing; the lab runs one page per test.

**Defending it.** "There is exactly one loop in the lab that sleeps, it is 25 ms, it lives where it can be tested, and every other wait is an event with a cursor, except one: when the claim is that nothing happens, the window is a number of frames of the page, in one function, with its own timeout, which the lint rule lets nobody else write. A flaky wait is then either a missing event or a missing cursor, and both are visible in the message."

## ADR-075: Specs are traced to the catalog with the compiler API

**Context.** The catalog in `TEST_STRATEGY.md` is the list of record; the strategy says that every id must have a spec whose title starts with it, that every spec id is in the catalog, and that the tags agree with the tier and the engines. About forty specs arrive over several branches from several authors. A check made of regular expressions over source is fooled by a `test(` in a comment or a string and by formatting.

**Decision.** [`tools/check-specs.ts`](../../tools/check-specs.ts) (`npm run specs:check`) reads every `*.spec.ts` under `tests/e2e` and `tests/live` with the TypeScript compiler API and finds the real `test(...)`, `test.skip(...)`, `test.fixme(...)`, `test.only(...)` calls, with the `tag` of the test and of every `test.describe` around it and the `@words` of the title (`test.step`, `test.use`, hooks and conditional `test.skip(condition, 'reason')` are not tests). It fails when: an id is not in the catalog; an id is declared twice (and says where first); a title does not start with an id; the tags disagree with the row (`@merge` if and only if tier merge, `@release` if and only if tier release, `@cpu` if and only if the engines include `chromium-cpu4x`; a tag nobody defined fails too, because a typo would drop a test out of every gate); a spec is for a row of another lane; `test.only` is committed; `test` is imported from `@playwright/test` and not from the shared fixtures (the plain test has no gap skips, no diagnostics and no throttle); a title or a tag is not a literal that can be read from source. `--complete` makes a row of lane `e2e` without a spec an error (stretch rows never are). It prints a table per area (rows, rows of lane e2e, specs, missing).

**Alternatives considered.** Regular expressions (above). Playwright's own `--list --reporter=json` (it sees the tests exactly as they run, but it loads the whole support library and the config, so a broken fixture would fail the traceability check with an unrelated error, and it would accept titles built in loops, which are exactly what makes an id ambiguous). Putting the check into `docs:check` (it belongs to the specs, which arrive over several branches, so it has its own command and its own `--complete` switch that the orchestrator turns on when Phase 3 is green).

**Consequences.** One id is one `test()` call with a title written out in full: a parametrised test needs one call per id, which is the price of an unambiguous mapping. Tests defined through a helper function are invisible to the check (and show as missing rows). The check cannot see a conditional `test.skip(...)` inside a body. The check of the Playwright projects against the `Engines` column that the strategy mentions is not implemented: nothing in a spec says which engines it supports except the tags.

**Defending it.** "The catalog is only true if something refuses a spec that disagrees with it. Reading the syntax tree instead of the text means the refusal is about what the code does, and every message names the file, the line and the row it disagrees with."

## ADR-076: What the CPU throttle can and cannot say

**Context.** The strategy has a low-end profile (`chromium-cpu4x`, the stand-in for a television or a set-top box). Firefox and WebKit have no equivalent, and a throttle is not a device.

**Decision.** The auto fixture `cpuThrottle` reads `cpuThrottleRate` from the project's metadata ([`playwright.config.ts`](../../playwright.config.ts)) and, for the test's page and before anything navigates, opens a CDP session and sends `Emulation.setCPUThrottlingRate`. The session stays attached for the life of the page. A rate on a project that is not Chromium, or one that is not a number of at least 1, is an error: a silently unthrottled "low-end" run would be a lie. Measured on this machine (Chromium 156.0.8078.4, a loop of 20 million square roots in the page, seven runs each): median 18 ms without the throttle, 77 ms with `rate = 4` (4.3 times), 77 ms after a second navigation of the same page, 18 ms again after the session is detached; the same loop run inside a real spec in the two projects gave 18 to 25 ms and 76 to 79 ms.

**What it can say.** That the player still starts, plays and decodes when the main thread is four times slower; that a regression which costs main-thread time shows up as a slower startup or dropped frames in the performance runs of Phase 5, in the same environment against its own baseline.

**What it cannot say.** Anything about the GPU or a hardware decoder (the lab decodes in software), memory pressure, thermal behaviour, the network stack or a real television's browser: I measured a JavaScript loop on the main thread, and I did not measure whether decoder threads slow down. It does not make `PB-VOD-001` slower: the test is three seconds of media time and took the same time in both projects (3.6 s in `chromium-cpu4x`, 3.4 to 3.7 s in `chromium`), so the functional spec answers "does it start", and the performance gate is where the slowdown becomes a number. Firefox and WebKit have no low-end evidence at all.

**Alternatives considered.** Throttling with OS tools (`taskpolicy`, cgroups: not portable, not available on a macOS runner without privileges). A busy-loop thread beside the player (it competes for cores, not for the main thread, and its effect depends on how many cores the runner has). No low-end profile (the strategy's resume claim is "startup and dropped frames on a slow device").

**Consequences.** The profile exists in one engine and is documented as such. Every test tagged `@cpu` runs twice, once at full speed and once throttled, and the throttle multiplies the work of the merge gate for those rows only.

**Defending it.** "It is a slowdown of one thread in one engine, measured at four times with a loop. It is enough to find code that is slow on a weak CPU, and it is not a claim about any device."

## ADR-077: PB-ENV-001 plays through the player, and says what it found

**Context.** The row asks for a capability check per engine: a playable flavour, or a documented gap. The probe of Phase 1 decodes small synthetic clips in a fresh browser process per attempt, five attempts per case, and it needs the probe media, which is generated with ffmpeg. The specs depend on something narrower and more demanding: the lab's own streams, through the real player page, with the hook.

**Decision.** `PB-ENV-001` runs only where the shared fixture did not skip it for a documented gap. It asks `streamFor('vod', 'dash')` for the stream the matrix selected for this engine, opens it in the real player and requires a first frame, a second of media time and five decoded frames, no critical error and `loadMode === 'media-source'` (the probe's own pass criteria, through the player). It records the environment as an annotation (`local-darwin-arm64: chromium 156.0.8078.4; evidence: docs/results/codec-matrix/local-darwin-arm64.json`) and, when the engine is not the version the matrix was probed on, an `evidence-drift` annotation. When it fails, the message says: which engine and version could not play which stream in which environment, what the player said (with the timeline), the user agent, what the committed evidence claimed (or that there is none, and the command that documents the gap), and that this is an environment failure, not a playback regression, so the specs must not be retried. This was seen with an origin made to answer 503 to every media request: the failure names `chromium 156.0.8078.4 in local-darwin-arm64 ... Committed evidence ... claims it plays: cmaf-vp9-aac ok 5/5`.

**Alternatives considered.** Running `probeCapabilities` inside the test (slow, needs ffmpeg or a cache of probe media in the environment, and it would measure the probe's page, not the player's). Asserting the player on every flavour and protocol (it would repeat PB-VOD-002 and PB-VOD-013).

**Consequences.** ENV-001 proves the primary DASH flavour in the engines that are not documented gaps; WebM, HLS and live are proven by their own rows. A documented gap is not re-probed by the test: that is `npm run codec-matrix`, and the skip reason names the file. An intermittent engine can pass ENV-001 and fail later, so a pass is evidence for the run, not a proof of reliability, and for the experimental engine (Linux WebKit, ADR-072) a failure of ENV-001 reads as a failure of the experiment: its message says so and does not tell anyone to treat it as a change of the environment. Linux WebKit is where my own samples and the player phase's experiment agree against the probe's page. Before the engine was enabled, two samples were taken in the Playwright image on this machine with a made-up environment id, so that nothing was documented and nothing was skipped: the three specs, ten repetitions each, one worker and one browser process for the whole run, passed 30 of 30, and PB-VOD-001 alone, in ten separate container starts (a fresh WebKit process each time, as the probe does), passed 10 of 10. The player phase's experiment, with the real player in a fresh process per run, passed 80 of 80, and the probe's committed verdict for the primary flavour in the same image is 2 of 5: the probe's page is not the player's page. With the engine enabled, the three specs passed in three runs in a row in that image (ENV-001 in 1.6 to 1.8 s, PB-VOD-001 in 3.6 to 3.8 s, PB-VOD-002 in 3.5 s), next to macOS WebKit (2.0 to 2.4 s, 4.0 s, 3.4 to 3.7 s); they are a sample, not a rate.

**Defending it.** "The environment check should fail for the reason the specs would fail, with the evidence in the message. Playing the stream through the player does that in two seconds; re-running a matrix measures something else, and more slowly."

## ADR-078: A failure points at the spec's line and names the metric and the value

**Context.** Playwright prints the code frame of the first stack frame that is not in `node_modules`. An error created inside a helper points at the helper (`player.ts:54`), which tells a reader nothing about their test, and a Firefox page error arrives with the page's own stack in its message.

**Decision.** Errors that leave the support library (`PlayerHandle`, the log waits, the assertion helpers) have the frames of `tests/e2e/support` removed from their stack ([`stack.ts`](../../tests/e2e/support/stack.ts)), so the first frame is the line of the spec that made the call, and the page's own stack (V8's indented frames and Firefox's `fn@url:line:col` frames) and Playwright's `page.evaluate:` prefix are removed from the message, which keeps the hook's timeline. The assertion helpers use Playwright's `expect` with a message that names the metric as a reader would look it up in [METRICS.md](../METRICS.md) and the value it saw (`rebuffers (metrics.rebuffer.count): expected at most 1, saw 2 totalling 1840 ms: at media time 4.50 s for 1200 ms; ...`), so the failure carries the expected and received values. An error is not given a `cause` that repeats its message (Playwright prints the cause in full).

**Alternatives considered.** `test.step(..., { box: true })` for the helpers (it points the error at the caller and shows a step, but it turns the synchronous assertions into asynchronous ones and cannot be used outside a test, so the helpers could not be unit tested). Leaving the stack alone (the frame of the library is always the first).

**Consequences.** A bug in the library itself is harder to locate from a failure, because its frames are hidden; the unit tests exist for that. The page-stack filter recognises two formats; a third engine format would leave frames in the message, which is noise and not a wrong answer.

**Defending it.** "The report should show the line a person wrote and the number the player produced. Everything between them is the library's business and is tested without a browser."

## ADR-079: The fixtures are ordered so that the skip comes before the browser and the diagnostics before the cleanup

**Context.** Playwright sets up fixtures by dependency, lazily, and tears them down in reverse. Two orders matter. Firefox does not start on the macOS host: a test that must be skipped there must be skipped before the browser is launched, not after (a skip in the test body, or in a hook that asks for `page`, comes after the fixture has started the browser, and the launch fails). And the diagnostics read the page and the server's log: they must run before the page is closed and before the session is deleted.

**Decision.** `documentedGap` is an auto fixture that depends on nothing that starts a browser, and every fixture that starts a browser or creates a session (`cpuThrottle`, `newSession`, `streamFor`, `labRun`) names it as a dependency, so it is set up first whatever the order of declaration. `diagnostics` is an auto fixture that depends on `newSession` and `player`, so it is torn down before them: the page is still open and the sessions still exist when it reads them. The things the test created (`labRun`: its sessions and its handles) are held by one internal fixture that the other three share. Checked on this host: `npx playwright test --project=firefox` on macOS skips each test in about a millisecond, with the reason in the report, and no browser starts; in the Playwright image the same project runs.

**Alternatives considered.** Skipping in `test.beforeEach` (too late, above). Removing the projects that cannot run from the config (the config would have to read the evidence, and a project that disappears is a silent skip). Overriding the `browser` fixture to refuse to start (the test would fail, not skip, and the reason would be an exception).

**Consequences.** The order is a contract of the dependency graph, not of a comment: someone who adds an auto fixture that uses `page` without depending on `documentedGap` can start a browser that cannot start. The fixtures are in one file, next to this warning, and the only checked behaviour is the run on the host described above; there is no automated test of the order.

**Defending it.** "A fixture graph is a program. The skip has to come before the thing it avoids, and the report has to be read before the world it describes is deleted; both are true because of what each fixture asks for, and I ran the one case that can go wrong."
