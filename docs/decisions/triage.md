# Failure triage decisions (ADR-160 to ADR-169)

Architecture decision records for the failure triage of [TEST_STRATEGY.md](../../TEST_STRATEGY.md) sections 5 and 10 and the catalog row PB-LAB-005: the modules in [`triage/`](../../triage), the mock of the model API [`tools/triage-mock.ts`](../../tools/triage-mock.ts) and the fixture reducer [`tools/triage-fixture.ts`](../../tools/triage-fixture.ts). The guide for a person who runs it is [TRIAGE.md](../TRIAGE.md). The lab-wide decisions this builds on are ADR-073 (the failure attachments) and ADR-083 (the request log) in [e2e.md](e2e.md) and [server.md](server.md), and ADR-132 (the one error signature) in [flake.md](flake.md).

**What these records do not have is an answer of the live service.** There is no API key on the machine that built this, and none was created: the optional model summary was verified against a local mock that follows the documented shapes (ADR-168), and the numbers about its cost are arithmetic from the published prices (ADR-169), not measurements. Everything about the deterministic part (signatures, clusters, categories, redaction, the report) is tested on the lab's own failure messages and attachments, which the tests generate by calling the lab's own code, and on seven real failures of the lab that were induced on purpose and run through the real specs ([results/triage](../results/triage/README.md): 31 failed tests, 12 clusters, 8 root causes; what it corrected is in ADR-161 to ADR-165).

## ADR-160: The clustering is the contract, the model is optional, and triage never decides a verdict

**Context.** The resume line is "AI-assisted failure triage that clusters CI failures by root cause". The tempting design is to hand a model the logs of a red build and publish what it says. That fails in the ways that matter in CI: the answer differs between runs (the same failures cluster differently on Tuesday), it costs money per build, it sends the lab's failure data to a third party, it needs a key and a network (so it cannot run in a pull request from a fork, offline, or in a unit test), and a wrong answer looks as confident as a right one. A merge gate that depended on it would make the explanation of a red build the least reliable part of it. At the same time, the real need is plain: three engines fail one cause a dozen ways and a person should not read a dozen failures to learn that.

**Decision.** Two steps, and only the first is the product. **Step one is deterministic code**: failures are grouped by a signature (ADR-161), the groups are given a root-cause category by an ordered table of readable rules that print their evidence (ADR-163), and the report ranks them and says the first thing to check. It needs no key, no network and no clock, and gives the same clusters in the same order for the same failures whatever order they arrive in. **Step two is optional prose**: with `--summarize` and a key, each cluster's redacted evidence goes to a model, which drafts a likely root cause for a person (ADR-167 to ADR-169). A draft is printed as a suggestion, quoted, with the model it came from; it never changes a cluster, a category, a class or a verdict. `npm run gate:triage` is `triage --from-ci`: it reads the artifacts of its run, says on its first line that it **is not a gate**, and **exits 0 whatever it finds, whatever it cannot read and whatever breaks in it** (and 2 only for a bad command line), so it cannot turn a build red or green; the gates decide ([TEST_STRATEGY.md](../../TEST_STRATEGY.md) section 6). With nothing failed it prints `no failures to triage`.

**Alternatives considered.** A model that clusters the raw logs (nondeterministic, untestable, expensive, and it hides a cause when it merges two). Similarity clustering of the messages with embeddings (it needs a model or a library, a threshold to tune on data the lab does not have, and "similar text" is not "same cause": two timeouts with different causes read alike). Regular expressions per category and no clusters (the same cause is still a dozen lines). A triage stage that fails the build when it finds an environment problem (a second verdict that competes with the gates and that someone will eventually trust over them). Making the summary the default (a surprise bill and a data transfer nobody asked for).

**Consequences.** The product works offline, in a fork's pull request, in a unit test and without a key. It knows only the causes its rules know: what no rule recognises is `unknown` and says so, which is the honest answer and the signal to write a rule (ADR-165). The model part is small, optional and fenced (ADR-166 to ADR-169), and claiming it is "AI-assisted" is true only in the way the documentation states: the requests were verified against a mock, the live service was not called. Because the stage never fails, a bug in triage costs a missing explanation and never a blocked merge.

**Defending it.** "A triage that is a model call is a demo. A triage that is code I can test, with a model as a draft on top that I can switch off, is a tool a team keeps: the clusters are the same on every run, the category says which rule fired and what it found so I can overrule it, and the model's words never move a verdict. And I say what I could not verify instead of letting the word 'AI' do the work."

## ADR-161: A signature is four stable parts, built on the lab's one error signature

**Context.** To say that nine failures are one cause, each needs a name that does not change with the session id, the port, the timestamp, the path of the machine, the engine, or the number of milliseconds in a message. The flake tracker already has such a function (`errorSignature`, ADR-132): the first line of the message with numbers, ids, timestamps, urls and paths replaced. Triage needs that, and a little more, because a clustering that is too coarse merges two causes (and a person stops reading the cluster) and one that is too fine splits one cause across three engines.

**Decision.** The signature is `message [assertion] @ location {shaka}`:

- **message**: the first line that says something (a bare `Error:` is joined with the line after it), normalised by the **same function** the flake tracker uses (`normaliseLine` and `cutSignature` are now exported from [`src/lab/signature.ts`](../../src/lab/signature.ts), `errorSignature` is made of them, and its tests were extended and still pass: one normalisation, not a fork), then three steps only triage needs. The three engines' words for a refused or reset connection (`net::ERR_CONNECTION_REFUSED`, `NS_ERROR_CONNECTION_REFUSED`, `Could not connect to the server`) are one phrase. A rung id (`v360`) is `<rung>`, because the engines start on different rungs and one cause must not split by the rung it hit. A fault rule id (`f1`) is `<rule>`, because the service numbers the rules of a session in order. A list of identical `; `-separated items is its first item and `…`. Three more steps were added because real runs needed them (ADR-162): the name of an engine (`chromium`, `firefox`, `webkit`, `chromium-cpu4x`) is `<engine>` and the id of the environment (`local-darwin-arm64`) is `<env>`, because a message that names them (the environment check does) would split one cause by engine; and the JSON of a fault rule that a fault message quotes is `{…}`, because 150 characters of rule push the words that tell two causes apart past the cut of 200 characters.
- **assertion**: the matcher that failed (`toBeLessThanOrEqual`, `not.toBe`), `test-timeout`, or `thrown`. The message of a lab helper has its own words, and the matcher says what kind of thing was checked.
- **location**: `file:function` of the first **application** frame that is not a spec (frames in `node_modules` and in Playwright are dropped), **with no line number**. A line moves with every edit and a signature names a cause, not a revision; a function name is stable. A spec's own body names the test and not the cause, so it is left out: the same helper failing in ten specs is one signature. When the message has no words of its own (`expect(received).toBe(expected)`, `Test timeout of 45000ms exceeded.`) the **spec file** is added, because otherwise every unrelated timeout would be one cluster.
- **shaka**: the first **critical** Shaka error the player reported, from the timeline and the metrics ([`src/player/errors.ts`](../../src/player/errors.ts) names them): its code, or `media` for any error of the media category (3xxx). A recoverable error does not split a cluster: it is what a healthy retry looks like. The category and not the code for media errors is a result of the real runs (ADR-162): WebKit and Chromium reported the same corrupt bytes as 3015 and 3016.

The signature is hashed (12 hex digits of its SHA-256) into the **cluster key**, the stable name of a cluster and of its cached draft.

**Alternatives considered.** The flake signature alone (it has no engine wording and no code, so the same refused connection is three clusters and two different Shaka errors behind one generic message are one). The stack's top frame with its line number (every edit of a helper renames every cluster, and the history of a cause is lost). Hashing the whole message (a timeline in the message makes every failure unique). Including the engine or the project (it would defeat the point: the same cause in three engines is one cluster listing three engines). Including the test id (ten specs on one broken helper are ten clusters).

**Consequences.** The flake tracker's history is untouched (its signature is still the blunt first line), and triage's message part agrees with it wherever the three extra steps do not apply. Two failures are the same cluster exactly when their four parts are equal, which is a definition a person can check by reading two lines. The parts are all in `triage-report.json` (`parts`), so a surprising merge or split can be debugged by comparing them.

**Defending it.** "I did not invent a second normaliser: I exposed the steps of the one the flake tracker uses and added the three things triage needs, each for a reason I can name. I left the line number out on purpose, because a signature that changes when someone adds an import is not a name for a cause."

## ADR-162: What the signature over-merges and over-splits, and how determinism is tested

**Context.** Any signature is a bet that equal names mean equal causes. A bet that is stated can be checked and improved; one that is hidden produces clusters that look authoritative and are wrong.

**Decision.** The limits are written down (here and in [TRIAGE.md](../TRIAGE.md)), and the report shows what the signature cannot see. **Over-merging**: two causes with the same first line, the same helper, the same assertion kind and no critical Shaka error are one cluster (for example two different requests that make the same rebuffer bound fail). The report does not hide it: the rules run on every member, and when they disagree the cluster says `the rule fired for N of M failures; the others fired <rule>`, and every member is listed with its test, engine and outcome. **Over-splitting**: one cause is split when an engine words it in a way the table of wordings does not know (the table has a refused and a reset connection, in the words of the three engines' own error names, none of which has yet been compared with a failure of this lab in that engine; a wording nobody has seen is not guessed), when the same failure carries a different critical Shaka code in two engines, when a free-text value that is not a number or a known id (a stream name) appears in the first line, or when the helper that threw differs. A person merges those by reading two adjacent clusters; clusters are never merged by similarity, so two clusters that read almost alike are listed apart, and that is a limit too. **Determinism** is tested rather than argued: the same failures in any order (shuffled), with different session ids, ports, timestamps, absolute paths and engines' ordering, give the same clusters in the same order with the same keys; two different root causes never merge (a table of near misses); the same cause in two engines is one cluster listing both; the representative of a cluster does not depend on the input order (it is the failure with the richest diagnostics, then by engine, test id and attempt); and the order of the clusters breaks every tie with the signature compared by code unit, so it does not depend on the locale of the machine.

**What seven real failures of the lab showed** (induced in a scratch copy and run through the real specs, [results/triage](../results/triage/README.md)): four of the limits above were not hypothetical, and each was fixed with a test and none by editing a fixture. **Over-splitting by engine**: the environment check's message names the engine and the environment, so two engines made two clusters (now `<engine>` and `<env>`); WebKit and Chromium reported the same corrupt bytes as Shaka 3015 and 3016, so two engines made two clusters (now `{shaka media}`). **Over-merging**: the recovery specs quote a whole fault rule as JSON before the sentence that matters, so the cut fell before the words that tell "the origin was down" from "the player gave up", and two causes read together were one cluster (now `{…}`). **One cause, several clusters**: different specs word one cause differently, which the signature cannot undo by construction; this is what root causes are for (ADR-163). The same runs also showed what stays a limit: a slow origin, which fails no request, is two root causes (a premise and a rebuffer count), and a Firefox or WebKit wording of a refused connection was not compared, because Firefox is a documented gap on the host that ran them.

**Alternatives considered.** A tuned similarity threshold (it would hide the over-merge in a number). Splitting clusters by test id to be "safe" (it removes the point of clustering). Learning the wordings from data (the lab has failure data from a handful of experiments, not a corpus).

**Consequences.** A wrong cluster costs a person a minute of reading two lines, not a wrong verdict. The wording table is the part most likely to grow when the first real failures of Firefox and WebKit arrive; adding a wording is a line and a test. The signature does not recognise a cluster across builds except by its key: history is the flake tracker's job.

**Defending it.** "Deterministic means the same input gives the same output in the same order, and I test it by shuffling. It does not mean always right. Where it is wrong I can say in which direction, and the report shows the members so the person is never taking my word."

## ADR-163: Categories are an ordered table of named rules, and the first match wins

**Context.** A cluster needs a root-cause category (TEST_STRATEGY.md section 10 asks, for every failure, "environment, regression, flake or gap?"). The category has to be explainable: a person looking at "environment" must be able to see why, and to overrule it.

**Decision.** `RULES` in [`triage/rules.ts`](../../triage/rules.ts) is a list of rules, each with a unique **name**, a **category**, a **class** of section 10, a one-line **rationale** (why this evidence means this cause), a **first check** written as an instruction, and a function that either returns **evidence lines** (strings a person can check against the attachments: the fault that fired, the requests that failed, the wait that ran out and which event) or `null`. The first rule that returns evidence wins, and the report prints its name, its rationale and its evidence. The order is part of the contract: **a rule that names a cause comes before one that describes a symptom**. A test that timed out waiting for the first frame is a symptom of a fault that the player did not recover from, so `fault-fired-player-failed` (a rule fired in the request log **and** the player ended in a critical error) comes before the waits; an origin that failed with no fault rule on it (`origin-error`) comes before the player's own error it caused; an environment rule (the service unreachable, a browser that did not launch, a missing stream) comes first of all, because it explains failures that otherwise look like many unrelated regressions. Rules run on **every member** of a cluster, and the cluster is described by its representative's verdict plus how many members agree. A cluster whose failures were all flaky is class **Flake** with the advice not to rerun the job (section 10), unless its rule says environment or known gap, which are more specific. What no rule recognises is `unknown`, class **Needs a person**: it is the rule that stands for "nothing matched" and is deliberately not in the table, so no rule can be added after it.

**Alternatives considered.** A score per category with weights (a number that cannot be argued with or tested by reading). A decision tree in code (the same, with nesting). A classifier trained on past failures (there are none labelled, and its mistakes would not explain themselves). The model as the classifier (ADR-160). One rule per message regex with no evidence (the person is asked to trust a label).

**Consequences.** Every category in a report is traceable to a rule, a rationale and evidence lines, and the rules are the documentation of how the lab's failures read: the table is in [TRIAGE.md](../TRIAGE.md), and a test fails when a rule or a category is missing from it. The cost is that the rules read the **words of the lab's own helpers** (the hook's wait timeouts, the request wait, the readiness check): a reworded helper would quietly turn its failures into `unknown`. The tests therefore produce their messages by calling those helpers, so rewording one fails a test here. A rule does not claim a cause is proven: it claims that this evidence is what that cause looks like.

**Root causes.** The signature is the words of one failure and the category is a rule's reading of it, so one cause worded by several tests is several clusters in one category (seen on real runs: an origin that answered 503 to every segment was three clusters, a Content Security Policy that blocked the page two, a player that lost its retry policy two). A rule that **names a cause** (not a symptom) therefore also says what exactly is broken, in a phrase computed from its evidence and not from the test's words (`the origin answered 503 on segment to requests no fault rule named`, `a fault of type status fired and the player did not recover`, `the player page did not boot: a Content Security Policy blocked its scripts`), and clusters that fired the same rule for the same cause are one **root cause**; a rule that only describes a symptom (a wait that ran out, a premise, a metric) has no cause and its cluster is its own root cause. The report says it in the headline (`12 clusters of 8 root causes`), in a table of the root causes that several clusters share, and in the JSON (`rootCauses`, `clusters[].rootCause`); the clusters themselves are unchanged. The cost is a second thing to get right per cause rule; the limit is that a cause that fails no request (a slow origin) has no phrase, so its symptoms stay root causes of their own. Also from the real runs: the environment check wraps what the player said, and when that is a page that did not boot the check no longer blames the environment (the page rules take it); and a failure of the run whose message says the web server did not start gets the evidence that the service's own output, which has the reason, is in the job log and not in the report.

**Defending it.** "Each rule is a sentence I can say out loud: 'a fault fired and the player ended in a critical error, so the recovery failed, not the test'. The first match wins because I wrote them from cause to symptom, and the report prints the evidence, so if I am wrong someone can see exactly which sentence was wrong."

## ADR-164: Triage reads the report and the lab's own attachments, and reads the request log by the contract

**Context.** The data of a failure is already shaped by [ADR-073](e2e.md): a failed test attaches the player's timeline and metrics, the page's configuration and console, the session's fault rules and the request log, under fixed names. Playwright's own report carries the message, the stack and the attempts. A red build also has failures that carry none of this: a browser that did not launch, a global setup that threw. And the request log has a trap ([ADR-083](server.md), [CONTRACTS.md](../CONTRACTS.md) section 4): since `abortReason` exists, a response aborted because the **client** hung up (a player cancelling a request when it seeks or changes rung) is not an origin failure, while one cut by a fault or by a service error is.

**Decision.** The collector reads every `playwright*.json` under a directory at any depth (a reports directory, a directory of downloaded artifacts with a report per engine job, or one file), and for each test whose final status is failed or timed out, or that is flaky, builds a typed `Failure`: id, engine, tier, attempts, the first failing attempt's message and the **application frames** of its stack, the digests of the attachments of that attempt (or of a later one, said, when the first has none), the environment id, and `missing`, the sentences that say what could not be read. The JSON reporter keeps attachment bodies in the report (base64), so the report alone is enough; attachments kept as files are looked for next to it and in `test-results*`. A failure of the **run** (a global setup that threw, a web server that did not start) has no test to blame and becomes a failure of its own with no attachments. Skips are listed apart with their reason, and a skip with none is printed as a bug (section 10). Interrupted tests are counted, not clustered. Nothing throws on what it finds: a file that is not a report, or that cannot be parsed, is named in the report. The request log digest counts an **origin failure** as a finished request with a status of 400 or more, or one aborted with a reason other than `client-closed`, and counts the client's hang-ups apart; `SessionDetail.counters.errors`, which counts both, is not used for this.

**Alternatives considered.** Reading `test-results/` directories and the HTML report (they are for people; the JSON is the contract). A reporter of triage's own, as the flake tracker has (it would need to be wired into every run, and Playwright's report already has everything). Counting every aborted response as an origin error (a player that seeks would then "cause" origin errors in every seek test). Skipping a failure whose attachments are missing (the launch failures are exactly the ones that explain a red build).

**Consequences.** One attachment contract serves the person who opens a failure and the program that clusters it. Only Playwright reports are read: a failure of the unit tests has nothing for triage, and says so. The collector is tested on reports of the shape the JSON reporter writes (built from Playwright's own source, the `JSONReport` types and the reporter that writes them), on the lab's own attachments, produced by calling its own `attachDiagnostics`, and on seven real reports of the lab ([results/triage](../results/triage/README.md)). Reading real data corrected it twice: a report of a listing (`--list`) has every test as `skipped` with no attempt, and read as 66 skips with no reason, where there is a bug to flag in none of them (a test with no attempt is now `not run`, which is neither a failure nor a skip); and an attachment kept as a file is looked for beside the report that names it before anywhere else, because two reports of the same run have directories of the same name.

**Defending it.** "I read what the lab already writes on purpose, and I say what is missing instead of guessing. And I did not count a player's cancelled request as the origin failing: the contract says it is not, and a triage that blamed the server for every seek would be wrong in the most common test."

## ADR-165: A new rule is a row and three tests, and what the table is honest about

**Context.** The first set of rules is a guess about what will fail. The value of the table is that it grows from failures that were not recognised, without anyone having to understand the whole.

**Decision.** To add a rule: write it in `RULES` **in the place of its strength**; give it a name, a rationale and a first check; test it in `rules.test.ts` with a failure that fires it (its message produced by the helper that writes it, never retyped), a near miss that does not, and the rules above and below it in the order; and add its row to [TRIAGE.md](../TRIAGE.md), which a test requires. Two things were added to what the strategy lists, and are stated here because the strategy did not ask for them. The category **`player-error`**: a player that failed with a critical error that no fault, no origin failure and no media error explains is neither a timeout nor a decode problem, and filing it under either hides it. The class **Needs a person** for `unknown`: section 10 has five classes and none of them is "no rule recognised this". The rules also know what they cannot know: a **negative** test, one that expects the player to fail (the manifest that is down, PB-REC-006), and that then fails on a timing bound while a fault fired and the player ended in an error, reads as `network-fault-not-recovered`, because the rule cannot know the error was expected. The evidence says what fired and the test's name says why. A second thing the table is honest about: a test that checks its own condition before it judges, and says so (`premise of the test, not the behaviour under test`, PB-VOD-006), is a failure that tells nothing about the behaviour; rule `test-premise-not-met` names it (category `instrument-disagreement`, whose meaning now includes a premise that did not hold) and gives it the class `Needs a person`, because whether the host, the origin or the player is at fault is not in the failure. It was `unknown` until a real run of a slow origin produced it.

**Alternatives considered.** Putting `player-error` under `timeout-waiting-for-event` or `decode-or-mse-error` (it is neither). Inventing a sixth class under another name (a guess dressed as a class). Teaching the rules each test's expectations (a second copy of the specs that would drift).

**Consequences.** The table is meant to be extended in small steps, each with a test that fails without it. The known wart is in the documentation where a reader will find it.

**Defending it.** "A rule is cheap to add and impossible to add silently: it needs a row, a near miss and a place in the order. And the two things I added beyond the brief are in the ADR, with the reason, not in a comment."

## ADR-166: Redaction is a list of named steps and a last check that fails closed

**Context.** The evidence of a failure is the lab's own data, but it was produced on a machine: it holds absolute paths with a person's name, hostnames of CI agents, URLs with query strings, and, if something went wrong in a test, a token in a header or a message. Sending any of it to a third party must not leak a secret, and **must not depend on the redactor being perfect**.

**Decision.** Three lines of defence. First, **nothing leaves unless a person asked** (`--summarize` with a key), and what leaves is a **digest** (ADR-167), never a page, a trace, a screenshot or a raw attachment. Second, `redact()` in [`triage/redact.ts`](../../triage/redact.ts) is an ordered list of **named steps** (each is a pattern and a replacement that says what it took out: `<jwt>`, `<host>`, `<home>`): private-key blocks and secret headers; tokens that have a format of their own (the API key shapes of the model service, other services' keys, GitHub tokens, cloud access keys, a JWT, a bearer or basic credential); a URL's host, credentials, query and fragment (the scheme and the path stay, because what was asked of the service is evidence); assignments of a password, a key, a token or a secret to a name (`password=` and its kin); long hex strings; emails, addresses, hostnames and `localhost`; CI workspaces and the home directories of three systems and the directories of absolute system paths (the file name stays). The order is part of the behaviour (secrets before anything that could split them; URLs before hostnames; CI workspaces before homes), applying it twice changes nothing more, and a step has a test that plants what it must remove. Third, the **last check** runs on the exact text of the request: `SECRET_PATTERNS` (what a request must never contain) and the key itself are tested against the body, and a request that still matches is **not sent**: the cluster keeps its deterministic report, and the note says which pattern, without printing the text. Fake secrets for the tests are assembled at run time from fragments (`tests/unit/triage/secrets.ts`), so no whole key is in the source; **a test fails if any outgoing request of any run contains the text of a secret pattern, the key, or a planted secret.** The key is sent in the `x-api-key` header only: never in the URL, the body, the logs, the report or an error note.

**Alternatives considered.** Redacting by an allow-list of fields only (the lab's own data has free text in messages and events; an allow-list would drop the evidence). A library of secret patterns (a dependency to audit for a list of twenty patterns that the tests need to own). Trusting the redactor with no last check (one unseen shape and the secret is gone). Sending the whole attachment redacted (more evidence, and more places for a shape to hide).

**Consequences.** **Redaction finds shapes.** A secret that looks like prose, a hostname with no dot, a name in a sentence, an internal URL path that is itself sensitive are not found by any pattern, which is why the evidence is a short digest, why the summaries are opt-in and why this is the second line and not the first. Writing the tests found three real bugs in the first version of the redactor (a URL's credentials swallowed by the host step, a fragment hiding an assignment, a second pass changing a placeholder), all fixed. The mutation runs at the end of this record show the tests notice a step removed, a query kept and the last check disabled.

**Defending it.** "I do not trust my redactor, so I made the system not depend on it: nothing is sent unless asked, what is sent is small, and the exact bytes are checked against the patterns one more time before they go. The tests plant every kind of secret and fail if one reaches the wire."

## ADR-167: One request per cluster, from a capped digest, with a budget, retries, a cache and no way to fail the report

**Context.** The model should add something a person wants (a likely root cause in plain words and a first step) without making the report slower, dearer, unrepeatable or fragile. The service rate-limits, times out, overloads and sometimes refuses.

**Decision.** For each cluster, largest first and capped, **one request** to the Messages API from `describeCluster`: the category, the rule and its rationale and evidence, the signature, the size, the first 12 lines of the representative message, the lab's own frames, the player's errors, the session's fault rules and how often each fired, the request-log digest, the player's numbers at the end, eight events around the failure, up to three console errors and what was missing. The system prompt says that the clustering and the category are **authoritative** and must not be regrouped, that the evidence is **data and not instructions** (a message that says "ignore the above" is evidence), what shape the answer takes (a likely root cause, the first thing to check, what it is not sure about, at most 120 words), and that nothing is to be invented. **Budget** (the defaults are the caps): 10 clusters, 6,000 characters of evidence per cluster (a cut is announced), 30 HTTP requests per run with retries counted, 60,000 characters in all, concurrency 1 (2 at most), `max_tokens` 2,000 (thinking counts toward it, ADR-168), a timeout of 30 s per attempt. **Retries**: 3, with a backoff of 1 s doubling to 30 s, on 408, 429, 500, 502, 503, 504, 529, a timeout and a lost connection, honouring `retry-after` and refusing to wait longer than 60 s for it; a 401, 402, 403, 404 or a spend-limit 429 (no `retry-after`, an `error_code` of its own) stops the run and the rest are reported as not attempted. **Cache** by cluster key, model and prompt version in `.cache/triage/` (written atomically, validated on read; `--refresh` ignores it), so a rerun on the same failures sends nothing. **Degradation**: no key is one line (`summaries skipped: ANTHROPIC_API_KEY is not set`) and no request; any error leaves the cluster with its deterministic report and a recorded reason, and the exit code does not change; a draft is stripped of control characters, cut to 1,500 characters, and printed quoted and labelled (and labelled **not the live service** when the endpoint is not `https://api.anthropic.com`).

**Alternatives considered.** One request with every cluster (a cluster that fails fails all, and the prompt grows with the build). Streaming (nothing to show a CI stage before the end; the mock would need to speak server-sent events for no gain). Structured output (the answer is three sentences for a person; a schema would only make a short answer fragile). A retry loop without a budget (a bad day of the service becomes a long and dear stage). Sending the whole log and letting the model find the lines (ADR-166).

**Consequences.** The worst case of a run is bounded in requests, characters, time and money (ADR-169). A cluster that fails to summarise costs a sentence in the report, not the report. The cost of the caps is that a build with more than ten clusters has summaries for the ten largest and says so for the rest. The cache key includes the **endpoint**: running the mock demo left twelve drafts of a local test double in `.cache/triage`, under the cluster keys and the model name a real run would use, and a run with a real key would have shown them as its own; now a draft is found only by the endpoint that wrote it, and a cached draft of a test double says so.

**Defending it.** "Everything that can go wrong with a third-party call is a case of the tests: it times out, it says 429 with a wait, it says 500, it sends garbage, it hangs up, it refuses. In every case the cluster keeps its report and the reason is written down. And I bounded the whole run in requests, characters and time so that the bill and the stage cannot surprise anyone."

## ADR-168: The request is the one the documentation describes, and the mock proves exactly that

**Context.** The brief for this phase fixed the shape of the call from the Anthropic Messages API as it was known. The documentation moved: the version header, the authentication header, the models and what a model returns have all changed since the shape people remember. And the code cannot be run against the live service, so what it was **checked against** is the documentation, and what it can **claim** is only that.

**Decision. What was read (2026-11-04) and what it said.**

- [Create a Message](https://platform.claude.com/docs/en/api/messages/create): `POST /v1/messages`; the body's `model`, `max_tokens`, `system` (a string or text blocks) and `messages` (the last turn is the user's: a prefilled assistant turn is a 400); the answer is a message whose `content` is a list of blocks, the text in the blocks of type `text`, with `stop_reason` and `usage`.
- [API overview](https://platform.claude.com/docs/en/api/overview) and [Authentication](https://platform.claude.com/docs/en/manage-claude/authentication): `Authorization` is the primary header, `x-api-key` is called "legacy fallback for `Authorization`, still supported", and the page's own cURL examples still use `x-api-key`; `anthropic-version` and `content-type: application/json` are required; a key that is **not scoped to one workspace needs `anthropic-workspace-id` on every request, and a key scoped to one workspace must omit it**.
- [Versions](https://platform.claude.com/docs/en/api/versioning): `anthropic-version` is required; `2026-10-21` is the newest and the one Anthropic recommends, `2023-06-01` and `2023-01-01` are older; in `2026-10-21` the `temperature`, `top_p` and `top_k` parameters are removed and a request that sends one is a 400 on every model.
- [Errors](https://platform.claude.com/docs/en/api/errors) and [Rate limits](https://platform.claude.com/docs/en/api/rate-limits): an error is `{ "type": "error", "error": { "type", "message" }, "request_id" }` with a `request-id` header; 400, 401, 402, 403, 404, 413, 429 (`rate_limit_error`, with `retry-after`), 500, 504 (`timeout_error`) and 529 (`overloaded_error`); a 429 for an enforced spend limit has no `retry-after` and an `error_code` of its own (retrying cannot help), and a limit the owner set is a 400.
- [Models overview](https://platform.claude.com/docs/en/models/overview) (re-read when this record was written): **Claude Haiku 5.5, API ID `claude-haiku-5-5`**, "for high-volume, latency-sensitive tasks such as classification, extraction, and routing", from $0.10 per million input tokens and $0.50 per million output tokens, thinking **adaptive**, default effort `medium`, a context window of 1M tokens and 128K of output, retirement not sooner than October 7, 2027. The ID has no date suffix. The Haiku 5.5 page, the migration guide and the [thinking](https://platform.claude.com/docs/en/build-with-claude/thinking) page: with adaptive thinking a response can begin with `thinking` blocks, the thinking tokens count toward `max_tokens`, and a response can stop at `max_tokens` before any text.

What was built from it: the default model `claude-haiku-5-5` (`ANTHROPIC_MODEL` overrides it); `x-api-key` for the key (**kept as the brief fixed it**, and as the owner decided: the documented primary `Authorization: Bearer` is one line away in `send()`, but a change of the authentication header would be untestable here, because no key exists on this machine and the summarizer is verified against the local mock only; the legacy header is "still supported" today, and if it is retired the first live run fails with a 401 whose note says so); `anthropic-version: 2026-10-21` (**a deviation from the brief, which said `2023-06-01`**: the documentation recommends the newest, its own examples send it, the one change it makes to the Messages API (the removed sampling parameters) concerns parameters this tool never sends, and an old version is preserved by the service; the version is an option of `summarize()`); `anthropic-workspace-id` only when `ANTHROPIC_WORKSPACE_ID` is set (found by re-reading the authentication page: a person with a key that is not scoped to a workspace would otherwise get a first live run that fails); a body of exactly `model`, `max_tokens`, `system` and one user message, with no sampling parameters, no `thinking`, no `output_config`; the answer taken from the blocks of type `text`, so thinking blocks are skipped; and `max_tokens` of 2,000 so that the thinking of a short answer does not use the whole budget (when it does, the cluster fails with a note that says so).

**What the mock proves, and what it cannot.** [`tools/triage-mock.ts`](../../tools/triage-mock.ts) is a local server on `127.0.0.1` (default port 4751) that **refuses what the documentation says the service refuses**: a missing or wrong `x-api-key` (401), a missing or unknown version, a wrong content type, a field outside the list or a removed one, a prefilled turn, `stream: true`. It answers with the documented shapes: success (optionally with thinking blocks, or with no text, or after a delay), 400, 401, 429 with `retry-after`, 500, a body that is not JSON and a dropped connection, with the error format and the `request-id` header. Its answer says in its first words that no model wrote it. The tests drive the real `summarize()` against it and assert the exact request (the headers, the body's keys and values), that the key is in one header and nowhere else, the secret-leak check on every request, retries and the honouring of `retry-after`, the budget, the cache, the degradation and the labelling. **It cannot show** what the real service answers to this prompt, whether a model follows the requested shape, the real limits and prices, a change of the API since the day it was read, or whether the mock itself matches the service where the documentation is silent (its error messages are its own words). The wording of every claim in the README and in TRIAGE.md follows from that: **verified against a mock of the documented shape; never run against the live service.**

**The command the owner runs with a key:**

```sh
ANTHROPIC_API_KEY=... ANTHROPIC_MODEL=claude-haiku-5-5 npm run triage -- --from reports --summarize
```

**Alternatives considered.** The official SDK (a dependency of its own, with its own retry and header logic that the tests would then not own, for one call). Keeping `2023-06-01` because the brief said so (it works, and is the safer bet against a surprise in the newest version; it is also not what the documentation sends today, and the point of this record is that the call was checked against the documentation, so the checked value won, flagged as a deviation). Sending `Authorization: Bearer` (the documented primary; the brief and the tests fix the legacy header, and both are accepted today). Checking the shape with a recorded real response (there is none, and inventing one would be the thing this record exists to avoid).

**Consequences.** The first run with a real key is the first time the real service is spoken to. Three things in this record are the likeliest to need a fix then, and each is one line and one test: the authentication header, the version, and the shape of an error the documentation does not show. Until that run, "AI-assisted" describes a mechanism that is verified against its specification, and the documentation says it that way.

**Defending it.** "I did not call the API from memory: I read what it says now, and the code differs from my brief where the documentation does. I wrote down which parts I could prove (the request, against a server that rejects what the service rejects) and which I could not (the answers), and I gave the owner the one command to find out."

## ADR-169: Sending failure evidence to a third party is opt-in, redacted, capped, cached, and its cost is arithmetic

**Context.** A summary of a failure is the lab's failure data on another company's servers, for a fee. A portfolio project that does this by default, or says nothing about its cost, is a project whose author did not think about the user.

**Decision.** **Opt-in**: nothing is sent unless `--summarize` is given **and** `ANTHROPIC_API_KEY` is set; with only the first, one line says the key is missing. **Redacted** (ADR-166) **and small** (ADR-167): the evidence is a digest and never a page, a screenshot, a trace, a video, a raw attachment or a source file; the test titles and ids that go are the lab's own. **Capped**: 10 clusters, 30 requests, 60,000 characters per run. **Cached**: the same cluster is not sent twice (`.cache/triage/`, git-ignored); `--refresh` is the only way to ask again. **The destination is visible**: the report names the endpoint and model of every draft, and a draft from any endpoint but the live one says so in capitals. **Cost, by arithmetic** from the prices of the models overview (from $0.10 per million input tokens and $0.50 per million output tokens): a typical run (a few clusters of 1,000 to 2,000 input tokens and about 300 output tokens) costs a fraction of a cent; the caps bound a run at 60,000 characters of input (about 20,000 tokens, more with the new tokenizer's larger counts) and 30 requests of at most 2,000 output tokens (60,000), which is under four cents at those prices. **Nothing here was measured**: nothing was sent. The report prints the tokens the service says it used when a real run happens.

**Alternatives considered.** On by default when a key exists (a key in a CI environment for another purpose would start sending failures). A hosted triage service (the same transfer, with a second party). A local model (no key and no transfer, and a download, a machine and an accuracy this lab cannot test; it is a good follow-up and the summarizer's endpoint option is where it would plug in).

**Consequences.** A reviewer can read the privacy and the cost in one paragraph and in the code that enforces it, and the default run of the repository never leaves the machine. The price of the caution is that summaries are a deliberate act, which suits a stage that explains a red build and is not part of one.

**Defending it.** "I treat a call to a third party as a feature with a cost and a risk, so it is off, the amount is bounded, what leaves is small and cleaned and checked a last time, and I wrote the arithmetic down as arithmetic. When someone runs it with a key, the report says what was spent."
