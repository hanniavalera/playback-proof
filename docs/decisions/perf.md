# The performance harness decisions (ADR-120 to ADR-129)

Architecture decision records for the harness that takes the lab's performance baselines and gates merges on them: the measurement library [`src/lab/measure`](../../src/lab/measure) (statistics, rules, the baseline file, the decision logic, the batch runner, the scenarios, the report), the policy numbers in [`src/shared/criteria.ts`](../../src/shared/criteria.ts) (`PERF_POLICY`) and the two commands [`perf/run.ts`](../../perf/run.ts) (`npm run perf`, `npm run perf:baseline`) and [`perf/gate.ts`](../../perf/gate.ts) (`npm run perf:gate`). The policy it implements is ADR-004 in [DESIGN_DECISIONS.md](../DESIGN_DECISIONS.md) and [TEST_STRATEGY.md](../../TEST_STRATEGY.md) section 7.1; the metrics are defined in [METRICS.md](../METRICS.md).

**Where the numbers come from.** Phase 5 had two parts. Part 1 built the harness and measured nothing. Part 2, on 2026-11-04 (UTC), recorded the baselines of six profiles in two environments on one machine (an Apple-silicon laptop: macOS 27.2, 12 CPUs, 16 GiB, Node 22.11.0, Playwright 1.64.1, Chromium 156.0.8078.4 and WebKit 27.2 natively; Chromium, Firefox 157.0 and WebKit in the Playwright container limited to 4 CPUs), derived from them the thresholds that depend on variation, ran the gate against its own baselines (the A/A check: 35 passes on the six profiles, no false positive) and injected regressions on purpose (the sensitivity check). The figures quoted below come from those runs, and the runs are in the repository: the baselines in [`perf/baselines`](../../perf/baselines), the derivation, the A/A summaries and the sensitivity reports in [`docs/results/perf`](../results/perf). The thresholds that could not be derived are still `assumption`s in `PERF_POLICY`, with the measurements beside them: the frame rate, the dropped-frame ratio and the rebuffering metrics did not vary in any baseline run, so there was no variation to derive a number from. **Not measured:** a CI runner. The baselines of the GitHub-hosted environments (`gha-linux-x64`, `gha-macos-arm64`) are recorded next, their first A/A check is the evidence that these thresholds fit them, and the durations in TEST_STRATEGY.md section 6.3 are measured on the workstation, to be re-measured in CI.

## ADR-120: One browser process per batch, a fresh context per run, and a warm-up run that is recorded and discarded

**Context.** A performance number is only as good as the question "what exactly is repeated". Three things could be: the browser process, the browser context, and the page. They cost very different amounts and carry very different state from one run to the next.

**Decision.** A **batch** is one scenario on one profile: one browser process (`launchProfile`, [`browser.ts`](../../src/lab/measure/browser.ts)), launched once and closed at the end (also when a run fails), and `1 + N` runs, each in a **fresh context** (`browser.newContext`, with the device descriptor the specs use) and with a session of its own on the service, created before the run and deleted after it. The first run of the batch is a **warm-up**: it is executed exactly like the others, **recorded** (`warmup` in the baseline and in the report, with its rung history) and **left out** of every statistic. `PERF_POLICY.warmupRuns` is 1; the runner accepts 0 or 1.

A context is a clean member session: no HTTP cache, no storage, its own page and renderer state. That is what "a viewer opens the player" means, it costs milliseconds, and it keeps the runs independent. A browser **process** per run would put the launch of the browser into every number (or, if excluded, would still make every first frame pay for a cold process that no member's player pays for) and its variance would swamp what is measured. One context for all runs would carry the cache, the JIT and the connection pool from one run to the next, so the runs would stop being independent samples. The warm-up exists because the first run in a fresh process still pays for things the later ones do not (code and file caches, the first decode), and the baselines measured it. The discarded warm-up startup was **4.6 times the median of the ten measured runs on local Chromium** (169 ms against 37 ms), 3.2 times on local WebKit (258 against 80.5 ms), 2.3 times under the 4x throttle (253 against 111.5 ms), 2.0 times on Chromium in the container (79 against 39.7 ms), 1.3 times on Firefox (72 against 54 ms) and 2.0 times on WebKit (311 against 157 ms): a batch without the warm-up would have put an outlier of that size among ten runs every time ([threshold-derivation.md](../results/perf/threshold-derivation.md)). **One warm-up is not enough everywhere**: on WebKit in the container the first two measured runs after it were still slow (516 and 258 ms against 146 to 183 ms for the other eight), which is why that baseline's p90 and CV (56.7 %) are dominated by the start of the process and its startup is tracked and not gated (ADR-124). A longer warm-up for that one profile would cost two more runs per scenario; it was not taken because a runner-specific warm-up would make the batches of different profiles different things.

**Alternatives considered.** A browser process per run (cold numbers, the launch in every sample). No warm-up (the first run of every batch is an outlier by construction, and with ten runs one outlier moves the p90 by a tenth of its distance). Discarding the warm-up without recording it (a reader could not see whether it was a typical run). Several warm-ups (the runner would have to say how many; one is what the evidence will be checked against).

**Consequences.** Each batch costs one more run. Measured on the quiet machine (the sum of the run durations in the baselines, [perf/baselines](../../perf/baselines)): a run takes 0.15 s (PB-PERF-001), 7.3 s (PB-PERF-002), 18.2 s (PB-PERF-003) and 7.5 s (PB-PERF-004, under the throttle) on local Chromium, against the design estimates of 5, 12, 23 and 15 s, so one profile with its warm-ups is 282 s (Chromium, three scenarios) or 83 s (the throttled profile, one scenario) of runs: the job "chromium and chromium-cpu4x" of TEST_STRATEGY.md section 6.3 is about 365 s of runs plus the starts of the service and of four browsers (one per batch), under its 720 s budget (the figure of a GitHub runner is not measured here). A scenario that is not independent of the previous run (anything stateful in the service) would be hidden by this policy, which is why the service's sessions are isolated by construction (ADR-003).

**Defending it.** "I decided what is repeated before I decided how often. A fresh context is a new viewer, a fresh process is a new machine, and a number that includes the second is not about the player. I record the warm-up so that anyone can see what I threw away."

## ADR-121: The percentile is Hyndman-Fan type 7; a summary is the median, the p10 and p90, the range, the MAD and the CV

**Context.** Every baseline and every verdict is a statistic of ten numbers. "p90" has at least nine definitions, and with ten values they disagree visibly: a figure that cannot be reproduced with a tool the reader already has is not evidence.

**Decision.** `percentile(values, q)` ([`stats.ts`](../../src/lab/measure/stats.ts)) is **linear interpolation between order statistics, Hyndman and Fan type 7**: with the values sorted, `h = (n - 1) q` and the result is `x[floor h] + (h - floor h) (x[floor h + 1] - x[floor h])`. It is the default of R's `quantile`, NumPy's `percentile` and a spreadsheet's `PERCENTILE.INC`, so any figure can be checked there. It is tested on small vectors whose answers can be done by hand (the p90 of 1 to 10 is 9.1, of two values 10 and 20 it is 19) and, with a seeded generator, for invariance under permutation, under a constant shift and under positive scaling, for mirror symmetry (the p10 of the negated values is minus the p90) and for monotonicity in `q`. A summary is `n, median, p10, p90, min, max, mad, cv`: the MAD is the unscaled median absolute deviation, the CV the **sample** standard deviation over the mean, and `null` (never NaN) where it does not exist: fewer than two runs, or a mean of zero (a count that was zero every time has no relative variation, and such metrics are judged by budgets, ADR-123). The **tail** of a metric is the p90 where higher is worse and the **p10 where lower is worse** (the frame rate): the p90 of a frame rate is its best runs.

**Alternatives considered.** Nearest rank: for ten runs it returns the 9th smallest and ignores the largest completely. Type 7 moves a tenth of the way towards it and is continuous in `q`, which is what a threshold on a statistic of ten numbers needs. The mean and its standard deviation as the headline (the mean hides the tail, ADR-004). A bootstrap interval around the median (more machinery than ten runs can feed).

**Consequences.** With ten runs the p90 sits at `h = 8.1`: essentially the second slowest run, plus a tenth of the gap to the slowest. It is a coarse estimate of a tail, noisier than the median: the standard error of the batch statistic, simulated for the percentile definition of the lab and ten normally distributed runs, is **0.37 sigma for the median and 0.46 sigma for the p90** (the asymptotic formulas give 0.40 and 0.54 and do not hold for ten runs: [`derive.ts`](../../src/lab/measure/derive.ts) simulates the real statistic). The measured baselines did not need the tail's share to be wider than the median's (ADR-123); the tail's allowance is wider in absolute terms because it is a share of the larger p90. The CV of ten runs is itself uncertain (about a quarter of its own value, for normal data): a CV is a guide to which metrics can gate, not a precise noise measurement, and the threshold derivation adds a quarter to the noise it estimates for that reason.

**Defending it.** "I picked the definition that R, NumPy and Excel agree on, said so in the first lines of the file, and tested it against numbers I can do in my head. The p90 of ten runs is the second-worst run, and I treat it as that."

## ADR-122: The service runs as a child process of the harness

**Context.** The scenarios need the test data service (streams, faults, request log). It can run inside the harness process (`startServer`), be started by something else, or be started by the harness as a separate process.

**Decision.** `startService` ([`service.ts`](../../src/lab/measure/service.ts)) spawns `tools/serve.ts` as a **child process** on `PB_PORT`, polls `/health` until it answers (and fails with the child's own output when it exits first: a port in use, a stream that was never generated, or a missing player build), and stops it **by pid** (SIGTERM, then SIGKILL after a grace period; a handler on the harness's own exit kills it too, so that a crashed harness leaves nothing running). One service per command, one session per run.

The player's own numbers are taken in the page with `performance.now()`, so a busy harness does not add its delay to them directly. The reason is what the service does: it **paces response bodies with timers** (the token bucket of ADR-050 to ADR-054: a throttle of 600 kbps is only 600 kbps if its timers fire when they should), and the harness spends its event loop on Playwright's protocol traffic. If both shared a loop, a busy harness would delay the service's timers, and the delay would show up as a throttle that is not the one configured, in the one scenario (PB-PERF-003) whose condition is a throttle. As a separate process the service shares the machine with the harness, which it would anyway, and nothing else.

**Alternatives considered.** `startServer` in the harness process (the shared event loop above). A service started by the CI job and addressed by origin (the harness could not say which build of the service it measured, and could not fail fast when the stream hashes changed). A process manager.

**Consequences.** The child is started through `node --import tsx` (one process, so that the pid is the service), which costs a service start-up per command. A service that does not stop within the grace period is killed, and the unit tests prove it with a stand-in that ignores SIGTERM.

**Defending it.** "The service is the network. It belongs in another process for the same reason a CDN is not inside the browser."

## ADR-123: The thresholds are data, they come from measured variation, and a floor protects both statistics

**Context.** ADR-004 says the gate fails a metric whose median is worse than the baseline by more than a relative threshold and an absolute floor, or whose p90 is worse by more than a wider threshold, with budgets for the metrics whose baseline is zero, and that the thresholds are set from the run-to-run variation measured in each baseline. It does not say where the numbers live, nor what the first numbers are while nothing has been measured.

**Decision.** The numbers are **`PERF_POLICY` in `src/shared/criteria.ts`**, in the typed form of the other policies (value, unit, how it is measured, basis `fact`, `arithmetic`, `assumption` or `measured`), rendered into TEST_STRATEGY.md section 7.1 by `npm run docs:check -- --write` and checked for freshness. [`rules.ts`](../../src/lab/measure/rules.ts) reads them into eight **rules**, and a unit test changes every threshold in turn and checks that it moves exactly one rule (no dead number, no shared one). The decision code ([`decide.ts`](../../src/lab/measure/decide.ts)) knows no number.

There are two kinds of rule. A **relative** rule (startup, frame rate) fails a statistic that is worse than the baseline's by **more than** `max(share x baseline value, floor)`: the median with the median share, the tail with a wider share, and **one floor for both** (ADR-004 states the floor for the median; it is applied to the tail too, because a 10 ms tail moving by 9 ms is as little a regression as a 10 ms median doing it). Exactly at the limit passes, and the comparison tolerates the last bits of a floating-point product (a limit of 0.1 + 0.2 is not exceeded by 0.30000000000000004). Only the worse direction counts: a faster startup or a higher frame rate never fails. A **budget** rule (rebuffer count, duration and ratio; dropped-frame ratio) fails a statistic that is above the baseline's by more than an **absolute** amount, because a share of a baseline that is usually zero is zero and every run would fail. The budgets are increases over the baseline, not levels: the level ("at most one rebuffer") is what the specs check (PB-ABR-002), and a level that ignored the environment would break the rule that baselines belong to one.

The relative numbers are **derived from the baselines** ([`derive.ts`](../../src/lab/measure/derive.ts), `npx tsx perf/derive.ts`, artifact [threshold-derivation.md](../results/perf/threshold-derivation.md)). Between a baseline and a later batch of the same code the median differs by noise alone, with a standard deviation of `sqrt(2) x SE` (SE: the standard error of a ten-run statistic), and the threshold has to cover three of them. SE is estimated twice from the ten raw values of the baseline and the larger is used: **parametric** (the sample standard deviation times the standard error of the statistic for ten normally distributed runs, 0.37 for the median and 0.46 for the p90, simulated for the lab's percentile definition) and **bootstrap** (4,000 resamples, fixed seed). A spread estimated from ten runs is itself uncertain by about a quarter (`1 / sqrt(2 x 9) = 24 %`), so the policy covers **1.25 times** that noise, rounded up to the next 5 %. The pairs that gate for startup had these noises as a share of the baseline median (p90 in brackets): local Chromium 6.4 % (9.3 %), local WebKit 14.2 % (12.3 %) and Chromium in the Playwright container 23.2 % (22.6 %), the noisiest; 1.25 x 23.2 % is 29 %, so **30 % for both statistics**. The floor is 1.25 times the noise of the quietest pair (3.6 ms, local Chromium), rounded up: **5 ms**, which binds only on a baseline under 17 ms. Low-end startup has the same shares (its one measured baseline needs only 15 %, but one stability limit governs both rules, ADR-124) and a floor of 20 ms (1.25 x 13.4 ms). The margins of the policy above the noise of each pair are in the last table of the artifact: 4.7 times on local Chromium, 2.1 times on local WebKit, 1.3 times on Chromium in the container, 2.9 times under the throttle.

**What could not be derived.** The frame rate, the dropped-frame ratio and the rebuffering metrics were **exactly the same in every baseline run**: 30 fps (once 151 decoded frames of 150 on Firefox), no dropped frame and no rebuffer in 50 runs of each, 10 under the throttle. There is no variation to derive a share from, so their numbers stay `assumption`s (product decisions: what a viewer would notice), with that measurement in their basis, and the checks below (A/A, sensitivity) say whether they are too tight or blind. The p90 share is **not wider** than the median share here (ADR-004 expected a wider one): the measured noise of the p90 was no larger as a share of its own, larger, value; its allowance is wider in absolute terms.

**Alternatives considered.** One global number ("fail above +20 %": it is wrong in both directions at once: a 5 ms change in a 25 ms metric fails and a 40 % change in a noisy one passes). Thresholds recomputed from each baseline's own CV on every run (it would let a noisy baseline buy itself a wide threshold silently; ADR-124 makes the noise visible instead). A significance test (a Mann-Whitney U against the baseline's runs needs far more than ten runs per side to have any power at the sizes that matter, and gives a p-value where a build needs a reason a developer can act on: "median 100 ms to 300 ms, 20 ms allowed"). Per-profile thresholds (each profile would gate at its own noise: sharper for the quiet ones; the policy would multiply by the number of profiles and every new environment would need its own derivation: the shared numbers cover the noisiest profile that gates, and the quiet ones simply have more margin).

**Consequences.** The rule is explainable in one line per metric and bisectable: the report prints the baseline, the current value, the change and the allowance side by side. The cost of one shared set is sensitivity on the quiet profiles: on local Chromium (37 ms) a startup regression gates only above about 11 ms (30 %), though its noise is 2 to 4 ms. The thresholds are valid for the machines that were measured (an Apple-silicon laptop, native and in the Docker VM with 4 CPUs): a CI runner has its own baseline, and its first A/A check is the evidence that these numbers fit it.

**Defending it.** "A threshold is a claim about noise, so it carries its basis: what it was derived from, on which machines, and how much room it leaves above the noise of each profile. Where there was no noise to measure (the frame rate never moved) I say that instead of dressing a guess as a measurement."

## ADR-124: A metric whose baseline is noisier than the stability limit is tracked, not gated

**Context.** TEST_STRATEGY.md section 7.1 says an engine and metric pair gates only once its baseline is stable enough to tell a regression from noise, and that the README says which pairs gate.

**Decision.** A metric judged by a relative rule gates only while its baseline's coefficient of variation is at or below `PERF_POLICY.maxBaselineCv` (**15 %**) and the baseline has at least two runs. Otherwise the comparison is still computed and printed, its verdict is **`tracked`**, it can neither fail the build nor start a re-measure, and its reason says which limit it exceeded (and whether it would have failed). `perf:baseline` prints, when it records a baseline, which metrics gate and which are tracked and why, so that nobody finds out later that a metric has been silently skipped; the gate prints the same reasons on every build. A budget rule has no such guard: its baseline is usually zero, and its budget is absolute. A CV that is undefined because the mean is zero does not stop a metric from gating.

**The limit is measured, not chosen.** The thresholds of ADR-123 were derived from the pairs that gate, the noisiest of which is startup on Chromium in the Playwright container (CV 13.3 %); the limit is that CV rounded up to the next 5 %. The startup CVs of the six recorded profiles: 4.0 % local Chromium, 6.8 % local WebKit, 6.4 % under the 4x throttle, **13.3 %** Chromium in the container, **15.3 %** Firefox in the container and **56.7 %** WebKit in the container. So **two pairs are tracked, not gated**: Firefox startup in the container is just above the limit (its noise as a share of the median is 37.5 %, which the 30 % thresholds do not cover), and WebKit startup in the container is dominated by the start of its process (the first two measured runs took 516 and 258 ms, the other eight 146 to 183 ms: its robust CV, from the MAD, is 8.1 %, the CV that the outliers inflate is what the limit sees, and what the p90 of ten runs sees too). Their frame rate and rebuffering metrics gate.

**One limit and one set of shares for every rule.** The throttled profile's own baseline is quieter than the limit (CV 6.4 %) and needs only 15 % (10.2 % x 1.25, [threshold-derivation.md](../results/perf/threshold-derivation.md)), so a limit and shares of their own for low-end startup (about 10 % and 15 %) would have made that gate twice as sharp on this workstation, and it was possible. It was **not taken, for the sake of one policy**. The baselines of the GitHub-hosted runners (`gha-linux-x64`, `gha-macos-arm64`) are recorded next and are expected to be noisier than this workstation; a metric whose own baseline CV is above the limit is tracked, not gated, so noise is already handled per environment by the one rule, and a rule of its own per profile would add a second place for the same decision, a second set of numbers to defend, and a low-end gate sharper than the evidence of any environment but this one. The price is stated: on this workstation a low-end startup regression gates only above 33 ms (30 % of 111.5 ms) where 17 ms would have been possible (the 8x-throttle run of the sensitivity check, +125 %, is far above either). If the runner baselines show that low-end startup is as quiet there, the shares can be lowered for every profile at once, with one derivation.

**Alternatives considered.** Gating everything (a noisy baseline would fail clean builds, and the team would learn to ignore red). Widening the threshold automatically (above). A stability limit and shares for each rule or profile (above: sharper where the evidence is, a second set of numbers to defend, and every new environment would need its own derivation). Refusing to record a noisy baseline (the second best answer is a quieter machine; but the baseline is evidence of what the machine is like, and a tracked metric is what the environment honestly supports).

**Consequences.** On a noisy runner some metrics are reported and not enforced, which is the truth about that runner: the measured baselines show it (above). A baseline that happens to contain an outlier makes its metric untrackable for the life of the file; the answer is to record it again on a quieter machine, and say so, not to loosen the limit.

**Defending it.** "A gate that cannot tell a regression from noise is a random number generator with authority. I would rather say 'this one is not enforced here, and why'."

## ADR-125: A regression must reproduce: the gate measures a fresh batch, judges it alone, and fails only if it fails again

**Context.** On a shared machine, one batch of ten runs can be unlucky. A gate that fails the build on the first violation blocks merges for noise; a gate that never fails misses regressions.

**Decision.** When a scenario's first batch fails a **gated** metric (and could be judged at all), the gate measures a **fresh batch**: a new browser process, new contexts, new sessions, its own warm-up. The two are **settled** by [`settle`](../../src/lab/measure/decide.ts): a metric that failed in both is a **regression** (exit code 1); one that failed in the first and passed in the second is **not reproduced** (the build passes, the report shows both batches and says so); a metric that only failed in the fresh batch is not flagged, because the question the fresh batch answers is whether the first failure repeats. The fresh batch is **judged on its own, not pooled** with the first (the pooled median of two batches could fail where neither does, and could hide a failure that repeats), and a failure of another metric does not confirm the first. Only a failing scenario pays for it, and only that scenario is measured again. There is no third batch.

If a clean build fails a metric in one batch with probability `p`, it fails it twice with about `p^2` when the batches are independent, which is what a fresh browser and fresh runs aim at. The independence is limited: a noisy neighbour that stays for both batches is a correlated cause that no re-measure removes, the baseline's own error is shared by both batches, and the report's load average of every batch is there to show the first.

**Measured on a clean build (the A/A check).** The gate was run against its own baseline, nothing changed, 10 times on local Chromium and 5 times on each of the five other profiles (35 passes; summaries in [`docs/results/perf`](../results/perf), `<environment>/<profile>-aa.md`): **0 false positives (exit code 1) and 0 first-batch alarms**. The worst pass of a gated startup metric used 21 % of its median allowance on local Chromium (+2.3 ms of 11.1 ms), 45 % on Chromium in the container (+5.4 ms of 11.9 ms, the noisiest gating profile), 5 % of the p90 allowance on the throttled profile and none on local WebKit; the two container profiles whose startup is tracked stayed inside the allowance they would have had. Frame rate, dropped frames and (local Chromium, five passes) rebuffering did not move at all. Three passes ended with **exit code 2**, which is not a false positive but was a finding: a race in PB-PERF-002 on Firefox, fixed (ADR-127). Zero events in ten passes bounds the false-positive rate per pass only to about 26 % (95 %, the rule of three), so the margin is the stronger statement: the spread of the batch medians across passes was at or below what the derivation had estimated from one baseline batch on five of the six profiles and **about twice** that on local Chromium (1.2 ms against 0.56 ms), where the allowance (11.1 ms) is still nine times the spread.

**Measured on injected regressions (the sensitivity check).** On local Chromium, PB-PERF-001 (baseline 37.05 ms; 11.1 ms allowed on the median, 11.7 ms on the p90), 33 gate runs ([`sensitivity/summary.md`](../results/perf/sensitivity/summary.md)): +150 ms of latency on every manifest and init request gave 337.9 ms (+812 %) in the first batch and 337.0 ms in the fresh one, exit code 1, with the reason in words. A sweep found the edge: an injected 9 ms per request and more moves the median by 14 to 18 ms and was reproduced **7 times of 7** (and 20, 40, 80 and 150 ms moved it by 35, 75, 151 and 301 ms); 6 ms and less changed it by 0 to 2.4 ms and passed. At 7 and 8 ms only some of the runs jump by about 15 ms, the p90 sees them, and the first batch failed 5 times of 6 but the fresh batch confirmed it only 3 times: **the confirmation buys stability with sensitivity**, and a regression right at the edge fails some builds and not others. A CPU throttle on the page of 2x, 3x and 4x (+48 %, +113 %, +177 %) was reproduced and 1.25x and 1.5x (+14 %, +27 %) passed under the 30 % share. A **one-off outlier** (+150 ms in the first batch only, `--inject-on first`) was **not reproduced** in 3 of 3 runs: the report says "the first measurement is discarded and the build passes", exit code 0. The low-end profile under an 8x throttle (PB-PERF-004) rose from 111.5 to 250.5 ms (+125 %) and was reproduced; a video segment held back for 8 s (PB-PERF-003, 5 runs a batch) gave a median of 3 rebuffers and 7,990 ms of stall against zero and failed all three rebuffering metrics in both batches. **Not shown:** the frame-rate and dropped-frame rules never fired, because no injection that could be run moved those metrics (an 8x throttle dropped no frame at 720p), and only Chromium was injected.

**Alternatives considered.** Fail on the first violation (a flaky gate). Retry until it passes (it measures the luck of the retry count). Pool both batches into twenty runs (more power, but the verdict is then about a mixture, and the question "does it reproduce" is gone). Majority of three batches (a third of the cost on every failing build).

**Consequences.** A real regression just above the threshold fails the first batch with probability less than one and both with a smaller one: **the confirmation buys stability with sensitivity**, and the sensitivity check above measured how much (a regression whose effect was 1.3 times the allowance or more was reproduced every time; one at the edge, about half of the time). A failing build costs a second batch of one scenario (the design allowance is `perfRemeasureSec`, 360 s; the slowest scenario measured 200 s on the workstation). The report keeps both batches' runs, so the one that failed can be read.

**Defending it.** "A result that does not reproduce is not a result. I measure whether it repeats before I tell a developer their change is slower, and I show both measurements."

## ADR-126: Baselines belong to an environment and a profile, are plain validated JSON, and are never compared across environments

**Context.** A number measured on a laptop says nothing about a CI runner, and a baseline that a hand edit or a copy can change silently is not evidence.

**Decision.** One file per environment and profile, **`perf/baselines/<envId>/<profile>.json`** (`detectEnvId()`: `local-darwin-arm64`, `docker-linux-arm64`, `gha-linux-x64`...), committed. It holds a schema version, the environment, the date, the commit, the Node, Playwright, browser and ffmpeg versions, the host's CPUs and memory, the **content hash of every stream it played**, and for every scenario the stream, protocol, condition, pinned rung, the rung the runs started on, the load average before and after, the warm-up, **every run** with its rung history, and per metric the summary and the raw per-run values. [`loadBaseline`](../../src/lab/measure/baseline.ts) validates all of it, including that **every summary follows from the raw values beside it** and that the values agree with the runs they came from, so a hand-edited number cannot pass for a measurement. It refuses a file that is missing (with the exact command that records it, written for the environment: the Docker form where the environment is a container), one of another schema version, and one **recorded for another environment or profile, even when it sits in this environment's directory**. A baseline cannot be built from runs that mixed start rungs where the start rung decides the number, from a gated metric that a run did not produce, or from a batch in which faults were injected on purpose.

Before any browser starts, the gate compares the **stream content hashes** of the running service with the baseline's: different media (a new ffmpeg build changes every hash, ADR-045) make every number incomparable, so it is a problem (exit code 2), not a regression, and says that every baseline of the environment has to be recorded again together. A different browser build, Playwright version or CPU count is only a **warning**: it may be the very reason a number moved, and it is not the code's doing.

A baseline also records **how the profile was measured** (`machine`, optional, so that older files still validate): started on the host or through `docker:pw` and with which CPU limit (`dockerCpus`); what [`perf/quiet.ts`](../../perf/quiet.ts) did before the command started (the load limit, the host's 1-minute load average when it started, how long it waited: a measurement is only as quiet as its machine, so the recording command is started through it with `--max-load 3`); and the 1-minute load average when the first batch of the profile started and when the last one ended (inside a container that is the Docker VM's, which is why the wrapper records the host's). The six baselines of this lab were started at a host load of 2.1 to 3.0 (two of them after waits of 10 and 15 s, one of 40 s).

**Alternatives considered.** A global baseline (meaningless across machines). Baselines in an artifact store (not reviewable in a pull request; a baseline change is a decision that deserves a diff). Trusting the file (the loader is the only thing between a typo and a wrong verdict).

**Consequences.** A new machine class needs its baselines recorded before its gate can run (a missing baseline fails the gate with the command, except with `--allow-missing-baseline` for local use, which measures and judges nothing). A baseline file is tens of kilobytes (ten runs of every scenario with their histories), which is what makes it reviewable.

**Defending it.** "Every number in the file can be recomputed from the numbers next to it, and the loader does."

## ADR-127: The start rung is part of the measurement, and the frame windows are pinned before they play

**Context.** The first rung depends on the engine, not on the code under test: configuration A starts on 720p in Chromium (its reported downlink is high) and on 360p in the other engines, which have no downlink (ADR-064). A startup number, a rebuffer count and a dropped-frame ratio all depend on which rung is playing.

**Decision.** Every run records the **rung it started on** and the whole rung history. The scenarios whose number depends on the start (`startRungMatters`: startup, rebuffering, low-end) are compared only with a baseline that started on the **same rung**, and only from batches whose runs all started on one rung: otherwise the gate says so and exits 2 instead of comparing two populations. The frame window of **PB-PERF-002 is pinned before playback starts**: the page loads without autoplay and with ABR off, `selectVariantByHeight(720)` flushes what was buffered (nothing has played), and then it plays, so that every frame of the five-second window after two seconds of warm-up is 720p. Pinning after the first frame would leave seconds of the first rung in the buffer and the window would count them as 720p. **The scenario waits for the load that the page starts by itself and never requests another** (`qa.waitFor('loaded')`): the page loads the manifest it is given whether or not it autoplays (autoplay only decides whether it then plays). The first version asked for a second `load()` after `open`, which races the page's own: if that one is still running, Shaka interrupts it (`LOAD_INTERRUPTED`, severity critical) and no first frame follows. It did not show in any of the 55 baseline runs; the A/A check found it on Firefox in the container, where 3 of the 5 first passes ended with exit code 2 (a failed run in 3 of 40, about one in thirteen), and the same race made the 20x-throttle probe of the sensitivity check fail. After the change, 5 of 5 Firefox passes (55 runs) and 2 of 2 local Chromium passes ended with exit code 0 ([`docs/results/perf/after-fix`](../results/perf/after-fix)), and a scripted-player unit test pins that the scenario waits for the page's load and never calls `load` itself. The baselines of PB-PERF-002 were recorded with the earlier flow and were **not** recorded again: its metrics are taken after the play and the two seconds of warm-up, and the fixed flow reproduced them (30 fps, no dropped frame). **PB-PERF-004** measures the startup of a plain autoplay load and then pins; it can only do that safely when the player already started on the pinned rung (a pin on the active rung changes nothing and flushes nothing), so a run that started elsewhere is **refused with that explanation** instead of measured. After the window the scenario checks that the active rung is the pinned one and that ABR did not move it, and fails the run otherwise. The catalog row of PB-PERF-004 does not say "pinned"; pinning is this harness's reading, so that its dropped-frame ratio is about one rung, and it is reported as such.

**Alternatives considered.** Normalising by rung (not possible: the cost of a rung is the thing being measured). Letting ABR choose during the window (rung changes inside the window make the frame rate a mixture). Two page loads in PB-PERF-004, one for startup and one pinned (about six more seconds a run under the throttle by the design estimate, which the budget of section 6.3 does not have).

**Consequences.** A baseline of PB-PERF-004 can only be recorded where the player starts on 720p (Chromium on a link the browser reports as fast), which ADR-064 measured on macOS and in the container (one session each) and which every run of the harness checks again.

**Defending it.** "A startup number without its first rung is a number about the browser's network estimator. I record the rung and refuse to compare across it."

## ADR-128: Exit codes separate a regression from a problem, and a run that fails is never dropped

**Context.** A gate that fails for a reason that is not the code teaches people to ignore it, and a gate that hides a harness failure as a pass is worse.

**Decision.** **0** passes (a failure that did not reproduce passes and is reported); **1** a regression that reproduced; **2** the measurement could not be trusted: no baseline here, a baseline that does not validate or belongs elsewhere, a changed stream, a start rung that differs, a documented gap (the engine cannot play the stream here: the harness decides it from the committed probe exactly as the specs do, [`gaps.ts`](../../src/lab/gaps.ts), and says so instead of skipping, because a skipped gate is a hole), a browser that did not start, a run that failed, a gated metric that a run did not produce. When there are several verdicts (several profiles, several scenarios), a reproduced regression wins over a problem elsewhere (it is a finding whatever else went wrong), and a problem wins over a pass (an incomplete verdict fails the build without blaming the code). **A run that fails ends its batch** with the player's last events and the browser's console in the message; the harness never drops it and carries on, because dropping the failed runs would bias the statistics towards the runs that went well, and never retries it silently. A run also fails as soon as the player reports a critical error, instead of waiting out its safety net: the first proof run of the gate with a stall injected for longer than Shaka tolerates (a request that sends nothing for 5 s is aborted and retried) waited the full 90 s of the rebuffering scenario to report the player's critical TIMEOUT, which is why the wait for the media clock now races the first critical error (a scripted-player unit test pins it).

**Alternatives considered.** One failure code (a developer cannot tell "I made it slower" from "the runner is broken"). Skipping a profile on a documented gap (what the specs do; a silent hole in a gate that exists to block). Retrying a failed run (it measures the retry policy).

**Consequences.** The CI job reads the exit code, and the summary says why in words. A scenario that hits an environment problem still lets the others run, so one report shows everything that is wrong.

**Defending it.** "Red has to mean one thing. Code 1 is 'your change made it slower, twice'. Code 2 is 'I could not tell', and it says why."

## ADR-129: What a lab number means, and what it does not

**Context.** These numbers will be quoted: on the repository's page, in a pull request, in an interview. A number without its scope is a claim the harness cannot back.

**Decision.** A figure of this harness is a **laboratory measurement of the player page, on one machine class, against localhost, with software decoding and synthetic content**, taken in a fresh context of a warm browser (so a startup here is the time from `load()` to the first presented frame of a player that is already built, not the page's load nor the library's download, METRICS.md), at the rung the report names. It compares **builds and configurations under identical conditions on the same environment**. It is **not** production quality of experience, it is **not comparable between environments** (and the harness refuses to), and it is not a statement about any device: the 4x CPU throttle slows main-thread work (page boot, parsing, the lab's own per-frame work); whether decoder threads slow down was not measured ([ADR-076](e2e.md)), and the network is not part of it, so `chromium-cpu4x` is a stand-in for a weak device, not a device, and Firefox and WebKit have no such stand-in. Frame rate is counted over media time (a stall does not read as low fps); the dropped-frame counter is the engine's own (`getVideoPlaybackQuality`), so it is compared only within an engine. The gate detects a **change relative to the committed baseline** that exceeds the measured noise of its environment and **reproduces**; it does not say that the baseline is good, and a slow drift smaller than the thresholds passes it by (each pass moves nothing: the baseline is only replaced by a deliberate recording).

What the lab can claim, and what is left to the sentences in the README, is therefore: it tracks startup time, rebuffering and frame rate on every build against a per-environment baseline, it fails a merge on a regression that reproduces, it reports what the machine was doing while it measured, and it says which of its metrics are enforced and which only tracked. What it cannot claim is a number for members.

**The machines of the committed baselines.** `local-darwin-arm64`: an Apple-silicon laptop (macOS 27.2, 12 CPUs, 16 GiB), Node 22.11.0, Chromium 156.0.8078.4 and WebKit 27.2 as Playwright 1.64.1 ships them, run natively; `docker-linux-arm64`: the same laptop's Docker VM (12 CPUs visible, the container limited to **4**, 7.7 GiB, Linux 6.5.11-linuxkit, Node 24.22.1) with Chromium, Firefox 157.0 and WebKit 27.2 of the Playwright image. Recorded on 2026-11-04 with the host's 1-minute load average at 2.1 to 3.0 before each profile (the harness itself adds about two to three to it while it measures: a Chromium and the service). It was a developer's machine with its desktop applications open and no other benchmark job; the load limit is a guard, not a laboratory. A baseline from a CI runner is a different environment with its own file, and **these thresholds have not been checked on one**: the first A/A check on a runner is the evidence that they fit it.

**Alternatives considered.** Quoting the numbers without this paragraph (they would be read as production figures). Hiding the throttle's limits (a "low-end TV" claim the CDP command cannot support).

**Consequences.** Every figure in this repository is reported with the environment, the date, the commit and the load average of every batch, as this harness records them (the baselines and the reports hold them).

**Defending it.** "I can tell you what the number is, where it was taken, what it is good for and what it is not. That is the part of a performance claim that interviewers should test."
