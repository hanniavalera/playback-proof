# Flake tracking decisions (ADR-130 to ADR-139)

Architecture decision records for the mechanism that enforces the flake policy of [TEST_STRATEGY.md](../../TEST_STRATEGY.md) section 7.2 (ADR-022 in [strategy.md](strategy.md)): the reporter [`flake/reporter.ts`](../../flake/reporter.ts), the history ([`flake/history.ts`](../../flake/history.ts), [`flake/store.ts`](../../flake/store.ts)), the statistics ([`flake/stats.ts`](../../flake/stats.ts)), the quarantine list ([`flake/quarantine.ts`](../../flake/quarantine.ts), [`flake/quarantine.json`](../../flake/quarantine.json)), the gate ([`flake/gate.ts`](../../flake/gate.ts)), the report ([`flake/report.ts`](../../flake/report.ts)), the quarantine-aware merge wrapper ([`tools/gate-merge.ts`](../../tools/gate-merge.ts)), the collector ([`tools/flake-collect.ts`](../../tools/flake-collect.ts)) and the error signature shared with failure triage ([`src/lab/signature.ts`](../../src/lab/signature.ts)). How to use it is [FLAKE.md](../FLAKE.md). They are written so each one can be defended in a review: what the situation was, what was chosen, what was rejected, what it costs, and how I would argue for it.

The policy itself (a window of 30, 20 runs before a verdict, 5 % per test, 2 % per engine job, quarantine for at most 14 days and 7 for a merge-tier test) was decided in Phase 1 and lives in [`src/shared/criteria.ts`](../../src/shared/criteria.ts); nothing below copies a number from it. **What these records do not have is flake data**: the mechanism was built and tested on fixtures and on one real Playwright run of a scratch project (Playwright 1.64.1, Node 22.11.0, macOS arm64, one worker, two projects, 17 test records, about 9 s, 2026-11-03). No number about the flakiness of the lab's own suite exists until `tools/flake-collect.ts` has gathered some (Phase 9), and the policy numbers stay initial policy until then.

## ADR-130: A reporter writes one record per Playwright invocation, with every attempt of every test

**Context.** Retries hide flakes: with `retries: 1` a test that fails and then passes is green in every report a person reads. Playwright's own JSON reporter holds the attempts, but it is built for a viewer: it is a tree of suites, it carries attachments and stdout, and the failures that matter for flake tracking (an intermittent one) are the ones whose first attempt is easiest to lose. Whatever tracks flakes needs, per test and per attempt, three things and no more: what happened (status and duration), why (a name for the cause, to count like with like) and under which conditions (commit, environment, engine, tier, retries, quarantine).

**Decision.** A custom reporter, listed next to the others in [`playwright.config.ts`](../../playwright.config.ts), writes `reports/flake/run.json` when the run ends: a `FlakeRun` ([`flake/run.ts`](../../flake/run.ts)) with the run id (the CI run, or one generated), a unique invocation id, the start date, the commit, the environment id (`detectEnvId()`), the Playwright version, the status and duration of the run, the shard if there is one, and per test the catalog id (parsed from the start of the title: `PB-VOD-007`; the title with its `describe` blocks when there is none), the engine (the Playwright project), the file, the tags, the tier from the tags, the outcome, whether the quarantine list said it was quarantined, the retries the configuration gave it, the skip reason, whether it ran in an experimental engine (the `experimental-engine` annotation of the shared fixture), and every attempt with its status, duration and, for a failed one, the error signature (ADR-132). The environment variables that decide where it writes and what it calls the run are listed in the head of the file; `PB_FLAKE_RUN_FILE` lets a wrapper keep two invocations apart (ADR-138). The reporter is written to be harmless: it is off in `--list` and merge modes, it writes through a neighbour file and a rename, and a failure to write is one line on stderr and not a failed run, because the gate that reads the file reports a missing one (exit 2).

**Alternatives considered.** Parsing `reports/playwright.json` after the run (it has the attempts, but also the whole tree and every attachment path, and the record would depend on a format that Playwright may change between versions; the reporter API is the supported seam). A fixture that writes the outcome from `testInfo` (it cannot see the status of its own test, and a worker that crashes takes the record with it). JUnit XML (no attempts, no tags). Recording in the CI job from the console output (not data).

**Consequences.** The record is a contract: `parseRun` refuses a version it does not know, and keeps the fields it does not know when it rewrites a line, so that an older tool does not erase what a newer one wrote. One more reporter runs in every browser job (a few milliseconds: it walks the suite once at the end). It is verified against the real runner once: a scratch project with a pass, a flake, a failure, a skip with a reason, a timeout, a test under `describe`, an expected failure and a quarantined test, in two engines, run through `tools/flake-collect.ts` ([`tests/unit/flake/reporter.test.ts`](../../tests/unit/flake/reporter.test.ts)); the outcome of each of its 17 records agrees with Playwright's own `test.outcome()`.

**Defending it.** "The one question this data answers is 'did a retry rescue this test', and only the reporter sees every attempt as it happens. I record that, with the cause and the conditions, in a file I own, and I keep Playwright's report for what it is good at: showing a person the failure."

## ADR-131: An outcome is Playwright's own, a flake needs a retry that could have shown it, and some tests are not executions

**Context.** METRICS.md defines the flake rate as "runs in which the test failed and then passed on a retry, divided by the runs in which it executed". Three cases need a decision. A run with no retry (`retries: 0`, which is the repository's local default) cannot show a flake: a test that flakes shows as a failure there, so a history that mixes such runs in understates the rate with a denominator that cannot have counted what it was meant to count. A skipped test did not execute. A run that was stopped (`--max-failures`, the global timeout, Ctrl-C) leaves tests that never finished, and says nothing about whether their retry would have passed.

**Decision.** The outcome of a test is Playwright's `test.outcome()` (all attempts as expected: `passed`; mixed: `flaky`; none as expected: `failed`; all skipped: `skipped`; an expected failure under `test.fail()` that fails is `passed`) with two additions: a test that never passed and whose last attempt ran into its timeout is `timedOut`, and a test the run was stopped on with no attempt that passed is `interrupted`. Executions are `passed`, `flaky`, `failed` and `timedOut`. An execution whose configuration gave the test no retry is **not an observation of flakiness**: it is left out of every rate and counted on its own (`unobserved`), and the report says how many there are. The collector always asks for one retry (ADR-138). A failure after every attempt is counted as a failure, not as a flake, and is reported but not judged by the flake gate: it already failed the browser job.

**Alternatives considered.** Counting every execution in the denominator (simple, and wrong in exactly the case a person is most likely to hit: gathering data locally with the default configuration and reading a flake rate of zero). Counting a `failed` outcome as half a flake (a test that fails twice in a row is not a test that a retry rescued; it is red). Treating a stopped run's tests as failures (the stop is the run's, not the test's).

**Consequences.** A history of local runs without retries is nearly useless for flake rates, and the tools say so instead of showing zero. The rate is a **lower bound** on how unreliable a test is: it sees only what one retry hides, so a test that fails twice by bad luck is a failure and never a flake. The reporter's outcome logic is table-tested against every combination of attempt statuses, and agrees with Playwright's own on the real run.

**Defending it.** "A rate needs a denominator that could have contained the numerator. A run that cannot retry cannot show a retried pass, so it does not belong in the denominator, and I show the count of those runs rather than hide it."

## ADR-132: The error signature is the first line of the message, normalised, in one function that triage reuses

**Context.** To say that three flaky outcomes of one test have the same cause (or that one flaky outcome today is the failure that triage clustered last week), the failures need a name that does not change with the session id, the port, the timestamp or the number of milliseconds in the message. Phase 8's triage needs the same name.

**Decision.** `errorSignature(message)` in [`src/lab/signature.ts`](../../src/lab/signature.ts): strip the colour codes, take the first line that says something, and replace what changes from run to run by a placeholder: urls (`<url>`), absolute paths (the directories go, the file name stays), date-times and clock times (`<ts>`), UUIDs and hex ids of eight digits or more with a letter in them (`<id>`), IPv4 addresses with their port (`<addr>`), hex literals, and numbers (`<n>`) that do not belong to a word (`vp09`, `h264`, `mp4a.40.2` keep theirs) or to a catalog id (`PB-VOD-001` keeps its number). A line longer than 200 characters is cut. Applying it to a signature changes nothing. It reads the first line only, because below it a Playwright message holds values (`Expected: >= 3`, `Received: 2.4`) and timelines, which are what vary.

**Alternatives considered.** A hash of the whole message (two causes that differ by a number never meet). The stack (the top frame is the assertion helper for every failure of a kind). Clustering by edit distance (nondeterministic across versions, and the point is a name a person can read in a report). Keeping the numbers that name a cause, such as an HTTP status (which numbers do is a judgment per message; the first line's words carry the cause far more often than its digits).

**Consequences.** Two causes whose first lines read alike are one signature. Numbers are normalised everywhere they stand alone, an HTTP status included: a 404 and a 503 in the same words are one signature, which is right for a cluster of "the origin refused the segment" and wrong if the status is the point. `Error: media time reached` on two different values is one cause, too. The table-driven tests of [`tests/unit/flake/signature.test.ts`](../../tests/unit/flake/signature.test.ts) pin pairs that must cluster (nine shapes of the same failure on two runs) and pairs that must not, and the real run's records carry signatures such as `Error: the first attempt always fails (worker <n>, ts <n>)` and `Test timeout of <n>ms exceeded.`.

**Defending it.** "A signature is a name, not a hash: it has to be something I can read in a table and say 'that is the timeout one'. It is blunt on purpose, it is one function, and its limits are written down."

## ADR-133: The history is JSON lines, one run per line, keys in a fixed order, the last 200 runs of each environment

**Context.** The history is appended to by every build, read by every gate, diffed in a branch and, at worst, read by a person with `git show`. It has to survive concurrent writers, stay small, and be readable with no tool.

**Decision.** One file per environment (`<envId>.jsonl`; histories are never compared across environments, ADR-004), one run per line, serialised with the keys of every object sorted ([`flake/history.ts`](../../flake/history.ts), `canonicalJson`), so that recording a build adds one line and a diff shows the runs added and, when the history is full, the runs that fell off its start. It holds the last 200 runs of an environment (almost seven windows of 30). A run is identified by its invocation id: recording the same run file twice does not count it twice, and what was recorded is never rewritten. Runs are kept in the order they **started**, so that a job that finished late takes its place. Reading is strict: a line that is not a valid run is an error that names the file and the line (and says when it is a merge conflict marker), never a line skipped. Measured on fixtures: a run of fifteen passing tests is about 4 KB as a line, so a full history is under a megabyte (the fixtures have short titles; real ones are longer); the one real run of this record, with failures and signatures, is 5.3 KB for 17 tests.

**Alternatives considered.** One JSON array (every append rewrites the file, every diff is the whole file, a merge conflict is unrecoverable). CSV (the attempts of a test are a list). SQLite (a binary in git; no diff; and a database for two thousand rows). One file per run (a directory of thousands of files, and the trim is a delete per file).

**Consequences.** Trimming is by count, not by age: a quiet environment keeps old runs, which the window of 30 ignores anyway. A file in an environment that is renamed (`PB_ENV_ID`) starts empty. The history cannot be edited by hand without it showing in the diff, and `parseRun` refuses what it does not understand.

**Defending it.** "The format is chosen for the diff and for the failure mode: a line per run means two writers can only conflict on the last line, a stable key order means nothing changes that did not change, and a reader that finds garbage stops and says where."

## ADR-134: In CI the history lives on an orphan git branch, and a push that loses a race is made again on the new tip

**Context.** A CI job leaves nothing behind but its artifacts, and the history has to outlive the job and be appended to by the next one, from any runner, with several jobs finishing at the same time (the engine jobs of one build) and without a service to operate.

**Decision.** A **git-branch store** ([`flake/store.ts`](../../flake/store.ts), `GitStore`): the orphan branch `ci-data` holds `history/<envId>.jsonl` and nothing of the code. `load()` fetches the branch (depth 1, into a private ref `refs/flake-store/ci-data`) and reads the file; a branch that does not exist is an empty history, and a remote that cannot be reached is an error, never an empty history. `append()` builds a commit with git's plumbing (a blob, a tree made in a private index file, a commit as the **CI identity it is given**) and pushes it without force. When the push is refused because another job pushed first (non-fast-forward, "fetch first", or the ref locked at that moment), it fetches again, applies the same append to the new tip and pushes again, up to a limit, with a short random wait so that writers do not retry in step; any other refusal (a hook, a permission) is an error at once and is not retried. It pushes **only when told to** (`--push`, a build of `main`), never on a pull request: a pull request's run is not what `main` did, and a fork's token could not push anyway. It touches no branch, no index and no `HEAD` of the checkout it runs in; it uses that checkout's remote and credentials (`actions/checkout` leaves them configured). A **file store** (`flake/history/<envId>.jsonl`, one writer at a time through a lock file that a dead writer cannot hold for ever) serves local use, the collector and Jenkins, where the workspace can live on a volume. Both implement one interface and one contract test.

**Alternatives considered.** A workflow artifact (immutable, per run, expires; reading the previous runs means listing and downloading them one by one with a token, and nothing can be appended). The Actions cache (immutable per key, evicted when unused for a week or when the repository is over its limit: a history that can vanish is not a history). A database or an object store (infrastructure to run, credentials to keep, an outage in the gate; and a reviewer who clones the repository could not read the data). A file committed to `main` (every build adds a commit to the code history, a protected `main` refuses the push, and the push races with merges). A wiki or `gh-pages` branch (an orphan branch of our own is the same idea with nobody else's tooling attached to it).

**Consequences.** The branch grows by a commit per recorded build (a compressed copy of the file each time): trimming bounds the file, not the history of the branch, and the tool never rewrites that history. The `main` job needs permission to push (`contents: write`), the pull request jobs do not. The race was tested with real git against a temporary bare repository in a scratch directory (never against the repository's own remote): two writers that both found no branch (the first pushes a root, the second is refused and builds on it, so there is one root and not two), a race forced between building the commit and pushing it on an existing branch (the loser fetches, applies its append on the winner's tip, and both runs are in the history, in a line of commits with no merge), a writer that loses every try (it gives up with an error and the others' work is untouched), four jobs pushing at once to a branch that does not exist yet (all four runs present exactly once), pull request mode (the branch does not move), no force flag or `+` refspec in any push it makes, and a hook that refuses a push for another reason (one try).

**Defending it.** "I wanted the history to be plain text I can read with `git show`, to survive the job, to take concurrent writers, and to need nothing I do not already have. A branch gives all four; its price is a commit per build, and the push is the one place I take care never to be clever: it retries on a lost race and never forces."

## ADR-135: A test is judged on its own window, the suite on the merge tier of the last builds, and quarantine takes a test out of the second and not the first

**Context.** The numbers are decided ([`FLAKE_POLICY`](../../src/shared/criteria.ts), with the binomial arithmetic): a window of 30, 20 runs to be judged, above 5 % per test, above 2 % per engine job. Applying them needs decisions the policy leaves open.

**Decision.** [`flake/stats.ts`](../../flake/stats.ts), pure functions of the recorded runs. **Per test and engine:** the last `windowRuns` executions that could have shown a flake (ADR-131); `flakeRate = flaky / executions`; `failureRate = failed / executions`; the verdict is `not-enough-data` below `minRunsToJudge`, `over-trigger` when the rate is **above** the trigger (one flaky outcome in the minimum 20 is exactly 5 % and is not above it; two in a full window is 6.7 % and is; the figures quoted in `criteria.ts` are asserted against the computation), `watch` for any flaky outcome below it, `ok` otherwise. **Per engine job:** retried-then-passed over all executions of the merge-tier tests over the last `windowRuns` builds (a build is a CI run in which the engine job ran merge-tier tests that were not quarantined); the verdict is `over-budget` above the budget. **Quarantine.** A quarantined test is judged on **all** its executions, those it ran non-blocking included, because "back after one full clean window" can only mean its own window; the stats say when the window is full and clean (`cleanWindow`). The **suite rate leaves quarantined executions out**, those recorded as quarantined and the earlier ones of a test that is quarantined now: otherwise quarantining the tests that put the suite over its budget would not turn the gate green until they left the window, and the policy's way out ("a same-day quarantine") would not exist. They are reported, not hidden. **The suite is judged once its window holds the minimum number of builds** (the policy gives that minimum to a test, and without it one flaky outcome in the first build of a new history is 7 % of the suite).

**Alternatives considered.** Every execution in the per-test window whether or not a retry could have shown it (ADR-131). Quarantined executions out of the per-test window too (a test returning to the gate would carry its old flakes and fail again at once). A suite rate from the first build (a gate that goes red on the first flake of a new environment and teaches people to ignore it). A rate with a confidence interval (the policy was decided on the binomial; an interval on thirty runs is wide, and a gate wants a rule a person can recompute by hand).

**Consequences.** The comparison is strict and floating-point safe for the sizes in use (the two sides are the nearest doubles of the same real number when equal, and any k/n with n ≤ 30 that differs from 5 % is far from it). Flakiness of 1 to 2 % per test is hard to see in 30 runs (3.6 % of windows, `criteria.ts`); the suite budget covers it in aggregate. A new environment is not judged on the suite for its first 19 builds: it shows its rate and says why it has no verdict. That is a decision of this record and not of the policy, and the open question for the owner of the policy.

**Defending it.** "The arithmetic of the policy is tested against the figures the policy quotes, at the boundary, in both directions. Where it was silent I chose the reading that lets the stated way out work, said so, and kept every excluded execution in the report."

## ADR-136: The quarantine list is a committed, strict file, and an entry with a problem quarantines nothing

**Context.** TEST_STRATEGY.md section 7.2: a quarantine has an owner, a reason with evidence, a start and an expiry, within 14 days (7 for a merge-tier test); the test still runs; it is never silently deleted; there are no renewals for a merge-tier test.

**Decision.** [`flake/quarantine.json`](../../flake/quarantine.json) (`schemaVersion` 1, a list of entries; it starts **empty**, which is the honest state). An entry: `id` (a catalog id), optional `project` (an engine the test runs in; without it, every engine), `reason`, `owner`, `since` and `expires` (UTC days, `YYYY-MM-DD`), `evidence` (an issue or a CI run). [`flake/quarantine.ts`](../../flake/quarantine.ts) reads it in two steps. The **shape**: every field a non-empty string, real calendar days, **no key it does not know** (a misspelt `project` would otherwise quarantine a test in every engine without anybody having said so). The **policy**: the id is a row of the catalog; the engine is one the test runs in; `since` is not in the future; `expires` is not before `since` and within the maximum age of the test's tier (the tier comes from the catalog); no test and engine is named twice, and no entry for every engine sits next to one for a single engine. An entry is in force from `since` through the end of the day it expires; from the next day the gate fails. Only entries **without a problem** quarantine anything: a typo in one entry takes nothing from the others and gives nothing to its own.

**Alternatives considered.** A tag or annotation in the spec (it hides the test from the reviewer of the list and has no expiry). `test.fixme` (it stops the test from running, which the policy forbids, and it asks a person to remember). An issue label (no schema, no gate can read it offline). A lenient file with warnings (the list is the one place where a typo means a test leaves the gate).

**Consequences.** A quarantine is a pull request, so it is reviewed and `git log flake/quarantine.json` is its history. **"No renewals" is not enforced by the tool**: a renewed entry is a new `since`, which a file cannot tell from a new quarantine of a test that came back and flaked again, so renewals are held back by the age limit and by review (the limit is written in FLAKE.md). Days are UTC, so a person east of UTC may have a `since` that is for a few hours "in the future" and a message that says so.

**Defending it.** "The list is small, human-edited and critical, so it is strict: I would rather fail the gate on a typo than quarantine the wrong thing. And an invalid entry does not protect, so the failure of being wrong is a red build and not a hole."

## ADR-137: The gate judges the history with this build's runs in it, fails with a decision, records the failed builds too, and does not judge the pull request's own failures

**Context.** The gate has to fail merges on regressions of flake rate, and the failure has to say what to do (TEST_STRATEGY.md section 10: fix it or quarantine it the same day, with an owner and an expiry). It must not turn into a second test run.

**Decision.** [`flake/gate.ts`](../../flake/gate.ts) (`npm run flake:gate`). It reads the runs just recorded (`reports/flake/run*.json` at any depth: a job that downloads the run files of several engine jobs has a directory for each) and the history of their environment, adds the runs to the history **in memory** and judges what this build ran. **Exit 1** for: a test above the trigger that is not quarantined; an engine job above the suite budget; an expired quarantine (and, said apart, an expired quarantine of a merge-tier test: a hole in the merge gate that outlived its week); a quarantine list that is not valid or is missing. Each failure is printed with the numbers and with **the decision it drives**: what to do, who, and by when (the latest expiry a quarantine may have today, for the tier of the test). **Exit 2** when it cannot judge: no run file, a history it cannot read, run files of several environments, a catalog it cannot parse, arguments it does not understand. Everything it does not fail on is a note: a quarantined test still above the trigger, a quarantined test that has had its clean window (its owner can take it back to the gate), tests and engine jobs without enough data. `--record` appends the runs to the history after judging, **whatever the verdict**, and `--push` publishes them (ADR-134); without `--record` a pull request is judged and forgotten. A build that failed the gate is recorded: a history of the good builds only would understate the rate. It is **not a verdict on the pull request's own failures**: a test that failed after its retry already failed the browser job.

**Alternatives considered.** Judging the history without the build's runs (the gate would lag by a build, and a pull request that introduces a flake would pass its own gate and fail the next one). Failing a pull request whose own run had a flaky test (ADR-022: it blames the author for a shared cost). Failing on any `failed` outcome (that is the browser job's verdict, and doubling it hides which stage says what). Exit 1 for every problem (a missing run file is a broken pipeline, not a flaky test, and ADR-022 says a rerun is for infrastructure).

**Consequences.** A pull request can be blocked by a flake that is not its own, which the strategy accepts (section 13, risk 4); the way out is in the message. A gate that judges what a build ran leaves the other engines' flakes to their own jobs. The tests cover every failure mode with its message and its decision, the boundary of the trigger and of the expiry day, the way out (quarantining the offenders turns the gate green), the exit codes of the command, the records it writes, and a real git store; and the gate was mutation-checked (ADR-139).

**Defending it.** "A gate that only says 'red' gets rerun until it is green. This one says which test, with which numbers, who decides, and by when; and it says 'I could not judge' with a different exit code than 'I judged and it is bad'."

## ADR-138: `gate:merge` runs the quarantined tests apart, and the collector asks for the retry that makes a flake visible

**Context.** A quarantined test must not block the merge and must still run (so that its results accumulate and it can come back). And the real flake data of the suite has to be gathered somewhere.

**Decision.** [`tools/gate-merge.ts`](../../tools/gate-merge.ts): with an empty list it is exactly `playwright test --grep @merge` plus the arguments it is given. With quarantined tests it makes **two invocations**: the blocking one is `--grep @merge --grep-invert <pattern of the quarantined tests>`, and its exit code is the command's; the second runs only the quarantined `@merge` tests (`--pass-with-no-tests`, an output folder, a JSON report, an HTML report and a run file of its own under `reports/`, so that it does not overwrite the first one's), its results are recorded as quarantined, and it never changes the exit code. Both share one run id, so they are one build. The pattern is matched against the string Playwright builds for `--grep` (the project, the file, the `describe` titles, the title, the tags, joined with spaces, tested from the start), and it is **anchored on structure**: the engine when the entry names one, then the spec file, then the id right after it. A pattern that matched more than it should would take a test out of the gate unseen, so it matches **less** than it could: a quarantined test inside a `test.describe` keeps blocking, and the wrapper says which tests it excluded. An entry that has a problem, or has expired, excludes nothing; a list or catalog it cannot read excludes nothing and says so. [`tools/flake-collect.ts`](../../tools/flake-collect.ts) repeats one invocation N times and appends each repetition to the file store; it puts the flake reporter on the command line (so the run is recorded whatever the configuration says), asks for `--retries 1` (ADR-131), gives each repetition a run file of its own, and stops, keeping what it has, when Playwright is killed or writes no run file.

**Alternatives considered.** `test.fixme`, or a skip list in the config (the test stops running). A custom Playwright reporter that turns a quarantined failure green (the job is green because the report was edited, and the test still blocks while it runs). `--test-list-invert` with exact test titles (exact, but it needs the titles, which the list does not have, and a first listing run to get them). One invocation with a post-hoc filter of the exit code (a quarantined failure and a real one in the same job cannot be told apart by an exit code).

**Consequences.** The quarantined tests cost a second Playwright start in the merge job (a few seconds plus their own run). The pattern was checked against the string Playwright builds, over every id of the catalog and every engine (it excludes exactly what the entries name), and against the real runner once: the fixture run excluded the quarantined test of one engine, ran the other engine's copy and the test that only mentions the id in its title. `package.json` still points `gate:merge` at plain Playwright; the orchestrator points it at the wrapper, and a `flake:collect` script at the collector.

**Defending it.** "The one thing a quarantine must not do is hide a test that is not quarantined, so the pattern is as narrow as I could make it, and its failure mode is a test that blocks too long, not one that leaves the gate."

## ADR-139: What the numbers cannot tell, and how the gate was checked

**Context.** A flake rate is easy to over-read, and a gate that passes proves nothing unless it could have failed (TEST_STRATEGY.md section 13, risk 2).

**What the rate cannot tell.** It is a count over a window, not a probability: 30 executions cannot tell a test that flakes 1 % of the time from one that never does, and one that flakes 5 % is caught in 45 % of windows (`criteria.ts`). It sees only what one retry hides, so it is a lower bound. It does not say that the **test** is at fault: a flaky outcome of a test of the player may be an intermittent defect of the player, introduced by a commit, and the history mixes commits (the signature and the commit of the last failure are in the report for that reason). A pull request's run is not recorded, so a flaky test that appears only in pull requests is seen by the gate on its own build and not in the history. Every number belongs to one environment. A skipped test is not counted, so a documented gap hides its own flakes (the skip reasons are listed). Quarantined executions are left out of the suite rate by design: a long quarantine is a hole that the rate does not show, which is why it is capped at a week for the merge tier.

**How the gate was checked.** Beyond the unit tests (statistics against the figures `criteria.ts` quotes, the history, the quarantine file, every failure mode of the gate with its message and decision, the command and its exit codes, the reporter against the real runner, the git store against real git), the gate was **mutation-checked**: one line of the code changed, the flake tests run, the change reverted.
