# GitHub Actions decisions (ADR-110 to ADR-114)

Architecture decision records for the pipeline that runs the lab as a merge gate on GitHub Actions: [`ci.yml`](../../.github/workflows/ci.yml) (the gate), [`nightly.yml`](../../.github/workflows/nightly.yml) (the release tier), [`streams.yml`](../../.github/workflows/streams.yml) (the streams the jobs share), the [`setup` action](../../.github/actions/setup/action.yml) and the job summary [`tools/ci-summary.ts`](../../tools/ci-summary.ts). The pipeline as a diagram, the jobs and how to reproduce each one locally are in [CI.md](../CI.md). The Jenkinsfile runs the same stages; its decisions are ADR-115 to ADR-119 in `docs/decisions/ci-jenkins.md`. They are written so each one can be defended in a review: what the situation was, what was chosen, what was rejected, what it costs, and how I would argue for it. The lab-wide decisions this builds on are ADR-001 (the browser matrix) in [DESIGN_DECISIONS.md](../DESIGN_DECISIONS.md), ADR-021 and ADR-022 (the merge gate and its budget, the flake policy) in [strategy.md](strategy.md), ADR-045 and ADR-047 (determinism and the stream cache) in [media.md](media.md), and ADR-072 (documented gaps, and the one override that runs Linux WebKit) in [e2e.md](e2e.md).

**Where the numbers come from.** **Nothing in this file was measured on a GitHub runner.** The workflows were written and linted (actionlint 1.7.12: no findings; Prettier) on one machine (Apple M2 Pro, macOS 27.2, Docker Desktop), on 2026-11-04, and their commands were run there: the Firefox leg's commands in the Playwright image (`npm run docker:pw -- --cpus 2`, `CI=true`, the five streams generated on the host) passed 3 of 3 `@merge` tests in 8.5 s; the whole catalog of streams generated in 149 s with two ffmpeg threads on the busy host (112 s with four threads in ADR-047). What cannot be known without a run (the time of a job on a runner, whether a cache hit, whether `--with-deps` is fast, whether Linux WebKit passes on x64) is said where it matters, and [CI.md](../CI.md) lists it. The facts about the runners come from the committed probe runs of the codec matrix ([CODEC_MATRIX.md](../CODEC_MATRIX.md): `ubuntu-24.04` is x64 with 4 vCPUs and 15.6 GiB, `macos-15` is arm64 with 3 CPUs).

## ADR-110: The stages are the `npm run gate:*` scripts, run as parallel jobs that share nothing but the streams

**Context.** The merge gate runs in two CI systems, GitHub Actions and Jenkins, and the claim is that it is the same gate. If each system lists its own commands (`npx playwright test --grep @merge --project=firefox`, `tsc && eslint ...`), the lists drift the first time someone adds a flag to one of them, and "the same gate" stops being true without anything turning red. The other question is the shape: a chain (`static` then `unit` then the browsers) fails fast and spends nothing on a pull request that does not type-check; parallel jobs give the whole verdict at once.

**Decision.** A job is one stage, and a stage is one npm script: `static` runs `npm run gate:static`, `unit` runs `npm run gate:unit`, every leg of `merge-gate` runs `npm run gate:merge -- --project=<project>`. The workflow adds only what a script cannot know: the runner, the browser to install, the streams to download and the files to keep. The scripts that do not exist yet (`gate:perf`, `gate:flake` and `gate:triage` are defined in `package.json`, but the files they call, `perf/gate.ts`, `flake/gate.ts` and `triage/cli.ts`, arrive in later phases) have no job: a job that cannot run does not exist yet, and the places where they plug in are commented in `nightly.yml` and described in [CI.md](../CI.md). The jobs run in parallel: `merge-gate` needs `streams` and nothing else, so a red `static` does not hide a red browser, and a pull request waits for its slowest job (TEST_STRATEGY.md section 6.3), not for the sum. A pull request run is cancelled by the next push; a push to `main` and a manual run are never cancelled (the group is the run id), because the verdict on a merged commit is not superseded by the next one. The nightly uses the same rule, and it also runs once on a pull request that changes `nightly.yml`: a schedule and a manual run exist only for a file on the default branch, so without that trigger a mistake in the nightly would be found the night after the merge. Every job has a timeout, no step may fail quietly (`continue-on-error` is not used anywhere), the token is `contents: read` and nothing else, the workflow triggers on `pull_request` (never `pull_request_target`: a pull request's code runs without a write token and without secrets, and the lab needs no secret), and the only actions are GitHub's own (`actions/*`, pinned to a major version). The setup that every job repeats (Node from `.nvmrc`, `npm ci`, and on request ffmpeg, the streams and one browser) is one local action, `.github/actions/setup`. [`tests/unit/ci/workflows.test.ts`](../../tests/unit/ci/workflows.test.ts) turns these statements into checks: every `npm run` in a workflow names a script that exists, `ci.yml` calls exactly `gate:static`, `gate:unit` and `gate:merge`, every job has a timeout, nothing is `continue-on-error` or `write`, every action is GitHub's and pinned, and the legs of the gate and of the nightly are the same. The nightly runs `npm run test:e2e -- --grep "@merge|@release"`, because no script runs both tiers: `test:merge` and `test:release` select one tag each, `test:release` finds no test today (Playwright exits 1 with "No tests found": checked), and two runs in one job would overwrite each other's report (the second replaces `reports/playwright.json` and clears `test-results/`). A script `test:nightly` in `package.json` would be cleaner; adding it is the owner's decision.

**Alternatives considered.** Raw commands in the YAML (the drift above). One job that runs every stage in sequence (one setup, but the wait is the sum and a log of twenty minutes to read). A chain with `needs: [static, unit]` before the browsers (it saves the browser minutes of a pull request that does not compile, and costs the author a second round to learn that a browser test also fails; minutes on a public repository are free, an author's wait is not). One reusable workflow that holds the whole browser matrix, called from `ci.yml` and `nightly.yml` (no duplicated matrix, but the gate's commands would not be in the file that the Jenkins parity test reads, and the check names would read `merge-gate / chromium`; the duplication is five entries, and a test compares them). `pull_request_target` or a token with write access to comment on pull requests (untrusted code with a write token). A Makefile or a task runner as the shared layer (the npm scripts already are one, and the repository has no other tool).

**Consequences.** Every parallel job pays its own checkout and `npm ci` (about 20 to 30 s of a warm npm cache, not measured here). A mistake in a script breaks both CI systems at once, which is the intent. The five legs are listed twice (`ci.yml`, `nightly.yml`) and kept equal by the test, not by construction. The branch protection rule has to list the job names that this file's jobs produce (the table in [CI.md](../CI.md)), and a renamed job silently stops being required until someone updates the rule.

**Defending it.** "The CI system is a scheduler. The gate is an npm script that I can run on my laptop, in Docker and in Jenkins, so when the gate is red anywhere I can reproduce it with one command and I never have to ask whether the two systems ran the same thing."

**Update (the flake gate, ADR-170 to ADR-172 in [ci-flake.md](ci-flake.md)).** `ci.yml` now has two more jobs after `merge-gate`: `flake` (`npm run gate:flake`, which exists now: `flake/gate.ts` arrived with Phase 5) and `flake-record`. So `ci.yml` calls `gate:static`, `gate:unit`, `gate:merge` and `gate:flake`, and only `gate:perf` and `gate:triage` are still without a job. "The token is `contents: read` and nothing else" has one exception, `flake-record`, the only job with `contents: write`, which runs for a push to `main` only; the tests name it, and fail on a write permission anywhere else.

## ADR-111: The browser jobs run on the host runner, not inside the Playwright container

**Context.** A Linux leg needs a browser and its system libraries. There are two ways. On the host runner: `npx playwright install --with-deps <browser>` (apt for the libraries, a download for the browser). Or the job runs `container: mcr.microsoft.com/playwright:v1.64.1-noble`, where everything is installed and the image is the one `npm run docker:pw` runs (and the one the Jenkins agent is planned to be built on). The macOS leg cannot be a container either way.

**Decision.** Host runners, for all five legs, one browser per leg: `npx playwright install --with-deps <browser>` on Linux, `npx playwright install webkit` on macOS, and the browser directory cached by the Playwright version (`~/.cache/ms-playwright`, `~/Library/Caches/ms-playwright`). The reasons, in the order I weigh them. (1) **The evidence describes this environment.** `docs/results/codec-matrix/gha-linux-x64.json` and `gha-macos-arm64.json` were probed on these host runners, installed the same way (all three browsers at once there, one per leg here), and the specs read them: the documented gaps, the choice of stream flavour and the `evidence-drift` check of PB-ENV-001 are statements about `gha-linux-x64`. `detectEnvId()` answers `gha-linux-x64` inside a container too (GitHub sets the same variables), so a container would silently attach that file to an environment nobody probed. (2) **One set of steps for five legs**, instead of a `container:` expression that is empty for the macOS leg (which I cannot test without running it). (3) **The one-browser install is enough**: Playwright's dependency table for Ubuntu 24.04 gives Firefox `libavcodec60` (what its AAC decoding uses) and WebKit the GStreamer plugins, so the Firefox and WebKit legs get what their engines decode with from their own `--with-deps`, without the other browsers'. (4) **The Node of the job is the Node of the repository** (`.nvmrc`, 22): the Playwright image carries Node 24 (ADR-036). What I give up: the libraries are installed by apt on every Linux run (a warm browser cache does not avoid it), where the image has them already, and the image is what a developer reproduces a failure in. **This is a decision from evidence of identity, not from timing**: I could not measure either option on a runner. The first real runs give the time of "Install the browser" per leg; if it is slow against the 90 s setup allowance of TEST_STRATEGY.md section 6.3, or the apt mirrors fail the job, the change is one `container:` per Linux leg with the options `--ipc=host --init`, and the decision is reopened with those numbers.

**Alternatives considered.** The container (above: its advantage is real, and it would also bring the Linux legs closer to the Jenkins agent; its costs are a pull of the image on every job (2.47 GB on disk here, arm64; the compressed transfer is smaller and was not measured), an environment the committed probe never measured, a different Node, and a conditional `container:` in a matrix with a macOS leg). Installing every browser's dependencies in every leg (what the codec-matrix workflow does, because it probes all three; here it would only add apt time). Caching the apt packages (fragile, and the install is the thing that must work on a clean runner). A self-hosted runner (a machine to keep up, and a public repository running a pull request's code on it).

**Consequences.** A Linux leg spends its setup in apt and a browser download (or a cache restore, which Playwright's CI guide says takes about as long as the download, and the system libraries cannot be cached at all: the cache is kept because it was asked for and costs one step, and it goes if the runs show no gain). A runner image update can change a system library under the browsers; PB-ENV-001 compares the engine version with the committed evidence and says so. Linux jobs and the Docker reproduction differ in Node (22 and 24) and in CPU architecture (x64 and arm64 on this machine): [CI.md](../CI.md) says which command reproduces which job and what it does not reproduce.

**Defending it.** "I run where I measured. The probe results the specs read were taken on the host runner, so that is where the specs run. A container would be a faster setup, and I would have to argue that it is the same environment as the evidence I am reading, which I could not."

## ADR-112: The streams are generated once per cache key, published as one artifact, and never generated on macOS

**Context.** The five streams are 282 files and 43.46 MB (ADR-047) and take about two minutes to generate on four cores (112 s on the development host with four threads; about two minutes expected on a four-vCPU runner, not measured there). Every browser job needs all of them: the service refuses to start when one is missing. There are five legs now, and every later job will need them too. The bytes depend on the ffmpeg build (ADR-045: identical for one build at any thread count, different across builds: the macOS host's ffmpeg 9.0.2 and Ubuntu's 6.1.1 give different `contentHash`es for the same specs). And the macOS probe job took about 25 minutes, most of it a slow runner and `brew install ffmpeg`.

**Decision.** One job, `streams` ([`streams.yml`](../../.github/workflows/streams.yml), a reusable workflow that `ci.yml` and `nightly.yml` both call), on `ubuntu-24.04`: restore `.cache/streams` from `actions/cache`; on a miss install ffmpeg from apt, check that its major version is the one the key names, run `npm run generate:streams -- --verify` (which re-hashes every file against its `stream.json`) and save the cache; on a hit or a miss, upload `.cache/streams` as the artifact `streams` and list the streams in the job summary (id, content hash, ffmpeg version, and whether they were restored or generated). **The key** is `streams-v1-<os>-<arch>-ffmpeg6-<hash>`, where the hash covers `src/server/media/**`, `src/shared/streams.ts` and `tools/generate-streams.ts`: every file the generator imports. A unit test computes that import closure and fails when a file is outside the hash, so the key cannot go stale because someone made the generator import something new. The ffmpeg major is a literal in the workflow (`FFMPEG_MAJOR: '6'`, Ubuntu 24.04's) because the key must be known before ffmpeg exists on the runner (a hit installs nothing): the miss path compares it with `ffmpeg -version` and fails with the instruction to update it, so an entry is only ever saved under the major that generated it. Every browser job downloads the artifact into `.cache/streams` (where the service looks, which a unit test checks against `defaultCacheDir()`), and prints one line per stream: the same content hashes in the logs of five jobs are the proof that five engines played the same bytes. `actions/upload-artifact` skips hidden directories, and `.cache` is one: `include-hidden-files: true`. The artifact is stored uncompressed (already-compressed media gains nothing from zip), kept for 3 days, and replaced when a run is re-run (`overwrite`). **macOS installs no ffmpeg**: its leg does not generate anything, it plays the artifact. (`codec-matrix.yml` still installs ffmpeg with brew on macOS, because the probe makes its own test clips; it runs on demand, not per pull request.)

**Alternatives considered.** Every job generates its own streams (five times the CPU, the macOS legs wait for brew, and the engines would play different bytes depending on the OS: a cross-engine difference could be a different encoder build, and nobody could tell). The cache alone, without the artifact (on a miss every job would generate, the macOS ones after a brew install, and the artifact is the one object that is attached to this run and that all of its jobs are guaranteed to get). The streams in git (50 MB of binary, rejected in ADR-045). Building the streams into a container image (a registry to publish to, and an image to rebuild when the media code changes). Reading the ffmpeg version at run time for the key (it costs the install on every run, the thing the cache exists to save). A key that hashes the whole repository (a regeneration, two minutes, on every change to a spec file).

**Consequences.** A cold cache costs the run two to four minutes in front of every browser job: it happens on the first run of a branch whose media code changed (a pull request restores the entries of `main`, and `main` saves them when it runs). Patch updates of Ubuntu's ffmpeg (6.1.1-3ubuntu5 to a later build) are not in the key: the streams of the old build keep being used until the media code changes, and the ffmpeg version is printed next to every stream. A change of runner image to another Ubuntu changes the ffmpeg major and the job says so. The streams of a run can be downloaded (`gh run download <run> --name streams`) and replayed on a laptop, which is also how a Linux-only failure is reproduced with the same bytes. Two pull requests that miss at the same time both generate and one fails to save its copy, which is a warning and not an error. The nightly restores the same entry every day, which also keeps it from being evicted after seven days without a hit.

**Defending it.** "The streams are test data, and the thing I owe the comparison between engines is that they are the same data. So they are built once, on the one runner where the encoder is known, and every engine downloads the same files. The cache key names exactly what the generator imports, and a test proves the list is complete."

## ADR-113: Five legs, and Linux WebKit is a required but experimental one

**Context.** The matrix has to cover the four Playwright projects of [`playwright.config.ts`](../../playwright.config.ts) on the two runner families. Linux WebKit is the contested one. Its MSE playback is intermittent on the probe's page in both Linux environments (2 of 5 attempts of the primary flavour on `gha-linux-x64` and on `docker-linux-arm64`, 9 of 20 in the larger spot check in the Playwright image: [CODEC_MATRIX.md](../CODEC_MATRIX.md), ADR-031 to ADR-033), and the real player page, which adds every SourceBuffer before it fetches, passed 80 of 80 runs, each in a fresh process, in the Playwright image on arm64 (ADR-067 in [player.md](player.md), ADR-072 in [e2e.md](e2e.md)). That is evidence from one image on one architecture, and not from a GitHub runner. The orchestrator's decision is to run it in the gate as an experimental engine and track its flake rate.

**Decision.** `merge-gate` is a matrix of five legs, each a required check, none allowed to fail: `chromium`, `firefox`, `chromium-cpu4x` (the Chromium project with the 4x CPU throttle, which runs the `@cpu` subset) and `webkit-linux` on `ubuntu-24.04`, and `webkit-macos` on `macos-15`. `webkit-linux` is the `webkit` project on Linux and its job is named `merge-gate (webkit-linux, experimental)`: every test of that engine carries the `experimental-engine` annotation (the one constant `RUN_SPECS_IN_LINUX_WEBKIT` of `tests/e2e/support/gaps.ts`, ADR-072), and the job summary prints the annotation's text, so a red leg says what it is while it is red. `fail-fast` is off, so one run shows every engine's verdict. `continue-on-error` is not used: a check that is allowed to fail is a check people learn to ignore, and ADR-022's rule is that a flake is measured, not hidden. The way out of the experiment is written down: when the flake tracker (Phase 5) has a window for the leg (TEST_STRATEGY.md section 7.2: 30 builds, 20 runs before a verdict, 2 % budget per engine job), the leg either keeps its place and loses the word "experimental", or the constant goes back to `false`, Linux WebKit becomes the documented gap again and the leg is deleted, in one commit with the numbers. `webkit-macos` stays as the realistic macOS-media-stack job: macOS WebKit is the engine the lab's primary stream is proven in (`ok 5/5` on `gha-macos-arm64`). `chromium-cpu4x` is a leg of its own because it is a project of its own: the throttle is a property of the project's `metadata`, and its job runs only what `@cpu` selects (the project's own `grep` is combined with the gate's `--grep @merge`: one test today, checked with `--list`), where the plain `chromium` leg runs the same `@cpu` test unthrottled. The timeouts are nets, not budgets: 15 minutes for a Linux leg against the strategy's 8 (cold apt and browser install, a failing test and its retry), 30 for macOS (a slow 3-CPU runner; its probe job took about 25 minutes), 30 and 45 for the nightly against the release budget of 15 minutes; each leg also carries the limit of its test run (`limit`, the job's timeout less four minutes, ADR-114).

**Alternatives considered.** Linux WebKit with `continue-on-error` (a red job that never blocks becomes decoration: rejected). Not running it (it throws away the one experiment that tells whether the real page is reliable on x64, and the strategy's claim "Chromium, Firefox and WebKit" would rest on one macOS job with 3 CPUs). Running it but requiring only macOS WebKit (the same as `continue-on-error` with an extra step). Two WebKit jobs on macOS only (no Linux data, and the macOS runner is the slowest and scarcest). Folding `chromium-cpu4x` into the Chromium leg (one job, two projects: the 4x throttle would delay the other tests' feedback and a throttled failure would not be a leg of its own).

**Consequences.** **While its flake rate is unknown, a flaky Linux WebKit blocks merges.** That is the price of not hiding it, and the first runs decide whether it is a price worth paying: if the real page flakes on x64 in the first runs, the right move is the exit above, not an exception. The leg's failures need reading: ENV-001's message for this engine says that a failure is a failure of the experiment, and a spec that fails there but passes in the macOS leg is data for the experiment, not a regression of the player. The count of browser jobs per pull request is five, one more than ADR-021 (which predates the experiment) and one on a macOS runner. The two environments have different evidence: `gha-linux-x64` says WebKit is a gap and the constant overrides it; `gha-macos-arm64` says it plays.

**Defending it.** "I had two facts that disagree, a probe page that fails most attempts and a real player page that passed 80 of 80, and neither was measured on the runner. So I did not pick one and bury the other: the engine runs, it is required, it is labelled, and there is a written condition under which it is promoted or removed."

## ADR-114: Reports are artifacts with fixed names, kept for a bounded time, and summarised on the job page

**Context.** Two later phases consume what a browser job leaves behind: the flake tracker (Phase 5) reads the Playwright JSON report of every leg, and failure triage (Phase 8) clusters failures from the attachments the `diagnostics` fixture adds (CONTRACTS.md section 7.2). A person debugging a red leg needs the same files and the trace. Without a rule, an artifact is whatever the last person to edit the workflow uploaded. Measured on a deliberately failed test (one test with a 1.5 s timeout in Chromium on the development host, which fails and retries once): `reports/playwright.json` was 36 KB, `reports/html` 8.2 MB (it copies the traces and screenshots next to its viewer) and `test-results/` 6.3 MB (trace, screenshot and error context per attempt); a green run leaves 528 KB in `reports/` and a hidden `.last-run.json` in `test-results/`.

**Decision.** Every browser job uploads `reports/` and `test-results/` as the artifact `reports-<leg>` (`reports-chromium`, `reports-webkit-macos`...), in the nightly under the same names (they are different runs), with `if: always()`, because a failed run is the one that is read. **The lab's diagnostics are inside `reports/playwright.json`**: `qa-events.json`, `qa-metrics.json`, `qa-info.json`, `page-console.json`, `session-detail.json` and `request-log.json` are in-memory attachments of the failed result, stored in the report as base64; only Playwright's own files (screenshot, error context, trace) are files in `test-results/`. A consumer therefore reads one JSON per leg, and takes the traces from the other directory. Retention is chosen per artifact: the streams 3 days (regenerable from the commit), the reports of a pull request 14 days (a review cycle), those of the nightly 30 days (the flake tracker of Phase 5 is meant to keep its own history, so the window it judges by does not depend on artifacts). A re-run of a job replaces its artifact (`overwrite`), because a name that already exists is an error in the artifact service: the latest attempt of a leg is the one that is kept. **A run that is too long is ended by Playwright, not by the runner**: the stage command gets `--global-timeout=<limit>`, a per-leg number of milliseconds that is the job's timeout less four minutes (11 minutes for a Linux merge leg), because a job that the runner kills leaves no JSON report (Playwright writes it when the run ends) and Playwright's CI guide recommends a global timeout for exactly that reason. Checked: `--global-timeout=6000` on two tests wrote `reports/playwright.json` with the errors "Timed out waiting 6s for the test suite to run", marked both tests as not run and left a partial `test-results/`. Each browser job also writes a summary to its page (`tools/ci-summary.ts`, from the report of its own run, also when the tests failed): the counts, the project and the environment the run reported about itself, the errors of the run outside any test (that timeout, a setup that threw), and one table each for the tests that failed, those that passed only on a retry (a flake, ADR-022) and those that were skipped with their reason, or "no reason recorded" (a silent skip is a bug: CONTRACTS.md section 7.3), or "did not run" when the run stopped, with the names of their attachments. It never decides: it exits 0 whatever the report says, and a missing or unreadable report is stated in the summary, because a summary step that fails would hide the failure that caused it. Unit tests cover the counts, the rows, the escaping of what a table cannot hold, a missing report, an unreadable one and a run that stopped, and the exit code; three mutations (no colour stripping, no pipe escaping, an exit code that follows the report) each failed them.

**Alternatives considered.** Uploading only on failure (the flake tracker needs the green runs too, because a flake rate is flaky runs over all runs). A different layout for the diagnostics, as files (a change to the contract of the `diagnostics` fixture, and the JSON report already carries them). One artifact for all legs (a failed leg cannot be downloaded alone, and every leg would race to the same name). The default 90 days (a public repository's artifacts are visible to anyone signed in to GitHub, and they hold failure data of a lab that has no secret, but there is no reason to keep them longer than they are read). A reporter that posts the summary as a pull request comment (it needs a write token on the pull request's own code, ADR-110). Printing the table in the log instead (no formatting, and it is lost in the noise of the run).

**Consequences.** A re-run of one leg replaces that leg's artifact; the first attempt's failure stays visible in the run's logs and in the run attempt history, not in the artifacts: a consumer that wants every attempt of a CI run would need the attempt number in the name, which costs it a glob. The traces are stored twice (in `test-results/` and in the HTML report) for a failed run: about 6 MB of duplication per failed test. **A job that hits its `timeout-minutes` can lose the JSON report**: Playwright writes it when the run ends, and the runner's kill does not wait for that. That is why the stage command carries `--global-timeout` (see the decision): a run that is too long is ended by Playwright, which still writes everything. What remains open is whether the upload step runs at all after a job timeout (it is not known without a timeout to observe), and the arithmetic of the limit: the per-test timeout bounds the worst case of a merge job (every test times out and its retry too) at about 11 minutes for the 15 tests of the design catalog (15 tests x 90 s over two workers) and at 22 for the ceiling of 30, so the 11-minute limit of a Linux merge leg is where the design catalog would be cut in its very worst case: the number is the first one to revise when the real runs give the times. The flag is on the command line and not in `playwright.config.ts` because the configuration is shared with Jenkins and with the nightly, whose runs are legitimately longer than a merge job's; what that costs is that the Jenkinsfile has to ask for its own limit if it wants one. The summary text is not a gate: a person reads it, and the verdict stays with the step that failed.

**Defending it.** "A CI run that fails and leaves nothing behind has taught nobody anything. The report has a fixed name per leg, the same two directories every time, and the page of the job says what failed before anyone opens a log."
