# Test data service decisions (ADR-058 to ADR-069)

Architecture decision records for the HTTP service that ties the lab together: [`src/server/app.ts`](../../src/server/app.ts) (router and JSON API), [`src/server/pipeline.ts`](../../src/server/pipeline.ts) (the media request pipeline), [`src/server/index.ts`](../../src/server/index.ts) (`startServer`), [`src/server/cli.ts`](../../src/server/cli.ts) and [`tools/serve.ts`](../../tools/serve.ts) (`npm run serve`), [`src/lab/service-client.ts`](../../src/lab/service-client.ts), checked by `tests/unit/server`, [`tools/smoke-service.ts`](../../tools/smoke-service.ts) and [`tools/bench-server.ts`](../../tools/bench-server.ts). The semantics are in [CONTRACTS.md](../CONTRACTS.md) (sections 3 to 5); the parts this service wires together have their own records: the media pipeline ([ADR-040 to ADR-049](media.md)), the delivery of a response body ([ADR-050 to ADR-054](server-delivery.md)) and static serving ([ADR-055 to ADR-057](server-static.md)). Each record can be defended in a review: the situation, the choice, what was rejected, what it costs, and how I would argue for it. The lab-wide decisions are in [DESIGN_DECISIONS.md](../DESIGN_DECISIONS.md) (ADR-002 puts fault injection in the service).

**Where the numbers come from.** Every figure below was measured on one machine: Apple M2 Pro (12 cores, shared with other work: the load average was between 1.5 and 2.9 during the runs), macOS (Darwin 27.2.0), Node 22.11.0, Vitest 5.1.0, ffmpeg 9.0.2 (which generated the streams), real TCP on `127.0.0.1`, at commit `52d5b07` (the code of this phase; the commits after it are documents), except where a figure says otherwise. Nothing was measured on Linux, in Docker, on x64 or in a browser. The tests assert the contract, not these exact numbers.

- **Tests.** `npx vitest run tests/unit/server`, five runs in a row: 17 files, 512 tests (150 of them written for this service, in 10 files, against the real `startServer` on port 0 with an in-memory fake of the media store), all passed in each run, each in 8.5 s. The unit job of CI needs neither ffmpeg nor generated streams.
- **Smoke.** `npm run smoke:service -- --cache-dir <a cache with the five streams>`: 15 of 15 checks passed, against the real streams, over HTTP, with the real clock and the real CLI as a child process (the table is in ADR-069).
- **Benchmark.** `npm run bench:server`, 2000 requests of 450,000 bytes, 20 at a time, keep-alive, loopback, with nothing else of mine running (ADR-069 has the numbers).
- **Mutation checks.** Ten defects were put into the code one at a time and the tests had to fail (ADR-069 lists them). One was not caught at first; the test was changed and the mutation then failed it.

## ADR-058: A hand-rolled `node:http` service with no framework

**Context.** The service is the lab's oracle and its fault injector. What matters about it happens below the level at which a framework works: a response that is cut after 1,234 bytes, a body paced by a token bucket shared with another response, a request that is listed while it is still in flight, a client that disappears in the middle of a write. `deliver()` ([ADR-053](server-delivery.md)) needs the raw `ServerResponse` and its socket. The lab's dependency policy is Node's standard library plus the player under test, and the service has twelve routes.

**Decision.** One `createServer` handler (`app.handle(req, res)`), one `switch` on the path plus one regular expression for `/api/sessions/:id/...`, and a few helpers in `http.ts` (send, JSON, errors, the CORS preflight, the body reader). The code is split by responsibility and not by layer: `app.ts` (router and control API, 310 lines), `pipeline.ts` (everything under `/s/<session>/`, 318 lines), `http.ts` (142), `buckets.ts` (37), `index.ts` (`startServer`, 57), `cli.ts` (94): 958 lines. The handler never rejects: whatever goes wrong is answered with 500 JSON, or the connection is dropped when the head has been sent.

**Alternatives considered.** Express: its body parser and error handler have defaults (limits, error shapes, content-type checks) that would have to be found, switched off or tested one by one, and the part that matters is below it anyway. Fastify: schema validation is attractive, but the validators exist already (`validateFaultRules`, `parseSessionRequest`) and its reply object has its own lifecycle that `deliver()` would have to work around. A router package: for twelve routes it is a dependency that replaces a regular expression.

**Consequences.** Every behaviour of the service is in the repository and in a test: the order of 404, 405 and 413, the shape of an error, what an OPTIONS gets. The price is that nothing comes for free: `OPTIONS` (CORS preflight) is answered before routing because `serveStatic` would answer it with 405, `HEAD` is a property of the helper that writes a response, and a new route is a few lines plus its tests. The service speaks HTTP/1.1 only.

**Defending it.** "The only interesting code in this service is what a framework would stand between me and, and the rest is a switch statement. 958 lines I can read in an afternoon beat a dependency whose defaults I would have to test, and every route has a test that states its status codes."

## ADR-059: Isolation by construction: everything a test can change lives in its session

**Context.** The browser suites run many tests at once against one service; a rule installed by one must never touch another ([CONTRACTS](../CONTRACTS.md) section 4). The way this usually fails is shared state that nobody thought of as state: a token bucket in a module variable, a cache of manifest bodies, a PRNG.

**Decision.** A `Session` owns the live clock parameters, the fault engine (rules, rule clock, `times` counters), the request log, the counters, the manifest bodies kept for the stale-manifest fault, and an `attachments` map where the HTTP layer keeps the token bucket of each throttle rule (`bucket:<ruleId>`). The service has no other mutable state than the store (id to session) and the diagnostic counter of `deliver()`. The session id is in every media URL, so any client can be told apart without cookies or headers, which a media element cannot add. Ids are 48 random bits (12 hex digits) with a collision check; they identify, they do not authenticate. The store holds at most 500 sessions (503 beyond), a session lives 900 s by default and at most 24 h, and expiry is lazy: an expired session is gone on its next lookup, and the store sweeps when it is full. There is no timer, so a service that is idle does nothing and the process can exit. Deleting a session forgets it at once, but responses that are already being written run to the end.

**Alternatives considered.** One process per session (isolation by the operating system: slow to start, one port each, and a harness that wants thirty sessions starts thirty servers). Rules keyed by a request header or a cookie (a media element's requests carry neither, and a cookie couples a test to a browser context). Rules keyed by client address (all tests share `127.0.0.1`). A timer that sweeps expired sessions (one more handle that has to be cleared on close; the cap bounds memory just as well).

**Consequences.** A session id in a URL is visible in logs and in a player's network panel, which is what a test author wants. A test that leaks sessions fills the cap after 500, and the 503 says to delete them. The worst case for memory is 500 sessions with full logs: the heap in use grew by 0.6 to 2.0 MiB while one session filled its log of 5000 entries (measured over runs of 20,000 to 240,000 requests), so at most about 1 GiB; no test comes near it, and the limit is stated here and not hidden.

**Evidence.** `isolation.test.ts`: a fault in session A against the same segment of session B at the same instant (A is cut after 10 bytes, B gets the whole segment, byte for byte); two sessions that each throttle at 1600 kbps run concurrently at 1600 each; three live sessions where one is stalled, one serves stale manifests and one is healthy; twenty sessions in parallel of four kinds (a status fault of its own code, a latency of its own length, an abort at its own byte, a live clock of its own age), each of which sees exactly its own world and a log that contains only its own requests. Putting the token buckets in a module-level map (instead of in the session) fails 3 tests.

**Defending it.** "The test that matters is not that session A is isolated from session B in the usual case but that I cannot find a place where it is not: there is no module-level state, and I put one there to check that the tests would notice: three failed."

## ADR-060: The media request pipeline is ordered: list, plan, decide what exists, build, write, complete

**Context.** Everything under `/s/<session>/` goes through one function (`serveMedia`). The order of its steps decides what the log shows, which requests count toward `times` and start the rule clock, and what a latency fault delays. It would be easy to get a different but plausible order by accident.

**Decision.** (1) The router finds the session; without one there is a 404 that no log can hold. (2) The request is **listed** (`log.begin`) before anything that can take time or throw: it is visible, pending, from its arrival, and `seq` is its arrival order. (3) It is **resolved**: the method (405), the stream and the protocol of the path (404), and that the URL is the one URL of the resource ([ADR-066](#adr-066-one-url-per-resource-and-the-routes-never-decode)). A request that is not a resource of the session never reaches the fault engine, so it neither consumes `times` nor starts the rule clock. (4) The **fault plan** is decided from the request alone (kind, representation, number, track) and before anything about the resource is looked at, with the log's `seq` as the jitter seed. (5) **What exists** is decided at the instant of arrival: the live window is read once (`liveView(now)`, then `availability`), the manifest is built, the bytes are fetched from the store. A segment that does not exist, or is not published yet, is a 404 with a reason, delivered like any other answer. (6) The answer is written by `deliver()` with the plan applied: latency, buckets, stall, abort. (7) The entry is completed in a `finally`, whatever the client did, and the session counts it.

**Alternatives considered.** Deciding what exists after the latency (a manifest delayed by 3 s would be built 3 s later and therefore be fresher than the origin made it: wrong, a slow network does not make an origin newer). Deciding the plan after existence (a request for a segment that does not exist would not count toward `times`, and a `status` fault would not fail it: a failing origin fails everything). Logging at completion (see [ADR-061](#adr-061-the-request-log-is-a-second-observation-channel-listed-from-arrival-completed-in-place)).

**Consequences.** A `status` fault answers a segment that does not exist with its status, not with 404 (tested). A HEAD counts toward `times` like a GET (tested). A 404 for a segment that is not yet published is delayed by a latency rule like any other answer (tested through the plan, not separately). The cost is that the time between the arrival and the write is spent twice in the log (see ADR-061).

**Defending it.** "It is the order in which an origin behind a slow network behaves: the origin decides when the request arrives and the network delays what it decided. I wrote the order down as a numbered list because the alternatives are all plausible, and every step has a test that fails if it moves."

## ADR-061: The request log is a second observation channel: listed from arrival, completed in place

**Context.** A test of a player can ask the player what it did (`window.__qa`) and can ask the server what the player fetched. The second channel is only useful if it can be read **while** a request is in flight ("a request for segment 7 has started": the test waits on the server instead of sleeping) and if a cursor cannot lose a request that finishes late.

**Decision.** `RequestLog.begin` is called on arrival and returns an entry that the pipeline updates in place: `faults` as soon as the plan is known, `status` and `ttfbMs` when the head has been flushed, `bytes` and `totalMs` after every piece of the body, and at the end `pending: false`, the final values and `aborted` (a fault abort and a client that left both set it; `faults` tells them apart). `bytes` is what the operating system accepted, as in [ADR-053](server-delivery.md), not what the client read. The times are measured from the arrival of the request at the handler, so the time the service spent before it started to write (a manifest build, `rewriteTfdt` of a live segment) is included: a client sees it too. Every request of a session that exists is an entry, whatever the answer: a 404 for a segment that does not exist, a 405, a path the service does not know (`kind: 'other'`). The stored path has no query string and is cut at 300 characters. The control API, `/health` and `/player` are not logged. Reading the log returns copies.

**Alternatives considered.** Listing at completion: the sequence number would be assigned late, so a reader at `since=<last seq seen>` can miss a slow request that completes after a faster, later one, and a test cannot wait for a request that has started. Server-sent events or a WebSocket for the log: a second protocol and a connection to manage, where polling a cursor costs one cheap request. A file log: not readable by a test without parsing, and shared across sessions.

**Consequences.** `ServiceClient.waitForLog` is the way an end-to-end test waits on the server, and it lives in `src/lab` because the lint rule that forbids timers in specs applies to specs. Memory: a session keeps its last 5000 entries (1 to 2 MiB of heap in use, see [ADR-059](#adr-059-isolation-by-construction-everything-a-test-can-change-lives-in-its-session)); the turnover of the entries is also what makes the service's resident size step up by 25 to 37 MiB in its first twenty thousand requests and then stay there ([ADR-069](#adr-069-what-the-service-does-not-model-and-how-it-was-checked)). A request whose client reads very slowly stays pending in the log until it finishes or the client leaves.

**Evidence.** `log-http.test.ts` (5 tests): a request delayed by 400 ms is in the log as `{ pending: true, status: 0, bytes: 0, faults: ['f1'] }` before it answers and the same entry is completed afterwards; a stalled response shows `{ status: 200, bytes: 200, pending: true }`; a slow request seen at seq 1 is not skipped by readers whose cursor is at seq 3; a client that hangs up during a latency, or in the middle of a throttled body, leaves an entry with `pending: false, aborted: true` and releases the delivery. Listing `faults` only at the end fails 1 test; not updating `bytes` while writing fails 2.

**Defending it.** "A log you can only read after the fact is a log you cannot wait on. Listing from arrival costs nothing and turns the log into something a test can synchronise with, which is the only way to keep the no-fixed-sleeps rule in tests that look at the server."

## ADR-062: The live clock and the stall model, as implemented

**Context.** [CONTRACTS](../CONTRACTS.md) section 3 defines a virtual live clock, and section 5 two origin failures: an origin that stops publishing and then catches up (`live-stall`), and a cache that serves an old manifest (`manifest-stale`). They are pure functions in `liveclock.ts` and `faults.ts`; this record is about how the service uses them.

**Decision.** The clock is the injected `Clock` (the system clock in production, a manual clock in the tests). A live session has `AST = createdAt - startOffsetSec`; the edge is `floor((now - AST) / d)`, the manifest lists `[max(1, edge - window + 1), edge]` and its `publishTime` is the publication instant of the edge segment; a segment above the edge is 404 (not yet published) and one more than 2 below the window is 404 (gone). DASH gets `timeShiftBufferDepth = window x d`, `minimumUpdatePeriod` 2 s, the session's presentation delay and a `UTCTiming` element that points at `/api/time`, which answers with the **service's** clock, so a player's clock offset is relative to the same clock that decides the edge. During a `live-stall` the manifest keeps the frozen window and the frozen `publishTime`, segments above the frozen edge are 404, and when the stall ends the edge is the free-running one again: segment numbers, and with them the media timeline, are untouched. `manifest-stale` replays, per manifest URL, the body recorded before the rule became active (a URL that had not been served has its first body in the window recorded and replayed), and replaying does not build the manifest. The window is read once, at arrival ([ADR-060](#adr-060-the-media-request-pipeline-is-ordered-list-plan-decide-what-exists-build-write-complete)).

**Alternatives considered.** Publishing with timers in real time (a state machine that drifts, cannot be driven by a manual clock and holds a handle per session). A `?now=` parameter chosen by the client (the player does not know it). Serving the live manifest from a cache refreshed every 2 s (it would add its own staleness, which is the thing `manifest-stale` has to control).

**Consequences.** The edge moves in whole segments, at exactly the instants the contract says: with the manual clock the edge is 15 at 1999 ms and 16 at 2000 ms (tested). The `Date` header of a response is Node's and comes from the system clock, not from the injected one; `/api/time` and every timestamp in a manifest come from the service clock.

**Evidence.** HTTP tests with the manual clock: the window slides (first 8, last 22 at +14 s), a segment older than the window by 2 is served and by 3 is gone, live segment `n` is source `((n-1) mod 12)+1` of loop `(n-1) div 12`, a stall frozen at 18 for 10 s answers 404 for segment 19 while the free-running edge is 19 and then catches up to 23 with segment 19 still the same segment; a stall installed after its segment was published starts at once; a replayed manifest is byte-identical and builds nothing; one live session's stall and stale manifest do not touch two others. The same stall through the real manifest, in real time (`npm run smoke:service`): frozen at edge 16 with an unchanged `publishTime` for 6000 ms, segment 17 a 404 meanwhile, then edge 19, and segment 17 byte-identical to what the store returns for an origin that never stalled. Removing the availability check fails 8 tests; ignoring the stale plan fails 3.

**Defending it.** "Every question about the live edge is a function of an instant, so the tests choose the instant. The one place where real time is unavoidable, the smoke test, runs the same stall for six real seconds against the real files, and the segment that comes out of the catch-up is compared byte by byte with the one an origin that never stalled would have served."

## ADR-063: One fault plan per request, and what happens when several fire together

**Context.** Rules fire on a request in combinations: a throttle with a latency, a status with a stall that was meant for the same segment, two throttles on one link. [CONTRACTS](../CONTRACTS.md) section 5 says what each does; the service has to say what they do together.

**Decision.** The engine returns one plan per request ([ADR-060](#adr-060-the-media-request-pipeline-is-ordered-list-plan-decide-what-exists-build-write-complete) step 4); the pipeline turns it into the arguments of `deliver()`. Latencies add. Every throttle that fired limits the response (the slowest wins, [ADR-051](server-delivery.md)). The first stall and the first abort in rule order win. A `status` answers with that status and an **empty body**, and then the faults that need a body are dropped (a stall of 0 bytes would otherwise hold the response open for no visible reason: a client that does not hang up would see a response that never ends; I found it by testing with a keep-alive client, a client that closes the connection after a response without a body hides it). The latency still applies. A `status` between 100 and 199 is accepted by the contract's validation but is an interim response, which clients never take as the final one: a 101 or a 199 leaves a client waiting, a 100 makes `fetch` fail; the service does not crash and the connection stays usable, and I did not change the validated range.

**Alternatives considered.** Letting the body faults act on the empty body of a status answer (it holds a response open for nothing). Applying only one fault per request (the combinations are the point of the profiles in `src/shared/profiles.ts`).

**Consequences.** A response that the plan marks as `status` shows in the log with every rule that fired, including the ones that were dropped, which is what happened to the request, not what was done to it.

**Evidence.** A status 500 with a stall of 10 s, an abort and a throttle of 1 kbps fires 5 rules, answers in under 2 s with the 150 ms of latency, and is completed and not aborted in the log (dropping the guard that drops the body faults fails this test: the entry stays pending); a throttle with a latency of 250 ms delays the head by at least that and paces the body after it; two throttles of 6400 and 1600 kbps give the client 1600 (within 10 %).

**Defending it.** "The plan is decided once, from the request, and the rest of the pipeline only carries it out; so the question 'what do two faults do together?' has one answer in one place and one test for each answer."

## ADR-064: Throttle wiring: one bucket per rule and session, shared by concurrent responses, replaced when the rule changes

**Context.** The contract says a throttle is one link for all the concurrent responses of a session and a rule ([ADR-051](server-delivery.md)). The bucket itself knows nothing about sessions or rules; the HTTP layer has to give the right bucket to the right responses, and to forget it at the right time.

**Decision.** The bucket of a rule lives in the session (`attachments`, key `bucket:<ruleId>`) with the rate it was made for. A response gets the bucket of every throttle that fired. The bucket is replaced when the rule's `kbps` differs from the one it was made for, and forgotten when the rule is removed and when the rules are replaced (`PUT`), so that a rule that comes back under the same id starts on a fresh link. A response that is already being written keeps the bucket it was given, so a rule change applies from the next request on.

**Alternatives considered.** A bucket per response (a session limited to 1500 kbps would see 3000 as soon as two requests overlapped). A global map keyed by rule id (the rule ids `f1`, `f2` exist in every session). Re-rating a live bucket when the rule changes (the bucket would then have to model a link whose capacity changes under queued consumers; the contract describes a rule change as a new condition).

**Evidence.** One 120,000-byte segment on a 1600 kbps rule arrived at a steady 90 to 110 % of the rate (asserted) and its log entry says it took more than 450 ms (120,000 bytes less the 16 KB burst at 200 kB/s is 0.52 s); the audio and the video segment of one session fetched together on a 1600 kbps rule took more than 900 ms for 240,000 bytes, where two private buckets would take about 520 ms (asserted, and the sum is within 15 % of the rate); sessions do not slow each other down. Against the real streams (`smoke:service`): 2395 kbps for one 433,673-byte segment and 2399 kbps for two segments in flight together (876,374 bytes) at a configured 2400. Creating a new bucket for each response fails 4 tests; a global bucket map fails 3.

**Defending it.** "The bucket is arithmetic, the session is the owner of the link. The only decision is when a link is a new link, and I made it the same as when a rule is a new rule."

## ADR-065: Errors have one shape, limits are enforced as the bytes arrive, and a client mistake is never a 500

**Context.** The control API is used by tests and scripts that need to read why a call failed, and a service that answers a malformed request with a 500 makes a lab failure look like a service bug.

**Decision.** Every error of the control API is JSON `{ error, details? }` with the right status: 400 (a body that is not valid JSON, empty, not an object, or invalid; a `since` that is not an integer >= 0; every problem listed in `details`), 404 (unknown session, rule, path; a stream that is valid and was not generated, with the command that generates it), 405 with an `Allow` header (which always includes OPTIONS), 413, 503 (the session cap). A 201 carries a `Location`. A body is accepted whatever its `Content-Type`: `fetch` sends `text/plain` for a string. A body over 64 KiB is refused with 413: a declared length is refused without reading a byte, an undeclared one (chunked) on the chunk that crosses the limit, so the service never buffers more than the limit; the rest of the body is discarded by Node and the connection stays usable. A bad request body is a request problem, so `JSON.parse` failures are 400 with the parser's message. An exception inside a handler is logged (when logging is on) and answered with 500 JSON, or the connection is dropped if the head was already sent. What is handed to `deliver()` is checked first (a status in 100 to 599, header values that are strings or finite numbers without line breaks), because `deliver()` answers an invalid header by dropping the connection ([ADR-053](server-delivery.md)): a failure becomes a 500 JSON instead.

**Alternatives considered.** Requiring `Content-Type: application/json` (it would reject a client that is right but did not say so, and it is the one thing that would make a browser send a preflight; see [ADR-067](#adr-067-security-choices-loopback-limits-and-what-they-do-not-cover)). Closing the connection after a 413 (a client that is still sending can lose the 413 to a reset). Letting Node answer a malformed request (it does: a half request line is a 400 from the parser and the next request on a new connection works, tested).

**Consequences.** `GET /player/*` errors are the plain-text ones of `serveStatic` ([ADR-057](server-static.md)), not JSON. After a 413 with a 70,000-byte body the same keep-alive connection serves the next request (tested). The `Allow` list is "what the resource supports, and OPTIONS".

**Evidence.** `api.test.ts` (39 tests): every endpoint, its happy path, and each status; a body of exactly 65,536 bytes is accepted and one more is a 413; the 413 for an undeclared body arrives while the terminating chunk has not been sent; every 405 has its `Allow`.

**Defending it.** "A test author reads these messages every time a test fails. I want the answer to say what is wrong and to be the same shape everywhere, and I do not want the lab to ever tell them 'internal error' for something they sent."

## ADR-066: One URL per resource, and the routes never decode

**Context.** `parseServicePath` accepts any extension and any run of digits. If the service served what it parses, `/seg/v360/01.m4s`, `/seg/v360/1.webm` and `/seg/v360/1.m4s` would be three URLs for one segment, and a manifest that wrote the wrong one would play.

**Decision.** For an init or media segment the request path must equal the path the builders of [`src/shared/urls.ts`](../../src/shared/urls.ts) make for that session, stream, representation, number and the representation's own extensions; anything else is a 404 that names the URL. A representation, a segment number or a playlist that does not exist is a 404, never an exception. Routes never decode percent-escapes: ids are plain tokens, and an encoded id is an id that does not exist (`v%33%36%30` is not `v360`). A query string is ignored for routing, and `Range` is ignored: the whole body is served with a 200.

**Alternatives considered.** Accepting aliases (a player bug would be hidden by the service). Decoding the path once (static serving does it, for files, where it is the point; for ids it would only add a second spelling).

**Consequences.** A manifest bug that writes `.mp4` for a WebM stream fails at once with a 404 in the log, which is where a test looks. `<video src>` against a media URL would not seek (no `Range`), which does not matter for the Media Source player the lab tests.

**Defending it.** "A test lab should have exactly one way to be right. Anything the service accepts that it did not publish is a way for a bug in a manifest to look like a working player."

## ADR-067: Security choices: loopback, limits, and what they do not cover

**Context.** The repository is public and the service has no authentication, because it has nothing to protect: the streams are test patterns, the ClearKey pair is public on purpose, and sessions are throwaway. It still runs on a developer's machine next to a browser.

**Decision.** The service binds `127.0.0.1` unless told otherwise; `PB_HOST` other than loopback prints a warning (the service has no authentication). Media routes never touch the file system with anything taken from the request: the store is addressed by validated stream and representation ids and numbers. The only path from a request to the file system is the player (`serveStatic`, [ADR-055 to ADR-057](server-static.md)), which is sealed to its directory. Limits: 64 KiB of JSON, 100 rules and 500 sessions, a label of 200 characters, a lifetime of 24 h, 5000 log entries per session holding at most 300 characters of a path, and Node's own limit on request headers (16 KiB, a 431). `Access-Control-Allow-Origin: *` is on every response because the page under test and the service are different origins in the lab.

**What this does not cover.** Any web page that the developer's browser opens can call the service while it runs (it is `*`, there is no authentication and no `Content-Type` is required): it could create up to 500 sessions, delete or change them, and read their logs. It cannot read files, run code or reach anything outside the service. The `Host` header is not checked, so DNS rebinding is not mitigated; the same attacker gets the same capabilities as above. A client that opens a response and never reads it holds that response (and a pending log entry) until it disconnects or the service closes: there is no per-response timeout. There is no TLS and no HTTP/2.

**Alternatives considered.** A token in an environment variable (every harness and every test would have to carry it, for a service whose data is public). A `Host` allow-list (it breaks `PB_HOST=0.0.0.0` and Docker, where the lab's Linux browsers reach the service by another name). Requiring `Content-Type: application/json` to force a preflight (the cheapest anti-CSRF measure; rejected in [ADR-065](#adr-065-errors-have-one-shape-limits-are-enforced-as-the-bytes-arrive-and-a-client-mistake-is-never-a-500) for its cost to correct clients).

**Defending it.** "I wrote down what a hostile page can do to this service, because the answer is 'waste a developer's time with sessions' and not 'anything else', and I did not add authentication to a service whose only secret is that it exists."

## ADR-068: Start, stop and `npm run serve`: nothing is left behind, and a missing stream is a refusal

**Context.** A test harness starts the service hundreds of times in a day and a service that does not stop cleanly leaves a process that holds a port and fails the next run in a way that looks unrelated.

**Decision.** `startServer` returns `{ origin, port, close }`. `close()` stops accepting, destroys every open connection (`closeAllConnections`: a keep-alive connection or a response that is stalled for a minute would otherwise keep `close` waiting) and resolves when the server is gone; a second call returns the first. The service owns no timers: the ones `deliver()` creates are cancelled when their client goes away, which is what closing causes. The CLI logic is a function of the environment (`serveFromEnv`, tested without a process or streams); `tools/serve.ts` only owns the process: it prints exactly one line, `playback-proof service listening on http://127.0.0.1:4600`, when it is ready, closes on SIGINT and SIGTERM and lets the event loop drain (exit 0), exits 1 on a second signal and after 10 s if something is holding the process open. It **refuses to start** when a stream that has a spec is not generated, with `stream <id> is missing: run npm run generate:streams` for each and nothing on stdout; `PB_PORT=0` picks a free port; a port in use says to set `PB_PORT`. `PB_CACHE_DIR` (not in the brief) points it at a cache elsewhere, which is what lets the refusal be tested deterministically and a worktree use the generated streams of another checkout.

**Alternatives considered.** `process.exit(0)` after `close()` (it would hide a leaked handle behind an exit code, which is exactly what the shutdown has to prove). Starting with the streams that exist and failing the requests for the others (a harness would find out in the middle of a test).

**Evidence.** A child process starts the service, opens a throttled, a stalled and a delayed response and an idle keep-alive connection, closes the service and has no `process.exit`: it ended on its own after 461 ms in one run, including loading TypeScript (without `closeAllConnections` it did not end and the test failed at its timeout). `close()` took under a second with a stalled response in flight. The smoke run starts the real CLI on a free port, reads the one line, and ends it with SIGTERM: exit code 0 after 46 ms, one line on stdout, nothing on stderr. The refusal was tested as a process (exit 1, stdout empty, every stream named) and as a function.

**Defending it.** "I do not trust a shutdown that ends in `process.exit`. The test starts a process, leaves every kind of handle open, closes the service and waits: if it ends on its own, nothing was left."

## ADR-069: What the service does not model, and how it was checked

**Context.** The owner of the lab will be asked what the service is not, and the numbers have to say what they were measured with.

**Not modelled, on purpose.** The network below the rate of a response ([ADR-054](server-delivery.md)); TLS, HTTP/2 and HTTP/3 (the lab tests the player's logic on HTTP/1.1); `Range`, conditional requests, compression and chunked bodies (a media response has an exact `Content-Length`, always); the semantics of a CDN (`Age`, `ETag`, cache keys, a shield); more than one origin; an encoder that fails in any way except the two in the contract; a clock that is wrong (the service clock is the truth, and the `Date` header is Node's); a client that cancels requests (it is tested as a hang-up, not modelled as a behaviour); any scale beyond one process on one machine.

**What was checked, and with what.** (1) The 150 tests of this phase, five runs in a row of the whole server suite (17 files, 512 tests, 8.5 s each, no failure), against the real HTTP server, with the real fault engine, the real `deliver()` and the in-memory fake store; the fake's buffers say which segment they are, so a test asserts exactly what was served. (2) `smoke:service`, 15 checks against the real streams, the real clock and the real CLI as a process: every URL a DASH or HLS manifest references (read by an independent parser) is served with the bytes, the size and the sha256 of the stream index; live DASH and HLS (window of 15, edge 15, segment 15 served and 16 a 404, `publishTime` equal to the publication instant of the edge segment, `UTCTiming` pointing at a clock within 2 s); the live loop on all four representations (`tfdt(13) = tfdt(1) + loopTicks`, `tfdt(25) = tfdt(1) + 2 loopTicks`); the faults on real segments; the encrypted stream's manifest without its key in it; clean SIGTERM. (3) Mutations: ten defects, one at a time, each must fail a test: no live availability check (8 tests fail), no sharing of a bucket (4), a bucket shared by all sessions (3), a replayed manifest ignored (3), live segments from the VOD accessor (3), OPTIONS under `/player` going to `serveStatic` (2), no `closeAllConnections` (2, one of them by a process that never ends), faults listed only at completion (1), no running byte count (2), and body faults acting on a `status` answer (1, after I strengthened the test: it was **not** caught at first, because the test used a client that hangs up when it has the head of a response without a body, which hid the stall).

**Benchmark.** `npm run bench:server`: 2000 requests of 450,000 bytes, 20 at a time, keep-alive, loopback, against a bare `node:http` server that answers with the same bytes and against the service, each in its own process and both driven by the same client. Median latency 2.35 ms for the bare server and 2.57 ms for the service (so **0.22 ms added**), 95th percentile 4.46 and 4.60 ms, 99th 5.02 and 6.40 ms, 7897 and 6906 requests per second (3389 and 2964 MiB/s). The same command four times gave a median overhead of 0.42, 0.27, 0.19 and 0.22 ms (the first three at the previous code commit, which differs in the logging of a long path only): the figure is between 0.2 and 0.4 ms, the 95th percentile difference was between -0.06 and 0.17 ms, i.e. below what a run can resolve, and the 99th percentile one 0.70 to 1.38 ms. Memory of the service: 93.9 MiB after warm-up, 96.0 MiB after the 2000 requests (+2.1 MiB; the bare server +1.6 MiB). That is not the whole story, and I looked, because the brief asks for flat memory. Over longer runs (not part of the benchmark) the resident size of the service rose by 26.8 MiB over 20,000 requests, 36.5 over 60,000, 27.6 over 120,000 and 29.8 over 240,000 (about 108 GB served): a one-off step of 25 to 37 MiB in the first twenty thousand requests and no trend after it, while the heap in use after a garbage collection stayed between 9.3 and 11.3 MiB and the bare server's resident size moved by only 1.3 to 2.8 MiB. So memory is bounded and does not grow with the number of requests, and it is **not flat**. Where it goes, from `vmmap` on the service (macOS), 30,000 requests for a 450 kB segment: the physical footprint went from 41.0 to 77.5 MiB and all of it was in the regions V8 maps (App-Specific Tag 16: 20.4 to 52.6 MiB); malloc did not move (17.0 to 17.3 MiB). 30,000 requests for `/health`, which has no log entry, moved those regions by 2.5 MiB; 30,000 `HEAD` requests for a segment (a log entry per request and no body, so no body writes at all) moved them by 30.5 MiB. The step therefore comes from the request log. My explanation, which I did not verify further: each entry lives for 5000 requests, so it survives the young-generation collections and dies in the old generation, which V8 lets grow before it collects, and the bare server keeps nothing per request. With the young generation capped at 1 MiB (`--node-arg=--max-semi-space-size=1`) the step was smaller at 30,000 requests (+11.5 MiB of footprint) and as large at 120,000 (+25.8 MiB of resident size, +25.1 at 240,000): its size depends on V8's limits and not on the service, and I did not try to make it smaller, because the log is the feature.

**Not checked.** Linux, Docker, x64, Windows, any Node other than 22.11.0; a browser as the client; more than 20 concurrent clients; 500 sessions with full logs; a service that runs for hours (the longest was 240,000 requests, 108 GB); `PB_HOST` other than loopback (the warning is tested as a function, not by listening on every interface); the Node client is the only client that measured goodput and time to first byte.

**Defending it.** "Every number here is from a command that is in the repository, and the list of what was not checked is as long as the list of what was. The one result I did not expect, a service that holds 25 to 37 MiB more than a bare server after 20,000 requests, I did not explain away and I did not hide: I ran 240,000 requests to see that it stops growing, found with `vmmap` which memory it is and which requests cause it, and wrote down that 'flat' is not what it is."
