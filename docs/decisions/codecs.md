# Codec and MSE capability decisions

Architecture decision records for the capability probe, the generated matrix and the Docker runner (ADR-030 to ADR-037). They are written so each one can be defended in a review: what the situation was, what was chosen, what was rejected, what it costs, and how I would argue for it. The evidence is in [CODEC_MATRIX.md](../CODEC_MATRIX.md) and the JSON files it is generated from; the numbers quoted below are from those files (5 attempts per case, commit `3e10134`, 2026-11-04) unless a record says otherwise. The lab-wide decisions this builds on are in [DESIGN_DECISIONS.md](../DESIGN_DECISIONS.md), in particular ADR-001.

## ADR-030: Capability is decided by decoding real media through MSE; `isTypeSupported` is kept as a claim and compared with the result

**Context.** The lab runs the same suites in three engines, using Playwright's bundled builds, and those builds differ in codecs and media pipelines. `MediaSource.isTypeSupported` is the obvious capability check and it cannot be trusted. In the committed Linux run, Playwright's WebKit answers `true` for all nine type strings it was asked, including Opus in MP4 and AV1 that its macOS build answers `false` for, while 11 of its 13 MSE cases fail in some attempts with `MediaError 4 "Failed to push buffer"`. Chromium and Firefox on the same image answer truthfully (Chromium says `false` for HEVC and fails it; Firefox says `true` for everything and plays everything). A check that only asks, or only calls `addSourceBuffer` (which succeeds in the engine that cannot play), would have produced a flaky WebKit job and taught nothing.

**Decision.** A probe decodes real media. For each case it appends ffmpeg test-pattern tracks ([ADR-037](#adr-037-probe-media-tiny-ffmpeg-test-patterns-reproducible-bytes-content-addressed-generated-on-the-host)) to real SourceBuffers, calls `endOfStream`, plays, and passes only when media time passes 1 s **and**, for video, at least 5 frames were presented (the content is 30 fps: 5 survives a loaded machine and still rejects "the first frame decoded, then nothing"; audio-only cases skip the frame check). It waits on events (`sourceopen`, `updateend`, `play()`, `timeupdate`, `requestVideoFrameCallback`) and uses a bounded safety-net timeout that reports a failure at the stage it hit and is never a measurement. On failure it reports the stage (`setup`, `sourceopen`, `addSourceBuffer`, `fetch`, `append`, `endOfStream`, `play`, `currentTime`, `frames`, plus the runner's `launch`, `navigate`, `evaluate`), the engine's own error text and the media element's `MediaError`. The `isTypeSupported` answer for every track type is stored next to the verdict and compared in both directions: **claims true but fails** and **claims false but plays**. Plain `<video src>` playback of the same files is run as a control, to say whether a failure is in the file or in the MSE pipeline. An engine that does not start is a result (`launchFailed` with the browser's own log), not an exception.

**Alternatives considered.** Trusting `isTypeSupported` (shown wrong above). Probing that `addSourceBuffer` accepts the type (it does, in the engine that cannot play). Requiring only that time advances (an element can advance time with no picture; hence the frame check). `canPlayType` or user-agent sniffing (they answer about `<video src>` or about a version string, not about the MSE pipeline). Using the lab's own streams as the probe (a phase-2 dependency, and it tests too much at once to say which codec is the problem).

**Consequences.** An attempt costs a browser launch plus about a second of playback, so the whole matrix takes minutes (about 9 on macOS and 7 in Docker for 5 attempts), not seconds: it is a tool and a CI job, and run-time callers probe only what they need (`probeCapabilities(browserType, { flavours, attempts })`). The probe appends each track as one buffer (initialization segment plus two fragments), not segment by segment as Shaka does, so it answers "can this engine demux and decode this codec and container through MSE", not "will the player's suites pass": the suites remain the proof of that. HEVC and AV1 are informational: the lab does not stream them.

**Defending it.** "I did not want a capability table I had to believe. One of three engines answers `true` to everything, so the only evidence that counts is bytes in, frames out. The cost is minutes of CPU in a job that runs rarely; the benefit is that every skip in the suites has a measured reason."

## ADR-031: A verdict belongs to a page profile: Linux WebKit decodes or fails depending on how the page drives MSE

**Context.** The first probe found Playwright's Linux WebKit failing MSE playback at `play()` (`NotSupportedError`, with `video.error` = `MediaError 4 "Failed to push buffer"`) while plain `<video src>` played the same files. The committed probe reproduces that symptom, and showed that the *rate* depends on small page-side details. In my own hands: the orchestrator's `webkit-diag.mjs` failed 12 of 12 attempts and my copies of its sequence (SourceBuffers added, then a network fetch, then the append, element muted through `video.muted`) failed 21 of 21; the first version of my probe, which fetched all the data before creating the MediaSource, passed 9 of 9 on the same bytes and image; the committed probe (muted element, data fetched after the SourceBuffers exist) passed 2 of 5 in the committed run and 9 of 20 in the [N=20 spot check](../results/codec-matrix/spot-checks/docker-linux-arm64-webkit-n20.json), with all 11 failures being `[play] NotSupportedError` plus `MediaError 4 "Failed to push buffer"`; development runs of it ranged from 2 of 6 to 4 of 5 (not committed). So the "0 of 9" of the first probe is not reproduced by the committed probe, which plays about half of its attempts, but it is reproduced by the sequence the first probe used. Changing **one** thing about the page, on the same engine, image and bytes, moves the result: **unmuted** passed 20 of 20 and **prefetch** (data fetched before the MediaSource exists, so the append follows `addSourceBuffer` at once) passed 20 of 20 (5 of 5 each in the matrix). Three ad-hoc variations outside the committed tool (not reproducible from the repository) behaved like the default: muted through the markup attribute (1 of 6), and a 50 ms and a 500 ms pause before the first fetch (0 of 4, 1 of 4). The same sensitivity rows read `ok` in Chromium and Firefox (Linux) and in Chromium and WebKit (macOS). I checked Shaka 5.3.3's `MediaSourceEngine.initSourceBuffer_`: it creates every SourceBuffer in `init()`, before the streaming engine fetches or appends anything, so a player page is on the side of the default profile, not of the prefetch one.

**Decision.** Every verdict is measured under a named page profile. The `default` profile mirrors a player page: `video.muted = true` before the source is attached, SourceBuffers created right after `sourceopen`, data fetched afterwards. It is the profile behind every cell, every `pickStream` decision and every skip. The primary flavour is also run, in every engine and environment, under two single-factor variations (`unmuted`, `prefetch`) and shown as the **sensitivity** table; it informs, it does not decide. A new profile is one entry in `SENSITIVITY_PROFILES`; changing what counts as the lab's page is one constant, `DEFAULT_PROFILE`.

**Alternatives considered.** Defaulting to a passing profile: it would report Linux WebKit as `ok` for a page that behaves like a player, and the suites would then fail in CI. Reporting only the failing profile: it would hide that a page-side behaviour decides the outcome, and that the lab's own "muted by default" (CONTRACTS, section 6) is one of the two factors. Probing with the lab's real player page: it does not exist yet, and the probe must work without it. A full factorial over every page detail: more cost than the question deserves; two factors were enough to show the dependence.

**Consequences.** (1) The statement in ADR-001 and in CONTRACTS section 2 that Linux WebKit cannot play MSE is refined: with a page that behaves like a player it is unreliable (a fraction of the attempts play), and with an unmuted element or prefetched data it played in every attempt of the committed runs. The skip for Linux WebKit stays correct for the lab's current page. (2) The unmuted row is `ok` in all three engines on both operating systems, so under Playwright's automation builds `play()` does not need the element muted; whether the page should stay muted under automation, or Linux WebKit should stay skipped, is the owner's decision for the player phase. If the page changes, set `DEFAULT_PROFILE` to match, re-run, and the matrix, `pickStream` and the skips follow. (3) I do not know why. No WebKit debugging was done; "an append that arrives after a mute notification races the GStreamer-based pipeline" is a hypothesis I have not tested. (4) This is one page-side factor space on one engine build (WebKit 27.2, arm64 Linux, in Docker Desktop's VM); GitHub's x64 runners may behave differently.

**Defending it.** "Saying 'Linux WebKit cannot play MSE' and saying 'it plays' would both have been wrong. The probe measures what a page like ours sees, and shows how much the answer moves when one thing about the page changes: that is the difference between a gap I can document and a gap I can fix."

## ADR-032: A fresh browser process per attempt, repeated attempts, and an intermittent format is not a supported format

**Context.** The first probe suspected that state leaks between cases in Playwright's Linux WebKit, and saw one case pass once in three attempts. A verdict that depends on what ran before it, or on one lucky attempt, is useless for a gate.

**Decision.** Every attempt launches its own browser process (the default; `--no-fresh-process` shares one) and every case runs several attempts (`--attempts`, default 3; the committed results use 5). A case reads `passes/attempts`, classified `ok` (all), `fail` (none) or `intermittent`. A flavour is **supported** only when it is `ok`: a gate cannot be built on a coin flip, so `pickStream` never returns a stream whose flavour is intermittent. The JSON keeps every attempt with its stage and error, summarizes the most frequent failure, and the reader checks that counts, reliability and failure agree with the runs ([ADR-035](#adr-035-the-matrix-is-generated-from-committed-per-environment-json-validated-and-checkable)).

**Alternatives considered.** One browser process for all cases (about three times faster, but a case's verdict would depend on its predecessors; I did not test whether it changes anything, because every committed result uses fresh processes, so the suspected leak is neither confirmed nor refuted here). A single attempt (it misses exactly the engines that matter). Majority vote, or retrying until it passes (that is how flakiness is hidden; this lab counts it).

**Consequences.** About 2 to 4 seconds per attempt, mostly the browser launch. With 5 attempts the cells are ratios, not probabilities: the same Linux WebKit case read 2 of 5 in the matrix, 4 of 5 in the spot check, 9 of 20 in the N=20 run. An `ok 5/5` next to intermittent cells in that engine can be luck (the matrix says so in the gap), which is one more reason the rule is "every attempt must pass". Regenerating the matrix will print different counts for intermittent cells; that is data, not a bug.

**Defending it.** "Flake rate is a first-class quantity in this lab. A capability probe that hid it behind retries or a vote would contradict the rest of the project. Intermittent is reported as intermittent, with its counts, and treated as unsupported."

## ADR-033: VP9 + AAC in CMAF is the primary flavour and WebM VP9 + Opus the DASH fallback; H.264 is not needed

**Context.** ADR-001 chose the formats from a first probe. The committed matrix confirms its macOS and Linux (Chromium, Firefox) findings with repeated attempts, and the single-track cases say which track an engine cannot take.

**Decision.** Keep the primary flavour `cmaf-vp9-aac` (fragmented MP4 with VP9 video and AAC audio, DASH and HLS from the same segments) and the fallback `webm-vp9-opus` (DASH only), in the order `vod-cmaf`, then `vod-webm`. Both decoded in every attempt in Chromium (macOS and Linux), Firefox (Linux) and WebKit (macOS). `cmaf-vp9-opus` cannot be the primary: WebKit on macOS rejects Opus in MP4 (`addSourceBuffer` throws and `isTypeSupported` says `false`: an honest "no"). H.264 + AAC also plays everywhere it was tried, but it is the codec whose presence depends on how a browser build was made; the lab does not need it, so it stays a probed flavour (`cmaf-h264-aac`) and a change shows up. AV1 does not play in WebKit on macOS and HEVC does not play in Chromium (both say so honestly).

**Alternatives considered.** H.264 + AAC as the primary (it plays in all three here, but it relies on proprietary codecs in the build, which I verified only on this machine's macOS and arm64 Linux builds, not on x64 runners; VP9 needs nothing proprietary). VP9 + Opus in CMAF (fails in macOS WebKit). WebM only (cannot be packaged as HLS, and the lab wants HLS). AV1 or HEVC (not universally decodable).

**Consequences.** AAC is the one proprietary codec in the primary flavour; it is there because Opus in MP4 is not an option in macOS WebKit. The fallback covers DASH VOD only (`vod-webm` has no HLS and there is no WebM live stream): when CMAF fails in an engine, HLS and live specs there are skipped, not rerouted. Both lab flavours share the VP9 video, so a VP9 regression takes out both; the single-track cases would show it. The probe says nothing about DRM (the clear-key stream is a separate capability).

**Defending it.** "Pick the format all three engines can decode with the fewest proprietary dependencies, measure that it really plays, and keep a second open-codec fallback. If the data changes, say a build drops AAC, the matrix shows it before the suites do."

## ADR-034: A documented gap is skipped with a reason built from the evidence; a failure outside a documented gap is a failure

**Context.** Some engine and environment pairs cannot play the lab's streams: Firefox does not start on the macOS host, and Playwright's Linux WebKit is unreliable. There are two bad ways to handle that: a red job nobody can act on, and a quiet `test.skip()` that turns a regression into a green build.

**Decision.** The decision is data-driven and explicit. `pickStream(capabilities, kind, protocol)` returns the stream of the first flavour that decoded in every attempt, or `null`. For `null`, `explainNoStream` builds the skip reason from the same data: engine and version, each candidate flavour with `passes/attempts`, the failing stage, the error text, and whether `isTypeSupported` claimed support. The matrix lists every gap with symptom, evidence pointer and consequence, computed with the same functions. The shared test fixture (phase 3) must skip only with that reason. A spec that fails where no gap is documented is a bug, and a launch failure is reported as a failure of the environment, not as a skip. Because the probe keeps running (in CI, on demand), a fixed upstream build changes the matrix instead of staying hidden behind a skip. `pickStream` also accepts `kind: 'live'` (the brief names `'vod'`): the live stream is the same flavour, and the same rule applies.

**Alternatives considered.** Hand-written `test.skip(browserName === 'webkit' && os === 'linux')` (invisible drift, no evidence, no reason text). Excluding the engine from CI (hides the gap). Retrying until green (hides flakiness). Treating an intermittent engine as "flaky, tolerate failures" (the flake gate is for the lab's own tests, not for an engine that cannot play).

**Consequences.** Specs depend on a capability result at run time: a probe in a worker fixture, or the committed JSON of the environment (phase 3 chooses). A flaky probe would make specs skip at random, which is why attempts repeat, processes are fresh, and an environment's result is committed. The skip reasons are long on purpose.

**Defending it.** "A skip is a statement about the product, so it has to carry evidence. The reason names the engine, the flavour, how often it failed, at which stage, and what the browser claimed, and the same data is in the generated document."

## ADR-035: The matrix is generated from committed per-environment JSON, validated and checkable

**Context.** A compatibility document written by hand is a claim: it drifts, and nobody can tell which run it came from. Every number in this repository has to come from a real run and carry its environment, date and commit.

**Decision.** The tool writes one file per environment, `docs/results/codec-matrix/<envId>.json` (`detectEnvId()`): OS, kernel, CPUs, Node, Playwright and ffmpeg versions, the exact command, date, the commit and whether code differed from it (documentation and generated results do not count, and the checkout is read before the browsers run), per engine the version, user agent, claims, native HLS answers and API availability, and per case every attempt. `npm run codec-matrix -- --render` regenerates `docs/CODEC_MATRIX.md` from all of them, deterministically (no timestamp of its own); `-- --check` fails when the document is stale. The reader validates what it renders: counts, reliability and failure summary must agree with the raw attempts, stages must be known, the file must be named `<envId>.json`, and a broken file is an error, never skipped (a missing environment would be a silent gap). Partial runs (`--cases`) must be written elsewhere (`--out`), so they cannot overwrite an environment's full result. Supplementary runs, such as the N=20 spot check, live in `docs/results/codec-matrix/spot-checks/` and are not rendered.

**Alternatives considered.** Hand-written Markdown. One JSON for all environments (every CI job would conflict on it). A database or an artifact store (not reviewable in a pull request). Rendering at build time without committing the document (the evidence would not be in the repository a reviewer clones).

**Consequences.** Tens of kilobytes of JSON per environment; a change to the renderer changes the document's bytes (visible in a diff, caught by `--check`); schema changes need a `schemaVersion` bump. Intermittent cells differ between runs. The validation stops accidents and hand-edited cells; it cannot stop someone who rewrites the counts and the attempts together.

**Defending it.** "The document is a function of files that say where, when and on which commit they were measured. If a cell looks wrong, the raw attempts are one click away, and re-running a case reproduces it: I re-ran two cases per environment, and the deterministic cells came back identical while the intermittent Linux WebKit cells stayed intermittent with different counts."

## ADR-036: `docker:pw` reproduces the Linux environment on a macOS host: pinned image, host user, per-checkout volume

**Context.** Playwright's Firefox does not start on the macOS development host, and CI is Linux, so a developer needs the Linux environment locally, with the repository mounted and without the container's Linux `node_modules` overwriting the host's macOS ones. The image has no ffmpeg.

**Decision.** `tools/docker/pw.sh` runs any command in `mcr.microsoft.com/playwright:v<version>-noble` with `--ipc=host` (Chromium needs shared memory), `--cpus` (default 4), `--init` (reaps browser processes) and the checkout at `/work`. The tag is pinned to the `@playwright/test` version: the script refuses to run when they differ (exit 3), and a unit test fails when `package.json`, the lockfile and the script disagree. `node_modules` lives in a named volume derived from the checkout path, so a worktree has its own; `npm ci` runs inside the container when the volume is empty or its stamp (lockfile hash, the image's Node version, architecture) changed, serialised with `flock`. The container starts as root only to hand the volume to the host user, then continues as the host's uid and gid (`setpriv`, which needs no passwd entry), so files written into the repository (`docs/results`, `.cache`) belong to the host user; `HOME` is `.cache/docker-home`. `PB_ENV_ID` and a few other variables pass through, and the host's commit and dirty flag are handed in because a worktree's git directory is outside the mount. `--dry-run` prints the docker commands (how the script is unit-tested without Docker) and `--clean` drops the volume. The container is named and removed on exit and on INT or TERM.

**Alternatives considered.** Bind-mounting the host's `node_modules` (native binaries differ per OS; esbuild would break). A custom image or a devcontainer (one more thing to build and keep in step with the pin). Running as root (root-owned files on a Linux host, and unprivileged browsers are the common case). `--user` alone (a fresh named volume is root-owned, and `HOME` is unwritable). `docker compose` (more moving parts for one command).

**Consequences.** The first run per checkout installs the dependencies (about 15 s here). The image's Node (24.x) differs from the host's (22.x); it is recorded in every result. This host is arm64: an x64 Linux environment is a different environment id and is not covered. Two first runs at once in one checkout are serialised, not parallel. The script is bash (no Windows). `os.cpus()` inside the container reports the VM's CPUs; the container's limit is recorded separately.

**Defending it.** "One command, the same image as CI, and nothing the container writes is owned by root. The pin is checked by the script and by a test, because the silent failure mode is new tests in an old browser."

## ADR-037: Probe media: tiny ffmpeg test patterns, reproducible bytes, content-addressed, generated on the host

**Context.** The probe needs valid MP4 and WebM with every codec of interest, small enough to fetch instantly, with no third-party content, and the same bytes in every environment, or results would not be comparable.

**Decision.** `src/lab/probe/media.ts` generates nine files from `testsrc2` (640x360, 30 fps) and `sine` (48 kHz mono), 4 s each: VP9 (MP4 and WebM), VP8, H.264 Baseline, AV1, HEVC, AAC, Opus (MP4 and WebM). MP4 is fragmented (`empty_moov+frag_keyframe+default_base_moof`; audio every 2 s), a keyframe is forced at 0 s and every 2 s (the same structure as the lab's 2 s segments), VP8 and VP9 use `-deadline good -cpu-used 4` with no look-ahead and no alt-ref frames (see the amendment under Consequences). The ffmpeg arguments are the recipe, and the SHA-256 of the recipe names the cache directory (`.cache/probe-media/<12 hex>/`): a changed recipe can never be mistaken for an old cache, and generation is idempotent. The files are byte-reproducible (`bitexact` flags and single-threaded encoders; SVT-AV1 needed `lp=1` before two runs agreed, which a unit test now guards), and the manifest records each file's SHA-256 and the ffmpeg version, which the results copy. A cache is verified (sizes, hashes) before every use, and generation goes into a staging directory renamed into place, so concurrent runs are safe. The Playwright image has no ffmpeg, so the container reuses the files the host generated into the mounted repository; with no cache and no ffmpeg the tool says so and names `--media-only`.

**Alternatives considered.** Committing the media (binary blobs in a source repository for something a command regenerates). Generating media in the page with WebCodecs or MediaRecorder (different codecs and containers than the lab streams). Using the lab's own streams from the media pipeline (a phase-2 dependency, and much larger).

**Consequences.** ffmpeg is needed once, on a host. The bytes depend on the ffmpeg build (recorded: 9.0.2 for the committed results). Whole-file appends, not segment by segment (ADR-030). HEVC is encoded without B-frames, so that its first presentation time is 0 and the buffered range starts at 0.

**Amendment (found by a failing unit test, not by reading the code).** The first recipe encoded VP8 and VP9 with `-deadline realtime -cpu-used 8`. libvpx's real-time mode adapts its work to how long the encode is taking, so the bytes depend on how busy the machine is: `v-vp8.webm` had four different SHA-256 values in four runs of the unit suite at a load average of about 20 (it passed alone, and failed about three runs in four under load). The claim above, "byte-reproducible", was therefore false for VP8 and VP9. The recipe is now the one the lab's own streams use (`src/server/media/specs.ts`, ADR-045): `-deadline good`, a fixed `-cpu-used 4`, `-lag-in-frames 0`, `-auto-alt-ref 0`, one thread (and `-row-mt 0` for VP9). The recipe changed, so the recipe hash changed, so a new cache directory is used; the four committed results in `docs/results/codec-matrix/` were produced with the earlier recipe (`media.specHash` 45d1d26cfa75…) and still say so, which is what that field is for. The codec verdicts are not expected to depend on the encoder's speed setting (profile, bit depth and chroma format are unchanged), but that is an expectation until each environment has been re-run with the new recipe; the outcome is recorded below when it has been. The determinism test was not weakened: it still compares every file from two independent generations.

**Defending it.** "Test patterns I can regenerate, with hashes in the results, so anyone can check that two environments played the same bytes. One of them turned out not to be reproducible under load; the unit test caught it and I fixed the recipe instead of loosening the test."
