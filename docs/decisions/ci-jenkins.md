# The Jenkins merge gate decisions (ADR-115 to ADR-119)

Architecture decision records for the second CI system of the lab: the [`Jenkinsfile`](../../Jenkinsfile), the compose project that runs it on a laptop ([`docker-compose.yml`](../../docker-compose.yml) and [`jenkins/`](../../jenkins/README.md): a controller configured as code and a Linux agent built on the Playwright image), the tool that writes the evidence of a build ([`tools/jenkins-evidence.ts`](../../tools/jenkins-evidence.ts)) and the evidence itself ([`docs/results/jenkins`](../results/jenkins)). The GitHub Actions half of the same merge gate has its own records (ADR-110 to ADR-114).

**Where the numbers come from.** One machine: an Apple M2 Pro, macOS, Docker Desktop with a Linux arm64 VM of 12 CPUs and 8 GB that **other work shared** (containers of other jobs came and went next to every build here: during the first full build `docker stats` samples, taken every ten seconds, saw seven of them, which together used up to about 7 of the 12 CPUs at one sample). Jenkins 2.580.2 (LTS) with 74 pinned plugins, the agent on `mcr.microsoft.com/playwright:v1.64.1-noble` with Node 24.22.1, npm 11.19.1, Ubuntu's ffmpeg 6.1.1-3ubuntu5 and OpenJDK 21.0.12.1 (the versions the builds printed, in [the evidence](../results/jenkins/build-3.json)), Chromium 156.0.8078.4, Firefox 157.0 and WebKit 27.2, on 2026-11-04, with the files as committed on the branch `p4/jenkins`. Every build ran once: the durations below are single observations on a busy machine, not a benchmark. Nothing was measured on a GitHub runner, on x64 or on a macOS agent. The merge gate had three specs per engine when these builds ran (PB-ENV-001, PB-VOD-001 and PB-VOD-002; the throttled project runs only PB-VOD-001), so the merge stage is short here and will grow with the suite.

## ADR-115: The stages are the `npm run gate:*` scripts, and the Jenkinsfile decides nothing

**Context.** The merge gate runs in two systems, GitHub Actions and Jenkins, and the resume line is about both. Two pipelines that each know what "static" or "merge" means will drift: a flag added to one, a check dropped from the other, and from then on a pull request can be green in one and red in the other for no reason a person can name. [TEST_STRATEGY.md](../../TEST_STRATEGY.md) section 6.1 already names the gates by script (`gate:static`, `gate:unit`, `gate:merge`, later `gate:perf`, `gate:flake`, `gate:triage`), and `package.json` is where each script says what it runs. What a pipeline still has to do for itself is plumbing: check out, install, give each job its own port, keep the reports, clean up.

**Decision.** Every line of the [`Jenkinsfile`](../../Jenkinsfile) that checks something is `sh 'npm run <script>'`, one per line: `gate:static`, `gate:unit`, `gate:merge -- --project=<engine>` with `CI=true` (the variable GitHub sets, which makes Playwright retry once and use two workers). Four stages sit before the engines, in one workspace: `Install` (`npm ci`, and the version of each tool on the agent, printed as `tool-version <name> <text>` so that the evidence reads them from the log), `Static`, `Unit` and `Streams` (`npm run generate:streams`, ADR-118). Then `Merge gate` runs four branches in parallel, one per Playwright project: `chromium`, `firefox`, `chromium-cpu4x` and `webkit` (Linux WebKit, an experimental engine: [CONTRACTS.md](../CONTRACTS.md) section 7.3, which gates like the others). The options are the ones the setup promised: timestamps, ANSI colour, a 40 minute build timeout, no concurrent builds (two builds would share one stream volume and one set of ports) and a log rotator. A later gate is one more block with its own `sh 'npm run gate:<name>'` line; none exists for `gate:perf`, `gate:flake` or `gate:triage` because their scripts do not run yet, and [`tests/unit/jenkins/lab.test.ts`](../../tests/unit/jenkins/lab.test.ts) fails if the Jenkinsfile calls a script `package.json` does not have, or a project `playwright.config.ts` does not define. A parity test against `.github/workflows/ci.yml`, the other half of the setup, reads the same lines: that is why each of them is on one line.

**What differs from GitHub, on purpose or not.** (1) The runtime is the Playwright image's Node 24.22.1 and npm 11.19.1, where `actions/setup-node` installs Node 22 (`.nvmrc`); `engines` allows both, and npm 11 prints a warning about install scripts that npm 10 does not (it changes nothing: esbuild takes its binary from its platform package). (2) WebKit is Linux WebKit here and macOS WebKit there: no container is a macOS agent, and the setup does not pretend (README). (3) The environment id is `jenkins-linux-arm64` ([`src/shared/env.ts`](../../src/shared/env.ts): `JENKINS_URL` is set), for which no codec probe is committed, so nothing is a documented gap and PB-ENV-001 records `no committed probe result` as its evidence; the performance baselines of the later gate will need their own. (4) `static` and `unit` are parallel jobs in GitHub and sequential stages here: one agent, and the cheap check goes first. (5) The unit stage runs with `VITEST_MAX_WORKERS=2` (ADR-116). (6) `junit allowEmptyResults: true` is in the post step and finds nothing: the lab's reporters are `list`, `json` and `html`, none writes JUnit XML, and what Jenkins archives instead is `reports/<engine>/playwright.json` and the HTML report. Adding Playwright's `junit` reporter to `playwright.config.ts` is what would fill Jenkins' test tab; that file is not this setup's to change.

**Alternatives considered.** One script, `ci.sh`, called by both systems (a layer between package.json and the pipelines that the npm scripts already are). Stage commands written in Groovy, or a shared pipeline library (the drift this decision exists to prevent, in a language the other half cannot read). A `matrix` block over the engines (shorter, but each step becomes `--project=$PROJECT` and each branch's port and report path has to be computed from the axis value; four literal branches are longer and a script can read them). Running everything in one `sh` (no stage view, no per-stage failure).

**Consequences.** Changing what a gate checks never touches the Jenkinsfile. The four engine blocks are near copies, which is the price of lines a script can parse; the unit test checks that the copies differ where they must (port, report paths, project). A gate that exists only in one system is visible as a difference between two short files.

**Defending it.** "I did not write a Jenkins pipeline, I wrote a thin shell around the scripts the repository already has, and a test that fails when the shell mentions a script that is not there. When GitHub's job list changes, the Jenkins list changes by one block, and what each block checks cannot differ."

**Update (the flake gate, ADR-174 in [ci-flake.md](ci-flake.md)).** `gate:flake` has its stage now, `Flake`, after `Merge gate`; `gate:perf` and `gate:triage` are the ones still without. Its lines are `sh 'npm run gate:flake -- --store file --runs reports/flake'`, and the same with `--record` for a build of `main`: one line each, read like the others. Two pieces of plumbing came with it that the first version did not need: each engine's `gate:merge` sits in a `catchError`, so that a red engine does not skip the stage after it, and each branch stashes its flake run files before its workspace is wiped.

## ADR-116: A controller with no executors, a Linux agent built on the Playwright image, and two engines at a time

**Context.** The browsers need the libraries, fonts and codecs of the Playwright image, which the lab already uses for Firefox and Linux WebKit on a Mac (`npm run docker:pw`, [codecs.md](codecs.md) ADR-036). A Jenkins controller that runs builds itself runs user code next to its own secrets, and a build that has no agent should not quietly run somewhere else. The Docker VM has 12 CPUs and 8 GB shared with other work, so the stack has to be small, and the four engines of the merge gate must not clobber each other: each service writes `dist/player`, each run writes `reports/` and `test-results/`, and the executors of one agent share one network namespace.

**Decision.** The controller ([`jenkins/controller`](../../jenkins/controller)) has `numExecutors: 0`: builds run on the agent or not at all. The agent ([`jenkins/agent`](../../jenkins/agent)) is `mcr.microsoft.com/playwright:v1.64.1-noble` (the tag must equal the pin of `@playwright/test`: a unit test checks it, and checks it against `tools/docker/pw.sh`) plus `openjdk-21-jre-headless` for the Jenkins agent and Ubuntu's ffmpeg, the one the media pipeline is verified against ([media.md](media.md)). It runs as uid 1000 (like the controller's user, so that the connection secret it reads, mode 0600, is readable), downloads `agent.jar` from the controller at start (the two cannot disagree about the remoting version), and connects over WebSocket on the port of the UI: no agent port is open (`slaveAgentPort: -1`), and the only published port of the project is 4700 on the loopback interface. The container has `init: true` (a small init process reaps the processes browsers leave behind), `ipc: host` (shared memory for Chromium and Firefox, which the image's documentation asks for), `cpus: 3` and `mem_limit: 4g`; it has two executors. The Jenkinsfile has `agent none` at the top, nests `Install`, `Static`, `Unit` and `Streams` in one stage with one agent (one workspace, one `npm ci`), and gives each engine its own `agent { label 'playwright' }`: its own executor, its own workspace (`playback-proof`, `playback-proof@2`), its own `PB_PORT` (4601 to 4604) and its own `reports/<engine>/` paths (`PLAYWRIGHT_JSON_OUTPUT_FILE`, `PLAYWRIGHT_HTML_OUTPUT_DIR`, which Playwright 1.64.1 reads before the config's own values). With two executors and four engines, two run while two wait. The stage view counts the wait inside the stage's duration, so the evidence takes it apart (`waitedMs`).

**What was measured.** *Parallel or one after the other* (builds 3 and 4, [`build-3.json`](../results/jenkins/build-3.json) and [`build-4.json`](../results/jenkins/build-4.json)): with two executors the merge stage took 54.5 s of wall-clock in build 3, while the four engines together ran 101.0 s of their own work and waited 57.8 s for an executor (each engine's run, checkout and `npm ci` included: `chromium` 27.4 s, `firefox` 29.4 s, `chromium-cpu4x` 19.5 s, `webkit` 24.7 s). With one executor, build 4, the same four ran one after the other: 104.5 s of wall-clock for 103.0 s of work (19.7 s, 28.7 s, 24.5 s and 30.1 s; the 144.3 s of waiting is each engine waiting for the ones before it). Two executors halved the wall-clock of the stage (54.5 s against 104.5 s), and two engines at once did not make each other slow in a way that shows (101.0 s of work against 103.0 s). These are single runs, on a VM that other jobs shared: the second comparison says only that the concurrency was not expensive here, and the first says what it bought, on a merge suite of three specs per engine that will grow. *Memory and CPU* (`docker stats` every ten seconds during build 3): the agent peaked at 2.1 GiB during the merge stage (two Playwright runs of two workers each, a quarter of the VM's 8 GB; the limit is 4 GiB), used its whole quota of 3 CPUs there (peak 314 %), and the controller stayed at about 750 MiB of its 1.5 GiB. *The Unit stage and the quota*: with the repository's own limit of four Vitest workers on this agent, build 2 failed in `Unit`, in `tests/unit/probe/media.test.ts`: the test that generates the probe media twice and expects the same bytes got another VP8 file the first time. The same file passed three times alone on the idle agent (68 to 77 s) and failed again under eight busy loops. The likely cause is that libvpx's realtime mode adapts to the time a frame takes to encode, so that the bytes depend on the load of the machine: the file changed with the load and with nothing else, but this was not traced into libvpx. The test and the recipe (`-deadline realtime`, `src/lab/probe/media.ts`) are the lab's, not this setup's. With two workers the whole unit suite passed twice on the agent (116 s and 68 s, with other jobs running on the VM) and in builds 3, 4 and 6 (105 s, 120 s and 109 s). Build 5, with two workers, failed in `Unit` as well, in another test: `tests/unit/server/static.test.ts` ("releases the file of every download that the client abandons" counted 84 open descriptors where its calibration expects at least 120 while 40 downloads stall), while the host's load average was about 18 on 12 cores. So the cap of two workers (`VITEST_MAX_WORKERS=2` in the Jenkinsfile, which Vitest reads after the config) is a mitigation of this setup's own contribution to the load, not a cure, and four workers of ffmpeg-heavy tests do not fit a quota of three CPUs anyway: two tests of the unit suite depend on how busy the machine is, and the machine is shared. They are reported, not changed here.

**Alternatives considered.** Building on the controller (no isolation, and a missing agent would go unnoticed). Docker in Docker or the host's Docker socket mounted into the agent (a build with the socket is root on the VM; the Playwright image is already the environment). The `jenkins/inbound-agent` image with browsers installed by `npx playwright install` (about a gigabyte of browsers per build, or another image to keep in step with the Playwright pin; the image the lab uses elsewhere has them). One agent container per engine (four JVMs and four sets of limits; the per-engine CPU share would be bounded, but 3 CPUs would become 4 containers' worth of idle). Four executors on one agent (eight browsers on three CPUs: every test gets slower and the 45 s test timeout has less margin; not run, because the VM is shared). One executor and four steps in one stage (one workspace and no port arithmetic: it is the sequential case, measured below).

**Consequences.** The merge stage's wall-clock is bounded by the agent's quota and by the executors, not by the number of engines; adding an engine adds a block and, past a point, an executor and CPUs. A build with the agent offline does not fail: it waits for a node, and the README says how to see that. The agent holds no credential of the controller (ADR-117). Concurrent builds are disabled, so the ports and the volume have one user.

**Defending it.** "The controller cannot run my code, the agent is the image I already trust for the browsers, and the number of executors is a measured choice with a reason: two at a time used the whole CPU quota and a quarter of the memory, and four would have used the same CPUs with twice the browsers."

## ADR-117: The controller is code: pinned plugins, Configuration as Code, a job defined in the file, a secret handed over through a volume

**Context.** A Jenkins that someone configured in the browser cannot be rebuilt, reviewed or diffed, and "I ran Jenkins" is worth little if the next person cannot. The pieces that usually go wrong are the plugin set (Jenkins resolves a dependency to the newest version on the day of the build), the admin password (it ends up in a repository, a log, or a script), the way an inbound agent gets its secret (the controller derives it after it starts), and the job (a click).

**Decision.** [`jenkins/controller/Dockerfile`](../../jenkins/controller/Dockerfile) starts from `jenkins/jenkins:2.580.2-lts-jdk21` and installs [`plugins.txt`](../../jenkins/controller/plugins.txt) with `jenkins-plugin-cli`: 13 plugins, 74 with their dependencies, **all pinned** (the file explains how to move to another core; the evidence of every build lists the versions the controller loaded, in the format of that file). `casc.yaml` is copied into the image and defines the security realm (one local user, no sign-up, no anonymous read, the standard crumb issuer, no usage statistics), `numExecutors: 0`, the agent node `playwright-1` with the label `playwright` and two executors (the executor count comes from `AGENT_EXECUTORS`, default 2), the location URL, and the job `playback-proof`, a pipeline job written as a Job DSL script in the same file: SCM `file:///repo` (the repository, mounted read-only into both containers), the branch from `PB_BRANCH` (default `main`), script path `Jenkinsfile`, lightweight checkout (the controller reads only the Jenkinsfile; the agent clones). The admin user comes from `JENKINS_ADMIN_ID` and `JENKINS_ADMIN_PASSWORD` in `.env`, which is git-ignored; [`jenkins/init-env.sh`](../../jenkins/init-env.sh) writes it with a random password (mode 600) without printing it, and the compose file refuses to start without one (`${JENKINS_ADMIN_PASSWORD:?...}`; no default). The agent's connection secret is written by one start-up script (`init.groovy.d`, which runs after Configuration as Code has created the node) into a volume that the agent mounts read-only, mode 0600, and passed to `agent.jar` as `-secret @file`: it appears in no command line, no log and no environment, and the agent needs no credential of the controller. Two settings exist because the job reads a local path: `-Dhudson.plugins.git.GitSCM.ALLOW_LOCAL_CHECKOUT=true` (the git plugin refuses a `file://` repository without it) and `git config --system safe.directory /repo` in both images (the mount belongs to the host's user). `useScriptSecurity: false` is set for the Job DSL script, which comes from this file and from nobody else.

**Alternatives considered.** Configuring in the UI and committing a backup (a backup is a result, not a source). Pinning only the direct plugins (a later build resolves other dependencies: the first resolution already picked `json-api` 20260814 and `commons-text-api` 1.15.0). The admin password or an API token passed to the agent so that it can fetch its secret over HTTP (it works, and puts the admin's credentials into the container that runs the builds). A fixed secret in `.env` (it cannot be: the secret is derived from the controller's own key). A Multibranch pipeline or webhooks (a real SCM; ADR-119). The `docker` or `kubernetes` cloud plugins (they create agents per build; the lab wants one agent that anyone can read).

**Consequences.** Rebuilding the controller from the repository is `docker compose up -d --build`; anything changed in the UI is gone at the next recreate, by design. The Jenkins home is a named volume, so builds survive a restart and `docker compose down -v` is a factory reset. A new Jenkins volume means a new agent secret: the controller rewrites the file at start and the agent, which restarts when it cannot connect, picks it up. The plugin lock must be refreshed by hand with the core (the file says how). The script-security exception and the local-checkout switch are acceptable for a loopback-only lab with one repository mounted read-only and are not what a production controller would do.

**Defending it.** "Nothing about this Jenkins was typed into a browser. I can delete the volumes and have the same controller, the same plugins, the same job and a new password from the repository, and the password and the agent secret are never in a file that is committed, a command line or a log."

## ADR-118: One named volume holds the generated streams, shared by every build; the generator is told where it is

**Context.** The merge gate plays generated media: five streams, 282 files, 43.5 MB of fragmented MP4, WebM and a CENC-encrypted stream, produced by ffmpeg ([media.md](media.md)). Generating them took 175.6 s on this agent in the first build (per stream: 75.3 s, 19.1 s, 43.6 s, 32.4 s and 4.4 s), which is longer than the whole merge stage. The cache is content-addressed (`<cache>/<specHash>/<streamId>`, a directory exists only when complete) and the generator is idempotent, and the byte equality between two ffmpeg builds is explicitly not promised (media.md). Each build deletes its workspaces, and the four engines work in four of them.

**Decision.** A named volume, `streams-cache`, is mounted at `/cache` on the agent, and `PB_CACHE_DIR=/cache/streams` is the same for every stage of the pipeline, so the service of each engine serves from it. The `Streams` stage runs once, before the parallel branches, as `npm run generate:streams -- --cache-dir "$PB_CACHE_DIR"`. The argument is not decoration: `tools/generate-streams.ts` reads `--cache-dir` and does not read `PB_CACHE_DIR`, which only `npm run serve` reads, so without it the generator would fill the workspace's `.cache/streams`, the service would look in the volume, and every engine would stop at "stream ... is missing" (the lab's own check in `tests/e2e/support/global-setup.ts`). A first run on an empty volume generates; any later run finds every stream complete and returns in a few seconds. `disableConcurrentBuilds` and the single generator stage mean the volume has one writer at a time; the branches only read it. `npm` has a second volume (`npm-cache`, the agent's `~/.npm`), which saves little when the network is fast (`npm ci` took 5 s cold) and matters when it is not. [`build-3.json`](../results/jenkins/build-3.json) has the cold stage; in build 4, on the warm volume, `Streams` took 0.7 s.

**Alternatives considered.** Generating inside each engine's workspace (four times the work, and the numbers of media.md say what that is). `stash` and `unstash` of the streams between stages (43 MB copied per branch per build, and a build that dies in `Streams` leaves nothing). A bind mount of the host's `.cache/streams` (a macOS file-sharing mount for several hundred files read by four services, and the host's ffmpeg 9 writes other bytes than Ubuntu's ffmpeg 6.1: two environments in one cache). Baking the streams into the agent image (a rebuild for every change of a spec, and the image would carry 43 MB of generated data that no longer match their `stream.json` when the generator changes).

**Consequences.** The first build after `docker compose down -v` pays the generation; every other build does not. The volume belongs to one ffmpeg: another ffmpeg writes other bytes under the same content address when the generator version has not changed, which is why it is mounted only into this agent. Old spec hashes stay in the volume until it is removed. A missing or damaged stream stops the run before the first test, with the instruction that fixes it.

**Defending it.** "Generation costs longer than the tests it feeds, so it is paid once per volume, not once per build or once per engine. And I found, by reading the generator, that it ignores the variable the service obeys: the pipeline passes the directory explicitly rather than relying on a convention that two tools do not share."

## ADR-119: What a local Jenkins proves, and what it does not

**Context.** The line on the resume says the suites ran as merge gates in Jenkins and GitHub Actions. A controller on a laptop is not a production CI: it has one agent, one user and no webhook. The honest question is what it can be trusted to show.

**Decision.** The setup claims three things and backs each with evidence in [`docs/results/jenkins`](../results/jenkins): **the pipeline definition runs**: builds 3 and 4 went green through every stage (the table is in the "Evidence" section of the [README](../../jenkins/README.md) and in `build-3.json` and `build-4.json`: install, static, unit, streams and the four engines, three tests each except the throttled project's one, all passed, none flaky, on the commit each build names); **the stages are the same gates**: by construction (ADR-115) and by the unit test that checks the Jenkinsfile against `package.json` and the Playwright config (a parity test against the workflow file is the other half's); **the gate can fail, in the right place, and says so**: builds 2 and 5 turned red in `Unit` on tests whose result depends on how busy the machine is, skipped the stages after it and kept their statuses straight (`NOT_EXECUTED`, not a second failure), and build 6, the planned negative run, turned red in `Merge gate`: on a throwaway branch of a copy of the repository an expectation of PB-VOD-002 was made false, and `chromium`, `firefox` and `webkit` went red, the throttled project (which does not run that test) stayed green, each failing test ran twice, and the six diagnostics of [CONTRACTS.md](../CONTRACTS.md) section 7.2 are in the archived JSON report of each engine for both attempts, next to the screenshot, the error context and the trace. The evidence tool records where a build was meant to turn red (`--expect-stage`) and whether it did (`asExpected`): build 5, which was meant to be build 6, is `asExpected: false`. It does **not** claim: that GitHub and Jenkins agree on every pull request (no pull request ran here); that the durations are those of a real runner (Docker Desktop's VM on a shared Mac, arm64); anything about macOS WebKit (the `webkit` stage is Linux WebKit, experimental); anything about performance or flake (those stages do not exist until their scripts do); webhooks, pull-request checks, branch protection, credentials for a real repository, high availability, backups or access control beyond one admin on the loopback interface.

**Alternatives considered.** Calling it "Jenkins in CI" (it is Jenkins on a laptop). Faking a macOS agent or a webhook so that the table has no gaps. Leaving the failing builds out of the evidence (builds 2 and 5 are useful ones: real defects of the unit suite, found by the gate it was built to be, and a first attempt at the negative run that shows why `asExpected` looks at the stage). Breaking the spec in the checkout (the negative run never touches it: the copy is a bare repository in a scratch directory, the job reads a branch of it, and restoring is pointing the job back at the real branch).

**Consequences.** The evidence contains two red builds that nobody planned, and says so in their labels. The negative run is part of the setup and can be repeated from the README. The unit stage is the weakest link of the pipeline on a loaded machine: five builds ran it, three passed and two failed on a different test each; until those two tests are made independent of the machine's load (the owner's call), a red `Unit` on this agent is read with the test's name in hand. When the e2e suites grow, the merge stage grows with them and the numbers above are no longer the numbers; the evidence files are dated and name the commit they ran.

**Defending it.** "I can show you the Jenkinsfile, start the stack on your machine, and point at the builds: two green ones with every stage timed, one red one I produced on purpose in the merge stage with the failure attachments archived, and two red ones the gate produced by itself, on tests that turned out to depend on the load of the machine. What I cannot show is production: no webhook, no macOS agent, one agent on a shared laptop, and the README says so."
