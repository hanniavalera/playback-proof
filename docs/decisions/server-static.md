# Static serving decisions

Architecture decision records for the module that serves the built player page (`/player/` from `dist/player`): [`src/server/static.ts`](../../src/server/static.ts), tested by [`tests/unit/server/static.test.ts`](../../tests/unit/server/static.test.ts) (ADR-055 to ADR-057). The repository is public and a web server that serves files is the classic place for a path-traversal hole, so this module is small and its tests are written as an attack, not as a demo. Each record can be defended in a review: the situation, the choice, what was rejected, what it costs, and how I would argue for it. The lab-wide decisions this builds on are in [DESIGN_DECISIONS.md](../DESIGN_DECISIONS.md); the URL layout it serves is in [CONTRACTS.md](../CONTRACTS.md), sections 3 and 4.

The numbers quoted below are from runs on macOS arm64 with Node 22.11 (`npx vitest run tests/unit/server/static.test.ts`: 190 tests in under a second). The suite was not run on Linux.

## ADR-055: A request path is resolved, resolved again through the file system, and checked against the real root; it is never cleaned

**Context.** The service has to hand a browser a few files from `dist/player`. The usual ways this goes wrong are well known, and each needs a different fix when the defence is "clean the string": removing `../` is bypassed by `....//` and by encodings; `path.join(root, request)` still walks out of the root through `..`, and `path.resolve(root, '/etc/passwd')` silently discards the root; `candidate.startsWith(root)` accepts `/srv/player-evil` as "inside" `/srv/player`; a symlink inside the root can point anywhere; a NUL byte can truncate a name in a lower layer; a backslash is a separator on one platform and a letter on another. A filter that lists bad inputs has to be right about every one of them, and a reviewer cannot tell by reading it whether the list is complete.

**Decision.** The module does not try to recognise a hostile path. It computes what the path means and checks where that lands, in this order, for every request:

1. Decode once and refuse what cannot be a file name ([ADR-056](#adr-056-a-path-is-decoded-exactly-once-and-what-decoding-produces-is-a-name-400-for-what-cannot-be-a-path-404-for-everything-else)).
2. Take the real path of the root (`realpath`, on every request, because the player is built later and the root may be a symlink) and resolve the request against it with the leading slashes removed, so that an absolute path cannot replace the root.
3. Require the result to be strictly inside the real root. The check is a prefix **that includes the separator**.
4. Take the real path of the result (every symlink on the way is followed) and require it to be inside the real root again. A symlink that leaves the root is a 404; one that stays inside is served as the file it points to; one that leaves and comes back is judged by where it lands.
5. Refuse any dotfile or dot-directory segment, in the requested path and in the real path (`.env`, `.git/config`, and an in-root symlink to either).
6. Serve only a regular file. A directory means its `index.html`, which goes through steps 3 to 5 like any other path (an `index.html` that is a symlink to a secret is a 404), and never a listing. A FIFO or a device is a 404, because opening a FIFO would wait for a writer forever.
7. Open the real path with `O_NOFOLLOW`, take the size from the opened handle (`fstat`), and stream that handle.

A refused escape and a missing file answer identically (404, same body), so the answer is not an oracle for what exists outside the root. Malformed input is 400. Every file-system error (`ENOENT`, `EACCES`, `ELOOP`, `ENAMETOOLONG`, `EMFILE`...) is "nothing to serve" and a 404: the status set of the module's API has no 5xx.

**Alternatives considered.** Sanitising the string (remove `..`, collapse slashes, replace backslashes): a pattern with a long history of bypasses, because it must anticipate every encoding. Refusing every request that contains a `..` segment outright: simpler to explain and no browser sends one, but then the traversal vectors would all be stopped by the first line of defence and the tests would never reach the prefix check or the symlink resolution, so the lines that matter would be untested; dot segments are therefore resolved lexically (`/player/a/../app.js` is `app.js`) and only an escape is refused. A library (`serve-static`, `send`): well tested, but it brings ranges, ETags and compression the lab does not want ([ADR-057](#adr-057-what-this-module-is-not-and-how-its-limits-were-checked)), it is a dependency, and it would hide the one part of the lab that is the point of this module. A chroot or a container: not available on a developer's laptop.

**Consequences.** There is one place (`check`) that decides, and a mutation of it breaks tests. The decision costs a handful of synchronous metadata calls per request (`realpath`, `stat`); I did not benchmark them, because the lab serves the player page a few times per test and the media goes through another route. The exported `resolveStaticFile(root, mount, urlPath)` is synchronous and is the same code path the server uses, so it can be tested and fuzzed without a socket. Known limits: (1) the check is made on the path at request time, so someone who can **write inside the root** while the server runs can swap a directory for a symlink between the check and the open; `O_NOFOLLOW` closes that for the last path component only, and Node does not expose `openat2(RESOLVE_BENEATH)`. The threat model is a remote HTTP client and a root written only by the build, and this is stated rather than hidden. (2) A hard link to an outside file is a file inside the root; it cannot be told apart. (3) The code was written for POSIX paths. Windows is not supported or tested; I expect the prefix check to refuse a drive letter, but I have not verified it.

**Defending it.** "I did not try to list what a hostile path looks like. I compute where the path lands and check that, twice, once before and once after the file system has followed every symlink, and I make an escape look exactly like a missing file. The test suite is built so that each defence is the only thing standing between one family of vectors and the secret: I weakened each of them in turn and the suite failed (the evidence is in the next record)."

## ADR-056: A path is decoded exactly once, and what decoding produces is a name; 400 for what cannot be a path, 404 for everything else

**Context.** Double decoding is how `%252e%252e` becomes `..`: a proxy decodes, the application decodes again, and a check made between the two is checked against the wrong string. Related traps: overlong UTF-8 (`..%c0%af` is a slash to a lenient decoder), IIS-style `%u002e`, a NUL (`%00`) that ends a name for the layer below, and an encoded slash or backslash that becomes a separator only after the check. `fetch` and `http.request` tidy `..` before the request leaves the client, so a test written with them cannot send the vectors at all.

**Decision.** The mount (`/player/`) is matched against the raw path, so `/%70layer/` is not under it. The remainder is decoded **once** with `decodeURIComponent`, and the result is a file name that is never decoded again, never "normalised until stable" and never fed back into the URL machinery. The query string is cut off before decoding, never reaches the file system, and is copied only into the `Location` of a redirect (control characters in it are a 400). A request is a **400** when it cannot be a path: a malformed escape (`%`, `%zz`, a truncated multi-byte sequence, an invalid or overlong UTF-8 sequence, `%u002e`), any control character after decoding (NUL, line feed, tab, DEL...), a backslash, or a path longer than 2048 characters. Everything else that is refused is a **404**, double-encoded input included. A redirect (`/player` to `/player/`, and a directory to its slash) is built from the decoded, normalised path and re-encoded, never copied from the request, so it always starts with the mount and cannot become a protocol-relative `//host/`. It keeps the query, because the player page is configured with one.

The decode-once property is tested in the positive direction: the fixture contains a directory literally named `%2e%2e`, and it is reachable by exactly `%252e%252e/inside.txt` and not by `%2e%2e/inside.txt` (which decodes to `../inside.txt`, outside the root). Decoding twice fails that test, and two more.

**Alternatives considered.** Decoding in a loop until the string is stable (it is exactly what turns a double encoding into a traversal). Decoding per segment and refusing an encoded slash (stricter, but the real-path check already covers it, and the strictness would hide the check from the tests). Parsing with `new URL` (it resolves `..` before the server sees it, which is also why the vectors are sent over raw sockets). Answering 400 for every refusal (it would separate "escape" from "missing", which is the oracle this module avoids; 400 is kept for input that is not a path at all).

**Consequences.** A client can tell a malformed request (400) from a missing file (404); that reveals nothing about files. A file whose name is not valid UTF-8 cannot be requested (nothing in a build output needs it). Node decodes the request target as latin1, so a non-ASCII byte that was not percent-encoded does not become the UTF-8 letter; browsers always percent-encode, and the failure is a 404. A literal `%` in a name is requested as `%25`. The 2048-character limit is far above any file name of the build and far below the 16 KiB at which Node's own parser answers 431 before the module is called (checked: a 20,000-character request line gets `431 Request Header Fields Too Large` and never reaches the module).

**Defending it.** "Decoding once is a property I can state and test positively: a file named `%2e%2e` is served at `%252e%252e` and nowhere else. 400 means this cannot be a path; 404 means there is nothing here, whatever the reason, so the status is never a way to ask the server what is outside its root."

## ADR-057: What this module is not, and how its limits were checked

**Context.** This is not a general file server. It serves a handful of small files from the same machine as the browser, in a lab whose measurements (startup time, rebuffering) and whose verdicts must not depend on what a cache, a compressor or a range request did to the player build. A stale player page that a browser kept would be a test that passes against code that is no longer there.

**Decision.** **Out of scope, on purpose:** no `Range` (it is ignored and the whole file is sent with a 200, which RFC 9110 allows), no conditional requests (no `ETag` or `Last-Modified` is sent and `If-*` is ignored), no compression (identity encoding), no directory listing, and no caching: every response, errors and redirects included, carries `Cache-Control: no-store`, together with `Access-Control-Allow-Origin: *` and `X-Content-Type-Options: nosniff` (a script or a style sheet runs only if its type is the right one, so the type table is explicit and an unknown extension is `application/octet-stream`). Only GET and HEAD are served; any other method is a 405 with `Allow: GET, HEAD` before the path is looked at (the CORS preflight, `OPTIONS`, is the router's job, CONTRACTS section 4). **In scope, because a file server that cannot do it is a hazard:** the file is streamed with `pipeline`, so a client that goes away destroys the stream and closes the file; the body is capped at the declared `Content-Length`; and a read that comes up short (the file was truncated by a rebuild) fails the pipeline **before** the response is ended, which drops the connection instead of leaving a keep-alive client waiting for bytes that never come. After `end()` it would be too late: the response has already let go of the socket.

**How it was checked.** All of it on the machine named above; the suite starts its own servers on port 0 and sends the vectors over `net.connect` so that the server sees exactly what was written.

- **Vectors.** 71 request targets in one table (26 expected to be 400, 45 expected to be 404), plus 3 more through a second mount whose root is a symlink, plus 1 beyond the parser limit (Node answers 431 itself): `..` in plain, encoded, half-encoded, double-encoded and path-parameter forms, absolute paths, NUL, line feed, tab, DEL, raw and encoded backslashes, malformed and overlong UTF-8 escapes, `%u` escapes, look-alikes (fullwidth dots, the division slash, `..` plus a space), the sibling directory whose name starts with the root's name (plain, encoded, and through a symlink), and lengths from 1,800 to 10,000 characters. Each one is asserted four ways: the exact status, no secret in the response (body or headers), the module's own answer is the same status (so the HTTP parser did not turn the vector away first), and `resolveStaticFile` returns `null`. A secret outside the root, a file in a directory outside it, and `/etc/passwd` (through a symlink) are the targets. Another 11 targets are dotfiles. A seeded fuzz (6,000 generated paths, made of the pieces above, fixed seed) checks the invariant at function level: a result is `null`, or a regular, non-dot file strictly inside the real root.
- **Symlinks.** Thirteen symlinks in the fixture root: to a file outside (relative and absolute target), to a directory outside, to the parent of the root, to the sibling whose name starts with the root's, to `/etc`, to a dotfile, a loop (two links), a broken link, an `index.html` that is a symlink out, and two that stay inside (a file and a directory). The ones that leave are 404 in every form of request, the ones that stay are served, and one that leaves and comes back is served as a file inside the root. The root itself may be a symlink (served, and still sealed). The decision is made on every request: a file that was served and is then replaced by a symlink to the secret is refused on the next request.
- **Mutations.** Each defence was removed in turn and the suite must fail. Prefix without the separator: 12 tests fail, including the 4 sibling vectors. No `realpath` of the requested path: 11 fail (some wire-level answers stayed 404 only because `O_NOFOLLOW` refuses a symlink in the last path component, which is why every vector is also asserted at function level). Decoding twice: 3 fail. No dotfile rule: 11 fail, the fuzz among them. Backslashes allowed: 4 fail. `pipe` instead of `pipeline` (the classic leak): detected in 5 of 5 runs. No short-read guard: the shrinking-file test fails; no length cap: the growing-file test fails (34,603,008 bytes received for a declared 33,554,432). The leak mutation also showed a defect in my own handle test, fixed: with `pipe`, Node's finalizer closes the leaked `FileHandle` on garbage collection (with the warning `Closing file descriptor N on garbage collection`), which can hide a leak from a descriptor count taken afterwards, so the handle tests now fail on that warning too. A second defect, found while writing the changing-file tests, was a helper that re-paused the socket after every chunk.
- **Handles.** The descriptors of the test process are counted through `/dev/fd`. Five rounds of 40 downloads of a 16 MiB file that stall mid-body and are then abandoned (200 aborted downloads): the count was 18 at rest and 138 while stalled (exactly 3 per download: the file and the two ends of the socket, so the counter does see the files), and no more than 18 after every round, with no handle closed by the garbage collector. HEAD, refusals and redirects (105 requests), a client that is already gone when the response starts (20 requests), and a response that cannot be written (a stub whose `writeHead` throws, with the file already open) leave the count unchanged too.

**Alternatives considered.** `Cache-Control: no-cache` with an `ETag` and 304s (the right answer for a CDN, the wrong one here: it adds a mechanism whose failure modes the lab would have to test and could be fooled by). Precompressed assets and `Range` for media (the media is served by another route, `/s/...`, which the fault engine controls; this module would be a second, uncontrolled way to deliver bytes). A single `fs.readFile` per request (simple, and it would have no handle to leak, but it reads the whole file into memory per request and cannot stop when the client leaves).

**Consequences.** Every request reads the whole file again, which is fine for a few hundred kilobytes and wrong for anything large; `<video src>` pointed at a file under `/player/` would not seek (the player uses MSE and the media route). An extension that is not in the table is sent as `application/octet-stream`, which `nosniff` will make a browser refuse for a script: add it to the table when the build starts to emit a new kind of file. A reader that stalls forever holds a file handle until the server closes the socket; the module sets no timeout of its own, the server that calls it should. A file replaced by another file of the same size while it is being sent is not detected.

**Defending it.** "It is deliberately boring: no ranges, no ETags, no compression, no cache, so nothing between the build and the browser can change the bytes or remember them. The part I would be asked about is the verification, so it is numbers rather than adjectives: 75 request targets over raw sockets, every defence removed once and the suite red each time, and a handle counter that I calibrated first (it saw 120 extra descriptors for 40 stalled downloads) before I believed it when it saw none."
