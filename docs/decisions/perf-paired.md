# The performance gate on shared machines (ADR-178 and ADR-179)

Architecture decision records that follow from the first A/A checks of the committed baselines on GitHub-hosted runners ([results/perf/gha-cross-vm.md](../results/perf/gha-cross-vm.md)). They extend the performance harness of [perf.md](perf.md) (ADR-120 to ADR-129), whose number range is full: these follow the last number in use (ADR-177 in [ci-measure.md](ci-measure.md)). How to run, read and re-baseline: [PERF.md](../PERF.md).

## ADR-178: The CPU model is recorded and said, never judged

**Context.** An environment id names a class of machines, not a CPU: `gha-linux-x64` is whatever GitHub's `ubuntu-24.04` hands out, and the first A/A jobs on it landed on five CPU models (Intel Xeon 8573C and 6975P-C, AMD EPYC 9V45, 9V74 and 7763: 13 jobs, counted from their machine records in [gha-cross-vm.md](../results/perf/gha-cross-vm.md)), while the baseline of `chromium` had been recorded on a sixth, the Intel Xeon 8370C, that none of the 13 jobs ran on. A report that says "startup is 40 % slower than the baseline" without saying that it ran on another CPU than the baseline sends its reader to look for a regression in the code. The baselines were recorded without the model.

**Decision.** The harness records the CPU model of the machine it runs on as **`host.cpuModel`**, in every baseline and every gate report written from now on: `os.cpus()[0].model`, trimmed, its runs of whitespace collapsed. The field is **optional**: the baselines recorded before it existed stay valid and are not recorded again (the loader accepts them, and a test loads every committed baseline), and a machine that does not name its CPU records none. libuv reports the placeholder `unknown` where `/proc/cpuinfo` has no model name, which is what the Playwright container on an Apple-silicon host says, and a placeholder is not a model: it is not recorded, so that "unknown" never differs from a real name.

The gate prints one line in the terminal, in the Markdown (so in the job summary) and in the JSON, **`baseline machine: <CPU model or 'not recorded'>; this machine: <CPU model>`** (`no baseline` where there is none, `unknown` for a machine that does not name its CPU), and, when both are known and differ, a note: *the CPU model differs from the one the baseline was recorded on: a difference in startup of that size may be the machine*. It changes **no verdict, no exit code and no threshold**: a test builds the whole report with and without a difference and compares everything but the machine facts. The A/A summary ([`perf/aa.ts`](../../perf/aa.ts)) lists the CPU model of every pass, counts the distinct models and prints a table of pass, verdict, CPU model, startup median against the baseline median and deviation. It accepts the passes of several jobs (one environment, one profile, one baseline) and says that they did not all run on the same machine.

**Alternatives considered.** Making the CPU model part of the environment id (`gha-linux-x64-epyc-7763`): a runner pool's models are not ours to choose, so a job could land on a model that has no baseline and fail for want of one, and the files to record and keep in step would multiply. Failing, or exiting 2, when the models differ: the harness cannot know how much a model matters for a metric (the plain Chromium startup passed on the three models its jobs landed on, the throttled one failed on one of its three), so a refusal would be a verdict without evidence. Scaling the numbers by a CPU benchmark: an invented factor.

**Consequences.** The reader of any report, a passing one too, sees whether the machine is the one the baseline came from. The line is a hint; what the gate should do about a baseline measured on another machine is a separate decision. Not measured here: how much each CPU model moves each metric.

**Defending it.** "The report says which machine the numbers came from and which one it ran on. It does not decide for the reader what the difference means."

## ADR-179: On a shared runner the gate is paired: the head is judged against a control measured on the same machine minutes before

**Context.** The committed baselines of `gha-linux-x64` were run against, unchanged, on 13 GitHub-hosted VMs three times each ([gha-cross-vm.md](../results/perf/gha-cross-vm.md)): **8 of the 39 passes failed with a reproduced regression, all 8 on one CPU model, an EPYC 7763; none of the 27 passes on the other four models did.** On that model the throttled profile's startup was 236 to 248 ms against a baseline of 172 ms (+37 to +44 % against a 30 % limit): the machine is about 40 % slower for a CPU-bound scenario than the one the baseline came from, and the fresh batch that confirms a failure runs on the same slow machine, so it confirms it. That is what the confirmation is for when the code regressed, and it cannot tell a slow machine from slow code. The same data says the opposite too: the plain Chromium startup of every pass was faster than its baseline (0.2 to 33 %), because that baseline came from a machine that was slower at startup than the three models those jobs landed on (the Xeon 8370C: 75.4 ms, against 50.8 to 75.3 ms in the 18 passes), so on the faster machines a regression has to exceed the limit plus the machine's advantage before the gate sees it. And one CPU model is not one machine: the same model measured 55 to 64 ms in one job and 73 to 75 ms in another. A committed baseline is a measurement of one machine, and a runner class is a pool of machines that the repository does not choose.

**Decision.** The gate has a mode, **`--paired [--control-ref <ref>] [--control-dir <dir>]`**, of the one command (`npm run gate:perf`, so that GitHub and Jenkins call the same script). It measures a **control**, the base build, on the machine it is running on, and judges the head against what the control just measured, with the same rules, thresholds, stability limit and confirm-on-regression as against a committed baseline (a metric whose control is too noisy is tracked and not gated, as before). In order: the control ref (default `origin/main`) is resolved to a commit, an unknown ref being exit code 2 with the way to fix it, and the same commit as the head being an **A/A by construction**, which the report says (`aa`) and which still measures both; the control gets a checkout (a detached `git worktree` in a temporary directory outside the repository, or the existing checkout given with `--control-dir`, which is never removed); its dependencies are the head's `node_modules`, linked, when the two `package-lock.json` are byte for byte the same, and `npm ci` otherwise; its player page is built; and its **own** harness records its baseline (`npm run perf:baseline`) for the same profiles, N, warm-up and port into a temporary directory, with the head's stream cache (the streams are not generated again, and the harness still refuses a changed stream). Then the head's gate runs against those baselines. Nothing overlaps: one browser at a time, the control first. The control's checkout and the temporary directory are removed on every path: a failure, exit code 2, SIGINT and SIGTERM.

The exit codes are unchanged (0, 1 for a regression that reproduced, 2 for a measurement that cannot be trusted) and **a control that could not be had, built or measured is 2, never 0**; the head is then not measured, and every profile gets a report that says why. Every report opens with *paired: the baseline was measured on this machine minutes ago from <sha>; the committed baselines of this environment were not used* and has a `paired` object: the control and the head, how the checkout and its dependencies came to be, the wall time of the control (preparation and measurement) and of the head, and the CPU model of each measurement. They share a machine, so they share a model (ADR-178); if they do not, that is printed loudly and the verdict stays what the numbers say. The A/A summary accepts the passes of a paired gate (one control and one head commit; each pass against the control it measured) and counts a pass whose control failed as exit code 2.

**Committed baselines stay.** They are the reference for a machine that is stable (a workstation, the container), for the trend and for the record; the gate on GitHub does not use them, for the reason above, and this ADR and its evidence are why.

**Alternatives considered.** One baseline per CPU model (`gha-linux-x64-epyc-7763`): the pool is not ours, so a job can land on a model that has no baseline, and ADR-178 gave the same reason. Thresholds wide enough for the slowest machine: they would hide regressions on the others by the same amount (the throttled profile was +37 to +44 % on one model, so a limit that tolerates that tolerates a regression of that size everywhere). Scaling by a CPU benchmark: an invented factor. A runner of one model (a self-hosted or a larger runner): a machine to run and to keep stable, which free hosted runners are not. Interleaving control and head batches to cancel the drift between them: the better pairing, and more machinery in the batch runner; the paired A/A is what says whether the drift of minutes matters. Measuring the control with the head's harness, which would keep the measuring method equal when a pull request changes it: it needs the head's harness to start the control's server and read its page, so the control's own harness was chosen (the simpler one, and the one known to work on that commit); the cost is under Consequences.

**Consequences.** The performance job measures twice. The A/A jobs on GitHub measured 283 to 288 s per pass of Chromium (PB-PERF-001 to 003) and 84 to 86 s of the throttled profile (173 s when a fresh batch was needed), so the two profiles, control and head, are about 12 to 13 minutes of measuring, plus the checkout of the control, its player build and an install when the lock files differ, and a fresh batch of what regressed: the 720 s of the budget table were for one pass. What it does not do: the confirmation re-measures the head against the **same** control batch, so it does not protect against a one-off in the control or a machine that changes between the two measurements; a pull request that changes how the harness measures is compared with the old way of measuring; one that changes the Playwright version needs both browsers installed or the control cannot be measured (exit code 2); a control older than the harness cannot be measured (exit code 2). **Not measured here: how often the paired gate raises a false alarm on a shared runner.** That is the paired A/A across several VMs (`--control-ref HEAD`), and until it has been run the thresholds are the ones derived on a quiet workstation.

**Defending it.** "The machine is part of the measurement, so the control is measured on the same machine as the head, minutes before it. A committed baseline says how a build performed on the machine that recorded it, and that is the reference where the machine is stable."
