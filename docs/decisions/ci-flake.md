# The flake gate in CI (ADR-170 to ADR-172, and ADR-174 for Jenkins)

Architecture decision records for how the flake gate ([FLAKE.md](../FLAKE.md), `npm run gate:flake`) runs in the two CI systems. The mechanism itself (the reporter, the history, the policy, the quarantine) is ADR-130 to ADR-139 in [flake.md](flake.md); the GitHub pipeline around it is ADR-110 to ADR-114 in [ci.md](ci.md), and the Jenkins one ADR-115 to ADR-119 in [ci-jenkins.md](ci-jenkins.md). This file is about the jobs: [`ci.yml`](../../.github/workflows/ci.yml) (`flake`, `flake-record`), [`nightly.yml`](../../.github/workflows/nightly.yml), and the `Flake` stage of the [`Jenkinsfile`](../../Jenkinsfile). Each record says what the situation was, what was chosen, what was rejected, what it costs, and how I would argue for it. The pipeline as a diagram and how to run a job by hand are in [CI.md](../CI.md).

**Where the facts come from.** **Neither flake job has run on GitHub yet, and the `Flake` stage has not run in Jenkins.** What was done on the development host: `actionlint` 1.7.12 with `shellcheck` 0.11.0 finds nothing in the workflows; [`tests/unit/ci/flake-jobs.test.ts`](../../tests/unit/ci/flake-jobs.test.ts) takes the arguments the workflow gives the gate, as written in the workflow, and runs them through the real gate against a real (temporary) git repository laid out as the job lays out its workspace: as a judge on an empty history, as the first push to `main` (it creates `ci-data`), and as a re-run. What was read on GitHub, read-only: the runs of the pipeline so far (the last green run of `main`, run 41787989882, took 4 minutes from the first job to the last; its slowest leg, `webkit-macos`, 3 minutes 49 seconds), the settings of the repository (public; the default token permission is `read`; `main` protected with the required checks; no `ci-data` yet), GitHub's documentation on required checks and on `always()`, and the source of `actions/download-artifact`. What is not known is in "What is not validated" in [CI.md](../CI.md).

## ADR-170: The gate is judged in one job and recorded in another, because only one of them may hold a write token

**Context.** The flake gate does two things. It **judges** a build: reads the history of the environment, adds this build's runs in memory and fails on a verdict. And it **records** the build: appends the runs to the history and publishes them to the branch `ci-data`. A pull request needs the first and must not be able to do the second: the run of a pull request executes the pull request's code (`npm ci`, `tsx`, the specs), so a token that can write to `ci-data` in that run is a token that any contributor's branch can use. GitHub gives permissions to a **job**, not to a step and not to an event (a job's `permissions` is a fixed map: it is not one of the keys GitHub lists as accepting an expression), so one job with the record behind an `if` on a step either has the write permission on pull requests too or cannot record on `main`.

**Decision.** Two jobs after `merge-gate`, both calling `npm run gate:flake` with `--store git`.

`flake` **judges**. It runs for every run that is not cancelled (pull request, push to `main`, manual run: ADR-171), with `permissions: contents: read` on the job and `actions/checkout` told `persist-credentials: false`, so there is no write token and no credential left in the workspace. The history is read from `ci-data` without a token because the repository is public. It downloads the `reports-<leg>` artifacts into `reports/flake` and calls the gate **twice**, because a history is per environment and the gate refuses run files of two (exit 2; a test covers it): once for the four Linux legs (`gha-linux-x64`), once for the macOS leg (`gha-macos-arm64`). The second call runs also when the first failed, so one red environment does not hide the other. The gate prints its report on the job summary and exits 1 on a verdict: the job is red, and the build with it.

`flake-record` **records**. It runs for a push to `main` and for nothing else (`github.event_name == 'push' && github.ref == 'refs/heads/main'`), and it is the only job of any workflow with `contents: write`. It calls the same two commands with `--record --push`. The gate always judges before it records and exits 1 on a verdict, which is the verdict `flake` reports; so the recorder passes over exit 1 (`|| [ "$?" -eq 1 ]`) and over nothing else: exit 2 (it could not judge, or the build was a pass whose recording failed) fails the job. A last step checks that both decision files say the build was recorded, because the gate only logs a failed recording when the verdict is already a failure (the exit code stays 1, and a build that failed the gate and then failed to record would otherwise look recorded).

**The nightly** repeats the two jobs (`flake (nightly)`, `flake-record (nightly)`) with the same steps, so that the history also holds the flake rates of the `@release` tests, which the merge gate never runs. The judge runs for every run of the nightly, the pull request that changes the file included (the only time its wiring is exercised before the merge); the recorder only for the schedule and for a manual run on `main`. The steps are repeated, not shared through a reusable workflow, because the jobs of a reusable workflow are named `<caller job> / <called job>`, which would rename the check that the owner requires; a unit test compares the two copies.

**Alternatives considered.** One job with `--record --push` on a condition: the permission cannot depend on the event (above). A separate workflow on `workflow_run`, which runs with the write token of the default branch after the first one: it is the pattern in which the artifacts of a pull request run become the input of a privileged job, and the recorder would read exactly such artifacts. Recording inside each leg: five writers racing per build, and a write token in the job that runs the browsers. A recorder that does not judge: the gate has no mode for it, and a second copy of the judgement is the thing the two jobs are meant to avoid. Judging only on pull requests: a push to `main` that goes red is the signal that a quarantine decision is due, and it should not wait for the next pull request.

**Consequences.** Two more jobs after the slowest leg, each paying a checkout, `npm ci` and a download (about a minute together: unmeasured). On `main` the judgement is computed twice from the same input (the recorder's verdict is not used). `flake` is a required check ([CI.md](../CI.md): the owner adds it to the rule, ADR-171 says why it matters). The trust model is written down and also pinned: [`tests/unit/ci/workflows.test.ts`](../../tests/unit/ci/workflows.test.ts) fails if a write permission appears anywhere but a job called `flake-record`, and [`tests/unit/ci/flake-jobs.test.ts`](../../tests/unit/ci/flake-jobs.test.ts) fails if the recorder's `if` changes, if any other job contains `--record` or `--push`, or if the judge gets more than a read token or keeps a credential.

**Defending it.** "The job that can write is not the job that runs on a pull request, and a test fails if that stops being true. The two jobs run the same command, so what a pull request is told is what `main` will be told."

## ADR-171: The judge runs when a leg is red and not when the run is cancelled, and its check is the one that notices a merge gate that did not run

**Context.** A job with `needs` is skipped when a job it needs fails. `flake` must not be: a build with a red leg is the build to judge (its other runs are data, and a flaky test can sit next to an unrelated failure). GitHub's own documentation on required checks says that a job that depends on a failed job "is skipped and may not block merging", that the successful states of a check are `success`, `skipped` and `neutral`, and to "use `always()` with `needs` for required checks that depend on other jobs". The documentation of `always()` says it returns true "even when canceled", warns against it "for any task that could suffer from a critical failure, for example: getting sources, otherwise the workflow may hang until it times out", and recommends `if: ${{ !cancelled() }}` to run a job or step regardless of its success or failure. The pull request runs of this pipeline are cancelled by the next push (`cancel-in-progress`, ADR-110), which is how most of them end.

**Decision.** `if: ${{ !cancelled() }}` on `flake`, and the same with the push-to-`main` condition on `flake-record`. Not `always()`: both jobs check out the repository, and with `always()` every superseded pull request run would start them, find the legs cancelled before they could upload, and end in a red check on a run nobody reads.
The consequence that matters more than the flake gate: **nothing can skip `flake`**. If `streams` fails, the five legs of `merge-gate` are skipped; `flake` still runs, finds no run file (`actions/download-artifact` does not fail when a pattern matches nothing, and the gate exits 2 with "reports/flake/reports-chromium: no such file or directory") and goes red. A leg that dies before it uploads does the same for its environment. So `flake` is a required check for a second reason than the flake rate: it is the check that notices a merge gate that did not run. Whether GitHub would have let such a pull request through anyway is **not known**: a skipped job that is a matrix leg is reported under the unexpanded name of its matrix (as far as I know: not seen here), which would leave the five required names "expected" and block the pull request, or it would count as skipped and pass; none of the last 40 runs of `ci.yml` had a skipped job, so neither has been observed. With `flake` required the answer does not matter.

**Alternatives considered.** `always()` (above). `if: ${{ success() || failure() }}` (the same as `!cancelled()` with more words). An aggregator job (`needs` all the others, fails unless every result is `success`), the usual way to have one required name that cannot be skipped: it would also close the hole, but it replaces the seven required names or adds an eighth, and the brief was that the names of the existing jobs do not change. Making each leg `if: always()`: the legs would run the browser tests after a failed `streams`.

**Consequences.** A red `flake` has three meanings, and its output says which: a verdict (exit 1, with the decision it drives), the gate could not judge (exit 2: a leg left no run file, the history is unreadable, a bad argument), or the run files of one environment came from two. A new job added to the workflow later must say whether it is covered by the same reasoning: a required check that `needs` another job and has no `if` is skipped when the other one fails.

**Defending it.** "I used the form GitHub's documentation recommends for running a job whatever the result of the jobs it depends on, and I checked what that does to a run where the legs never started: the judge goes red because it has nothing to judge, which is the behaviour I want from a required check."

## ADR-172: The history lives on the branch `ci-data`: read by anyone, written by `main` only, created by the first write

**Context.** Where the history lives is ADR-134 ([flake.md](flake.md)): an orphan branch of this repository, `history/<envId>.jsonl`, no code. What this record decides is who may touch it from the workflows. Facts of the repository, read with the API on 2026-11-04: it is public; the default permission of the token of a workflow is `read`; `main` is protected (the seven required checks, no force pushes), and there is no ruleset and no `ci-data` yet.

**Decision.** **Read:** anyone, with no token (public repository): `flake` fetches `ci-data` with `git fetch --depth=1` into a private ref (`refs/flake-store/ci-data`), which touches no branch, no index and no `HEAD` of the checkout. A branch that does not exist is an empty history, not an error, so a pull request run before the first recording judges against nothing and passes with a note ("not enough data": a verdict on a rate needs 20 executions of a test and 20 builds of an engine job). **Write:** `flake-record` only (and its twin of the nightly, for the schedule and for manual runs on `main`), with the token of the job (`contents: write`; the repository default stays `read`, so nothing about the repository settings has to change). The store builds the commit with plumbing as the identity it is given, **`github-actions[bot] <41898282+github-actions[bot]@users.noreply.github.com>`** (the id is the bot's: `gh api users/github-actions[bot]`), pushes `<commit>:refs/heads/ci-data` **without force**, and when the push is refused because another job pushed first it fetches again, appends the same runs on the new tip and pushes again (ten tries at most). **The first write creates the branch:** with no tip the commit has no parent, so `ci-data` starts as an orphan with one commit per environment, and two jobs that both find no branch settle it with the same retry. Nothing has to be created by hand. Recording is idempotent: a run already in the history (the invocation id is inside the run file) is not added again, so a re-run of `flake-record` records nothing new.

**What bounds the write token:** the job runs only for a push to `main`, so it executes merged code; the pull request runs, including those of forks, never get it; the workflow uses no secret (a test forbids `secrets.`); the data on `ci-data` is data, not code, so a bad push can spoil the history but not the product; and the protection of `main` is expected to refuse a direct push of the token to it (not tried: it would take a push to `main`). **What is not mitigated:** the job's token is available to git for the whole job, and the job runs `npm ci` and `tsx` of the merged code with it, so a compromised dependency of the lockfile that got into `main` could use it. Giving the token to the push step alone (an `http.extraheader` built from an environment variable) was considered and not done: it changes how the store's git commands authenticate and cannot be tested without a real push. The recorder runs after the merge, so a pull request cannot get there first.

**Alternatives considered.** The ones of ADR-134 (an artifact, the Actions cache, a database, a file on `main`). A personal access token or a deploy key: a long-lived secret for a lab that otherwise has none. Protecting `ci-data` with a rule: the bot could not push to it either, unless it is a bypass actor; it is data, and the rule would have to be kept in step with the identity.

**Consequences.** The history grows by a commit per environment per recorded build (a build of `main` writes two), and it holds the last 200 runs of an environment. A fork's pull request judges against the same history as any other, and cannot write to it. If the owner later restricts who may create or push branches, the bot has to be allowed to push `ci-data`, or `flake-record` goes red on the push and the history stops growing (the judge keeps working on what is there).

**Defending it.** "Reading is public and writing is one job that only runs on `main`, with the permission asked for on that job and nowhere else. The branch is created by the first write, and the code path that does it is covered by the store's race tests and by a test that runs the workflow's own arguments against a real bare repository."

## ADR-174: Jenkins judges every build, records the builds of `main`, and keeps its history on a volume of its own

**Context.** The Jenkinsfile runs the stages of the workflows, so `gate:flake` needs a stage. Three things differ from GitHub. The four engines run in parallel branches with workspaces of their own (ADR-116), wiped when the branch ends, so an engine's run file is gone when the next stage starts. A declarative pipeline skips every stage after a failed one (the console of builds 2 and 5 in the evidence says `Stage "Streams" skipped due to earlier failure(s)`), so a red engine would skip the judge, which is the build that most needs judging. And a local Jenkins is not a CI service (ADR-119): its builds are its owner's, of `main` mostly and of a throwaway branch for the negative run, a history is worth the number of builds in it, and a verdict on a rate needs 20 builds of an engine.

**Decision.** A `Flake` stage after `Merge gate`, on its own agent: it checks out, runs `npm ci`, unstashes the run files of the four engines into `reports/flake/<engine>/` (the shape of GitHub's download) and calls `npm run gate:flake -- --store file --runs reports/flake`, with `--record` added for a build of `main`. Each engine stashes `reports/flake/run*.json` (the run file and the quarantined one) as `flake-<engine>` in `collectResults`, just before `cleanWs()`; an unstash of a stash that does not exist fails the stage, which is how a lost agent shows. Each engine's `gate:merge` runs in `catchError(buildResult: 'FAILURE', stageResult: 'FAILURE')`: the engine's stage is red and the build ends red, and `Flake` still runs. The history is a file store (`/history/jenkins-linux-arm64.jsonl`) on a **named volume `flake-history`** of the agent, apart from the stream cache so that clearing one never clears the other; the agent's Dockerfile makes `/history` and gives it to the agent's user, the way it does `/cache`, and `PB_FLAKE_HISTORY_DIR` names it to the gate. Jenkins is one environment, so the gate is called once (GitHub's two environments are two calls).

**What is recorded.** Builds of `main`, whatever their result, and no others. `isMainBranch` accepts the names the git plugin gives the branch (`origin/main`, `refs/heads/main`, `main`) and nothing that merely contains the word. A build of any other branch is judged and forgotten, as a pull request is on GitHub: the negative run (README) is made red on purpose on a throwaway branch, and a build like that must never become flake data. Not only the successful builds: the gate records a failed build by design (ADR-137 in [flake.md](flake.md): a history of the good builds only would understate the rate), and a red `main` build on GitHub is recorded too.

**What it can show, and what it cannot.** The stage shows the plumbing (stash across workspaces, a stage that runs after a red engine, a history that survives builds and grows), and the rules that need no history: an expired quarantine, an invalid list, no run file at all. It cannot show a rate: until the volume holds 20 builds of an engine the gate says "not enough data", and a laptop will rarely have them. Nor can the numbers be compared with GitHub's: a history is per environment.

**Alternatives considered.** Recording every branch (experiments and the negative run would become data). Recording only green builds (the understated rate above). A history kept as a build artifact with `copyArtifacts` (another plugin, and the log rotator keeps the artifacts of five builds). A git store on the mounted repository (a read-only mount of a different repository from the one GitHub has). `/cache` for the history (one wipe erases both). A stage for every engine instead of one for all (four histories of one environment, and the gate refuses to judge them apart).

**Consequences.** A new volume: `docker compose up -d --build` creates it, and the agent image has to be rebuilt for `/history`. The file store takes no lock; what keeps two builds from appending at once is `disableConcurrentBuilds()`. The evidence of builds 3 to 6 predates the stage, and the console excerpt of the evidence tool keeps the summary lines of the other gates but not this gate's `flake gate:` line (not changed here). The engines' `catchError` changes how a red engine reads in Jenkins: the engine's stage is red as before, and the evidence tool, which takes the first failed stage, still names it.

**What is not validated.** **No Jenkins ran any of this**: the round that wrote it had no Docker, so the Jenkinsfile was checked by the unit tests that read it as text and by reading, not by the Jenkins parser. A real build must prove, in this order: (1) the Jenkinsfile loads and `Flake` appears after `Merge gate`; (2) stash and unstash work across the parallel workspaces: the run files of the four engines arrive under `reports/flake/<engine>/reports/flake/` and the gate prints `4 runs in this build`; (3) with an engine made red (the negative run), `Flake` still runs, the engine's stage is red, the build ends in FAILURE and the evidence tool still reports the engine as the failure; (4) `/history` is writable by the agent's user: a build of `main` creates `jenkins-linux-arm64.jsonl`, a second one appends to it, and it survives `docker compose down` (not `-v`); (5) the branch name of this job's checkout is one `isMainBranch` knows (the log says `Checking out Revision <sha> (<name>)`); if it is not, the stage judges and never records, and `ls /history` shows an empty directory; (6) a build of another branch writes nothing.

**Defending it.** "Jenkins runs the same script as GitHub in one more stage. The three things that differ (separate workspaces, the stages skipped after a failure, a history that belongs to one laptop) each cost a few lines and one test that reads them, and what a real build still has to prove is written down before it runs."
