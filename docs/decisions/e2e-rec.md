# The recovery suites decisions (ADR-101 to ADR-103)

Architecture decision records for the recovery specs: [`tests/e2e/recovery.spec.ts`](../../tests/e2e/recovery.spec.ts) (PB-REC-001 to PB-REC-007, the faults of the VOD path), [`tests/e2e/recovery-live.spec.ts`](../../tests/e2e/recovery-live.spec.ts) (PB-REC-008 and PB-REC-009, the live origin) and their helpers in [`tests/e2e/rec`](../../tests/e2e/rec) (`faults.ts`, `live.ts`, `shaka.ts`). They stand on the support library ([ADR-070 to ADR-079](e2e.md)) and on the fault engine and the request log of the service ([ADR-082 to ADR-085](server.md)). They are written so each one can be defended in a review: what the situation was, what was chosen, what was rejected, what it costs, and how I would argue for it.

**What the player under test does.** Every claim below about Shaka Player 5.3.3 with the lab's configuration A (its defaults) was first read in the installed sources, then observed in the runs. A failed HTTP request is retried by the networking layer (`lib/net/networking_engine.js`, `lib/net/backoff.js`: two attempts, a first retry after 1 s fuzzed by +-50 %, so 0.5 s to 1.5 s). When the attempts run out the streaming engine sets the error to critical, waits one more back-off, and asks the player to disable the failing rung for 30 s (`lib/media/streaming_engine.js` `handleStreamingError_`, `lib/player.js` `disableStream`): if another rung exists the error is lowered to recoverable, raised as an `error` event, and the ABR switches (`variant-changed`, reason `abr`); if none exists, or ABR is off, the error stays critical and the default `failureCallback` only logs. An ABR switch aborts the fetch that is pending (the abort is ignored and the segment is asked for again on the new rung: `fetchAndAppend_`). A manifest request failure is retried by the same layer and then fails `load()`. The manifest and segment timeout that would matter (10 s to the first byte) is above every delay this suite injects. None of this was changed: the specs observe the defaults.

**Where the numbers come from.** One machine: Apple M2 Pro (12 cores, shared with other agents' browsers and containers: the load average was between 15 and 22 during the runs), macOS 27.2, Node 22.11.0, Playwright 1.64.1; Chromium and WebKit natively, Firefox and Linux WebKit in the Playwright image (`npm run docker:pw -- --cpus 3`, one container at a time), always two workers, on 2026-11-04. Localhost, synthetic content, software decoding. Nothing was measured on a CI runner or on another architecture. The specs assert behaviour and arithmetic from Shaka's retry parameters, not these durations.

## ADR-101: A recovery test proves the fault fired before it judges the recovery, and the proof comes from the origin

**Context.** A recovery test has two halves: the fault happened, and the player coped. The second half passes by itself when the first did not happen: a player that never asks for the faulted segment "recovers" from it perfectly. Faults are applied by the service below the browser, so they are identical in every engine, but whether the player asks for what the rule matches is the player's business: a segment number the player does not request, a rung it is not on, a stale window that opens after its last refresh. In three of the nine rows the condition also depends on the engine and on timing (where the ABR is when the fault lands, which rung the engine starts on), so "I configured the fault" proves nothing about "the fault was felt".

**Decision.** Every spec starts by waiting on the server's own record, before it asserts anything about the player. For the faults that fail or delay a request (status, latency, abort, stale manifest) the request log names the rule on the request it hit (`faults`), and `waitForFault(session, ruleId, count)` ([`rec/faults.ts`](../../tests/e2e/rec/faults.ts)) waits for that many finished requests that carry the id, returns them, and the spec asserts what the rule did to them: the status (404, 503), the first-byte time of the delayed request, exactly the 20,000 bytes of the truncated body with `aborted`, the stale body having the same size as the manifest served before the window. When it does not happen the failure says so with a number: `the fault rule f1 {...} named 2 of the 3 requests it was waited for within 15000 ms: the player stopped asking for what the rule matches before the rule was used up`, followed by the last requests of the log. A live origin stall is the exception: it fails no request, the origin stops publishing, so the log cannot name the rule (the service's `evaluate` skips `live-stall` rules, ADR-084). Its proof is the origin's own state read from the service at two moments, `live.stalled` true when the player runs dry and false when it resumes, and what the player did not ask for while it lasted (no segment above the frozen edge before the origin returned, and some after). A fault that is installed in the middle of playback (PB-REC-003) is installed only after the player has been served by the rung it takes down (below, ADR-102), and the spec waits for the first refusal before it asserts the move.

**Alternatives considered.** Trusting the configuration (above: it can pass for the wrong reason). Asserting on the player's error events as the proof (a retried 404 raises none, which is exactly the success case of PB-REC-001). A counter in the service ("rule f1 fired N times") instead of the log (the log already says on which request, in which order and with which timing, which the specs also use). Matching by time (`afterMs`) to hit a moment of playback (slower, and not the same segment in every engine: the profiles select by segment number for that reason).

**Consequences.** Each spec carries one extra wait and one or two assertions about the origin, and a failing spec says first whether the fault fired. The mutation runs above show it: a rule moved to a segment that is never requested fails in 15.5 s with the message quoted; a player configured not to fail over (`qa.configure({ streaming: { maxDisabledTime: 0 } })`) fails PB-REC-002 with "named 2 of the 3 requests", and the attached `qa-metrics.json` shows state `error` and a critical `BAD_HTTP_STATUS`; a stall shorter than the buffer fails PB-REC-008 because the player never runs dry. The log is read by polling every 25 ms (ADR-074), so a proof can arrive up to 25 ms late. The live stall's proof is weaker than the others because it is the origin's flag and not a request: the `live.stalled` read is one round trip after the player's event, and the spec relies on a 4 s margin between the player running dry and the origin returning.

**Defending it.** "A recovery test that does not show the fault is a test of nothing, so the first thing every one of them does is ask the origin whether it did what I told it to, with the request and the rule's id in the answer. When it did not, the report says how many times it did, which is usually the whole diagnosis."

## ADR-102: The oracle is the outcome and the invariants of the failure path, not a sequence of requests

**Context.** The first draft of PB-REC-001 asserted what the strategy's text says: two requests for video segment 3, the first 404, the retry 200, on the same rung. It passed in Chromium and failed in macOS WebKit. The cause is not the fault but the ABR: Chromium starts on the 720p rung, macOS WebKit on 360p and climbs after about a second (the lab's earlier measurement, and the logs here), and that climb lands inside the retry's back-off window (the segment is requested after 0.3 to 0.5 s and the retry waits 0.5 s to 1.5 s). When the ABR switches, Shaka aborts the pending fetch and asks for the segment again on the new rung. So the log shows the retry on the same URL followed 4 ms later by the segment on the new rung (7 of 8 runs of the first batch), or no retry at all and the segment on the new rung (1 of 8). PB-REC-002 shows three shapes in macOS WebKit (a retry and a failover; a retry pre-empted by the climb with the burst falling on two rungs and no error at all; a pre-empted retry and a failover), PB-REC-004 two (the slow request waited for, 8 s, or abandoned after about a second when the ABR climbs, 3 of 6 runs each in a later batch). None is a defect: the viewer gets the segment either way.

**Decision.** The specs assert what holds in every shape, and record the shape in an annotation (`recovery`) so that the report says what happened. For a single refusal (PB-REC-001): the rule named exactly one request and it was a 404; some later request for that segment, on any rung, delivered it, within twice the longest first retry wait; and no error of any severity reached the application (a failover raises a recoverable error, and a successful retry raises none). For a burst of three (PB-REC-002): three refusals, all for that segment; a later request delivered it, within three waits of the retry policy; nothing critical, at most one rebuffer; and every rung that appears in an error event is not the rung that delivered (a rung Shaka gave up on cannot serve the segment). For the slow segment (PB-REC-004): the delayed request was held back for the whole delay or abandoned by the player (the log says `aborted`), the media clock passes the segment, at most one rebuffer, no error, and no stall left open. For the truncated segment (PB-REC-005): exactly 20,000 body bytes then a dropped connection, the segment fetched again whole (more than twice the cut, which the profile chose to be under half of any segment), no error kind that repeats (a single fault can cost one error of a kind, never a loop); the codes are on record because the media pipelines differ. For the rung outage (PB-REC-003): see below. Every time bound is arithmetic from Shaka's defaults, written next to the constant and kept in [`rec/shaka.ts`](../../tests/e2e/rec/shaka.ts): the retry waits at most `1 s x 1.5 = 1.5 s`, so a retry is late after twice that; a burst costs three such waits; the first critical error of dead segments costs two (the audio has one rendition, so its first failed fetch has nowhere to go: the retry wait and the streaming engine's own back-off); all video rungs given up on costs two per rung. **PB-REC-003 puts the outage where the player is.** Chromium is on the 720p rung from the start, macOS WebKit is not, and an outage on a rung the player has not climbed to yet is a different test in each engine. The spec pins the rung (`selectVariantByHeight(720)`), gives the ABR back at once (`setAbr(true)`: with ABR off Shaka cannot fail over and the error stays critical, which a mutation run confirms), waits until the rung has delivered a segment, and only then installs `rung-outage`, so the rung goes down mid-title for good in every engine. It then asserts that the ABR (reason `abr`) moves to a lower rung, that the segment the rung could not deliver came from another rung within two waits of the retry policy, that the origin delivered nothing from the rung after the first refusal, that the requests to it stay at or under four (two fetches can be in flight, its initialization segment and a media segment, each attempted twice; 2 were seen in every run), and that every error the player surfaced names that rung.

**Alternatives considered.** Pinning the rung with ABR off for the single-refusal and burst specs (every engine would then show the textbook sequence, and it would hide the pre-emption, which is real behaviour, and the failover, which needs the ABR). Asserting the exact sequence per engine (a list of expected shapes per engine is a test of the browser's start rung, and it flakes at the boundary: the first WebKit batch of PB-REC-004 passed 6 of 6 and the next failed 2 of 2). Asserting the number of stall episodes after the stale-manifest recovery (see ADR-103: the recovery can split in two). Installing `rung-outage` at the creation of the session, as the profile does (Chromium would fail the very first fetch of the title and the other engines would meet it a second later when they climb: two scenarios under one id). Retrying a flaky run (no: the specs take the shape as given).

**Consequences.** The specs are weaker than a recorded sequence, and say so: they do not detect that the player took a longer path than before, only that it did not fail, did not hammer, did not exceed the bound and left the evidence. A regression that made the failover impossible is detected (no `abr` move, a critical error, a media clock that stops); one that made it slower by a second is not, below the bound. The annotation makes a change of shape visible in the report without making it a failure.

**Defending it.** "An oracle has to be true of every valid behaviour of the thing under test and false of the invalid ones. The textbook sequence is true of one engine's timing. The outcome, the bounds from the retry arithmetic and the order of cause and effect (a rung that raised an error is not the rung that served the segment) are true of all of them, and I confirmed that by running each spec until the first WebKit run showed me a shape I had not predicted, then fixing the oracle and not the engine."

## ADR-103: The live recovery specs: what is stalled, how long, and what is deliberately not asserted

**Context.** Two rows are about the live origin. PB-REC-008 (risk 20, merge tier) is the riskiest test of the merge gate: if Shaka's defaults did not recover from an origin that stops publishing for 10 s, a live event would freeze for everyone. PB-REC-009 asks that a stale manifest does not strand the player outside the seek range. The default live window is 30 s deep and the presentation delay 6 s, so the conditions that make each fault matter are far apart, and the hook does not report the seek range.

**Decision.** *PB-REC-008.* The spec starts the player, waits for the first frame, reads the origin's current edge from the service and installs `originStall(edge + 3, 10_000)` (`LIVE_LIMITS.injectedStallMs`: longer than the 6 s presentation delay, so the buffer must drain): the stall starts when the third segment from now is published, 4 s to 6 s later, wherever the player's startup put it on the clock. It waits for `buffering-start` (the player ran dry) and reads that the origin is stalled at that moment, then waits for `playing` and reads that it is not, then lets 2 s of media play. It asserts what the row says (resumed after the origin returned, at most one stall episode, no critical error left) and what makes the proof: no segment above the frozen edge was requested before the origin returned, and some after. **It does not assert the latency**, and that is the most important finding of the phase: the defaults do recover, in all four engines, with one stall episode of 3.6 s to 4.4 s and no error of any severity, but the playhead resumes where the buffer ended, which is the whole outage behind the live edge, and nothing brings it back. Measured in Chromium over 40 s of media after the resume (a scratch run, not a spec): latency 10.07 s at the resume, then 10.12 s at +5, +10, +20, +30 and +40 s, no `live-edge-seek`, playback rate 1; the specs saw 10.05 s to 10.64 s at the resume and 10.09 s to 10.64 s 2 s later in the 14 final runs of the four engines (11.1 s in the first Firefox pass, which stalled for 4.4 s). `liveSync` is disabled in configurations A and B. The readiness criteria (`LIVE_LIMITS`) allow 10 s outside an injected fault and ask for the latency to be back within them 60 s after a stall (PB-RDY-003): configuration A cannot meet that, and `criteria.ts` itself says that a limit the default cannot meet is a finding, not a number to relax. The row, which does not mention latency, is satisfied; the latency is in the annotation of every run. *PB-REC-009.* The first version stale for one refresh (2 s) passed everywhere and could not fail for the row's reason: with the default 30 s window nothing short of 36 s of staleness leaves the playhead behind the seek range. The spec therefore creates the session with a DVR window of 5 segments (10 s, `LiveOptions.windowSegments`, valid from 2 to 120) and `staleManifest(12_000, 1_000)`: the window opens a second after the first media request (the player has a good manifest first) and lasts one segment longer than the DVR depth. The stale body lists the media up to the edge of the moment the window opens (30 s); the playhead plays them and stops there (it stalls at 29.95 s to 30.02 s: the spec asserts it played what was listed, to within a second); the seek range, which starts one DVR depth behind the origin's edge, passes the stopped playhead 10 s after the window opened. That the playhead was really left behind is checked on the origin's state (the edge read when fresh manifests return, less the DVR depth, against the media time of the stall), not assumed. The spec then asserts the log (at least four of the six refreshes of the window answered with the stale body, the same bytes as the manifest served before it; no gap between two manifest requests above the readiness limit of 4 s, so the player kept polling), the resume, and that the playhead is inside the seek range, which the hook cannot say directly: the latency is `seekRange().end + presentation delay - currentTime` (METRICS.md), so a playhead inside the range has a latency between the delay and the DVR depth, each given a segment of slack (the range is defined only to within a segment): 4 s to 12 s. A playhead that stayed where it stopped would read 16 s or more. Shaka does move it: twice, forward by about 4 s and then 8 s (the hook counts them as `live-edge-seek`), the first while the manifest is stale, the second when the fresh one arrives, and the latency after the recovery is 6.2 s to 8.0 s. The number of stall episodes is not asserted (the first one is the buffer running dry, 7.6 s to 8.9 s; a second one of 0.08 s to 0.76 s followed the resume in 6 of the 14 final runs and in 4 of 5 early Chromium runs, because the audio, which Shaka refills once a second, ran dry just after the jump): it is on record in the annotation.

**Alternatives considered.** Installing the stall at the creation of the session with the edge the session reported (the stall would start 6 s after creation whatever the page's startup took, and a slow start would put the player's own startup inside it). Asserting that the latency returns to the target (it does not, and a test that always fails is not evidence of anything but the finding, which the report carries; the readiness check is the place that judges it against numbers). Asserting `rebuffer.count <= 1` for the stale manifest (it made the first stability batch fail 4 of 5 in Chromium, for a promise the row never made: removing it is not weakening the row). A stale window over the default 30 s window (36 s plus the recovery: a 45 s test, ten times the cost of the others, for the same behaviour). Reading the seek range through the page (`page.evaluate` is not for specs, and the player object is not exposed: a library need, below).

**Consequences.** PB-REC-008 takes 18.4 s to 20.7 s in the final runs (the estimate of the area is 20 s) because it waits for a real outage; PB-REC-009 takes 17.5 s to 21.4 s. The stall proof has a 4 s margin: a runner so slow that the player's buffer outlives the outage by 4 s would fail the wait for `buffering-start` with the timeline. The DVR window of 5 segments is a property of this spec, written next to the constants, not of the stream, and PB-REC-009 therefore says nothing about the default window's behaviour at depth 30 s. The seek range is inferred from the latency; if the hook ever reports `seekRange()` the inference should be replaced.

**Defending it.** "The merge-tier test asks the question the row asks, with the real outage, and passes because the defaults recover; the number the row does not ask for, the latency afterwards, is on the report because that is where it will matter and I would rather hand the next phase a finding than a green tick. The stale-manifest test was made able to fail for its reason by changing the one condition that made it unreachable, and I checked that it does: shortening the window to 6 s fails the stranding precondition, with the numbers."
