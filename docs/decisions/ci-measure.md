# Measurements on GitHub runners (ADR-175 to ADR-177)

Architecture decision records for [`measure.yml`](../../.github/workflows/measure.yml): one long measurement on a GitHub runner, started by hand, so that the measurements that need a machine to themselves run there while a workstation does something else. How to dispatch it, how to download what it leaves and what each runner is called are in [CI.md](../CI.md), section "Measurements on GitHub runners". The performance harness and its baselines are ADR-120 to ADR-129 in [perf.md](perf.md) (the baseline of an environment, ADR-126), the flake collector is ADR-138 in [flake.md](flake.md). Each record says what the situation was, what was chosen, what was rejected, what it costs, and how I would argue for it.

**Where the facts come from.** **The workflow has not been dispatched on GitHub.** What was done on the development host: `actionlint` 1.7.12 with `shellcheck` 0.11.0 finds nothing (and found a planted `SC2086` in a scratch workflow, so the shell checks were on); [`tests/unit/ci/measure.test.ts`](../../tests/unit/ci/measure.test.ts) keeps the properties below and was run over copies of the file with one mistake each; every script of the job was run from the workflow's own text, with `npm` and `npx` replaced by functions that print their arguments. The command lines of the tasks were **read** in the worktrees of the branches that own them, because three of the tasks run files that are not on `main`: `perf/aa.ts` on `p5/perf` (commit a28a6fe), `ab/run.ts` on `p6/ab` (1712989), `live/readiness.ts` and `live/soak.ts` on `p7/live` (the options in `src/lab/readiness/args.ts`, commit c315915; the file that runs them, `src/lab/readiness/commands.ts`, was still uncommitted work). Nothing from a runner is claimed.

## ADR-175: A measurement workflow is dispatched by hand, and everything it is given is data

**Context.** The performance harness, the A/A check and a soak need a machine that nothing else uses, for an hour or more each, and a workstation has other work to do. A GitHub runner is a separate machine per job, in parallel, and it is the environment the merge gate runs in (`gha-linux-x64`, `gha-macos-arm64`), for which a performance baseline can only be recorded on a runner (ADR-126: a baseline belongs to one environment). The price of such a workflow is that it takes **free text** from whoever dispatches it (extra arguments, a label), and the classic way to turn text into code in a workflow is `${{ inputs.args }}` inside a `run:` script, which pastes the value into the script before the shell reads it: an apostrophe breaks the script, `$(...)` or `;` runs.

**Decision.** `workflow_dispatch` is the only trigger: only people who can already start a workflow can start it, and it never runs for a pull request, a push or a schedule. The token is `contents: read` and there is no secret, so the workflow gives its dispatcher nothing that a push would not. **`task`, `runner` and `engine` are closed choices** (GitHub refuses any other value, in the page, the CLI and the API), so the code that runs is one of six branches of a `case`. **Every input reaches the shell only through `env:`**: no `run:` script contains an expression at all. `args` is split into words with `read -r -a` and handed over as an array, so it is never evaluated (no `eval`, no `sh -c`, and no expansion of `*` or `$(...)`: a hostile value becomes an argument that the CLI of the task rejects). `label` is the one free text that becomes part of a name, so a first step, which cannot fail, reduces it to letters, digits, dots, dashes and underscores and 60 characters before it is written to `$GITHUB_OUTPUT` (the upload refuses a name with a slash or a colon and would lose the results, and a newline in a value written to the output file adds outputs of its own). `timeout_minutes` is clamped to 340 at the job (a hosted job is stopped at 360 minutes) and the task gets **10 minutes less**, as a limit of the step, so that after a timeout the machine record and the results are still uploaded. The concurrency group is the task, the label, the runner **and the engine**, and a running measurement is never cancelled: with `cancel-in-progress: false` GitHub keeps one running and one waiting run per group and cancels a waiting one when a third arrives, so a group of task and label alone would let three engines dispatched with one label cancel each other's queued runs. The checkout is complete (`fetch-depth: 0`) because the A/B runner asks git when its pre-registration was committed, and a shallow clone would answer with the tip. [`measure.test.ts`](../../tests/unit/ci/measure.test.ts) fails if the file gets another trigger, a write permission, a permission of a job's own, an expression in a script, an input under a key that could be code (only names, the runner, the limits, the browser and environment variables are allowed), a task list that is not closed or a task without a branch, a missing limit, and it was run over a copy with each of those.

**Alternatives considered.** Inline expressions with careful quoting (the usual way to write this bug, and it cannot be reviewed away: every future edit is a new chance). A composite action that takes the inputs (the same pasting, one level down, unless it too passes them as environment). A `matrix` of tasks in one dispatch (many long runs under one limit, one artifact and one cancel button, when each measurement should have its own limit and its own result). A schedule (a measurement is somebody's decision, and it costs the runner minutes). `nightly.yml` (that is the release gate: it runs tests and fails the build). `eval "$ARGS"` so that quotes work (it is exactly the execution that this decision removes).

**Consequences.** `args` cannot carry a value with a space, and a JSON value is written without one. A branch is measured by dispatching on a ref that **contains this file** (merge `main` into the branch first), and the first dispatch of a new workflow needs the file on the default branch (GitHub's rule). A third dispatch with an identical group cancels the waiting one, which the documentation says. Whoever can dispatch can also push a branch with any workflow, so this is not a defence against a malicious writer; it is a defence against **data** (a typo, a label pasted from an issue, text from somewhere else) becoming code, and it keeps the permissions at what a read-only job needs.

**Defending it.** "The only free text goes through environment variables, so it is data in every line; the code it can pick is a closed list; the token can only read; and a test fails if any of that changes."

## ADR-176: Each task is the command of its npm script, written against the CLI as it exists on its branch, and the test knows what is not on `main` yet

**Context.** The six tasks are the long runs of five phases: the performance baseline and its A/A check (`p5/perf`), an A/B experiment (`p6/ab`), the readiness checks and the soak (`p7/live`) and the flake collection (`main`). Their scripts are defined in `package.json` already, but the files behind three of them are not on `main`, so a workflow that is correct today could name flags that the owners of those branches change before they merge.

**Decision.** One `case` in one step, one branch per task, each the command of its npm script with the engine given the way that CLI takes it:

| Task | What the step runs | What it leaves |
| --- | --- | --- |
| `perf-baseline` | `npm run perf:baseline -- --profile "$ENGINE" $ARGS` | `perf/baselines/<env>/<profile>.json`, `reports/perf/<env>/<profile>.run.json` |
| `perf-aa` | `REPEAT` times `npm run perf:gate -- --profile "$ENGINE" --reports-dir reports/perf-aa/pass-<i> $ARGS`, then `npx tsx perf/aa.ts reports/perf-aa/pass-*/*/<profile>.json` | `docs/results/perf/<env>/<profile>-aa.json` and `.md`, the report of every pass |
| `ab` | `npm run ab -- $ARGS` (the plan names its engine; the input only picks the browser) | `docs/results/ab/<id>.<env>.<stamp>.raw.json`, `.report.json`, `.report.md` |
| `readiness` | `npm run readiness -- --engine "$ENGINE" $ARGS` | `docs/results/readiness/<env>-<engine>[-<protocol>].json` (A and the candidates of the run in one file) |
| `soak` | `npm run soak -- --engine "$ENGINE" $ARGS` (`--minutes` goes in `args`) | `docs/results/soak/<env>-<engine>-<minutes>m[-<injections>][-<protocol>][-<candidate>].json` |
| `flake-collect` | `npm run flake:collect -- --project "$ENGINE" $ARGS` | `flake/history/<env>.jsonl`, `reports/flake/collect/run-<n>.json` |

**What was assumed**, and from where. The performance CLI is the one on `main` (`--profile`, `--reports-dir`; the profiles are exactly the four engines of the input) plus `perf/aa.ts` as `p5/perf` has it: `npx tsx perf/aa.ts [--out-dir D] <gate-report.json>...`, which refuses reports of two environments or profiles. There is no `perf:aa` npm script, so the file is run directly. The A/A loop keeps every pass's report apart (the gate overwrites `reports/perf/<env>/<profile>.json`) and does not stop at a pass that fails: exit 1 is a **false positive**, which is the result the check counts, and exit 2 is a measurement that could not be trusted (no baseline of this environment, a changed stream, a browser that did not start), which turns the job red after the summary is written. The A/A needs the baseline of the runner's environment **committed in the ref that is dispatched**, so `perf-baseline` comes first, then a commit of the file, then `perf-aa`. The A/B runner takes the engine from the plan (`ENGINES` is chromium, firefox, webkit in `ab/prereg.ts`) and refuses to run without a valid, committed plan. `readiness` and `soak` take `--engine` of chromium, firefox or webkit (`ENGINES` in `src/lab/readiness/args.ts`), and `soak` needs `--minutes` (a number, `ci` for 5 or `release` for 30): without it the CLI prints its usage and exits 2, which is the failure the dispatcher should see. The flake collector runs `playwright test` with `--retries 1`, and on a runner that sets `CI` it does not reuse a server, so each repetition builds the player and starts the service; the job uses the merge gate's workers (one on macOS). `ab`, `readiness` and `soak` have no `chromium-cpu4x` (their engine lists do not), and the job stops at its first step with a message instead of installing a browser for nothing.

**The pending table.** A task that runs a file which is not on `main` is listed in the test with the file and the branch (`perf/aa.ts` and `p5/perf`, `ab/run.ts` and `p6/ab`, `live/readiness.ts` and `live/soak.ts` and `p7/live`). The test fails on a file that is neither there nor listed, **and on a listed file that exists**: the day a branch merges, the entry has to go, and from then on the file is checked like any other. It also fails on an entry that no task needs any more. *Update: `p5/perf` and `p7/live` have merged and their entries are gone; `perf-aa`, `readiness` and `soak` are now checked against `perf/aa.ts`, `live/readiness.ts` and `live/soak.ts` like any file on `main`.*

**Alternatives considered.** A shell script per task (`measure/perf.sh`): a layer between `package.json` and the workflow that drifts from both. One dispatch that runs every task (the longest one sets the time and one failure hides the others). Waiting for the branches to merge (the performance agent needs the runner baselines to finish its own work, which is the reason for this workflow). Adding `repeat` as an input to every task (it is only for the A/A, so it is documented as that and ignored by the others).

**Consequences.** If a branch renames a flag, the dispatch fails with the CLI's own usage error and the artifact still holds the machine record, so the failure costs minutes and not a night. The flake collector's history has to be merged with the one in the checkout by hand (`flake/history` is git-ignored data). The default `timeout_minutes` is 60, which does not fit ten A/A passes: the documented commands give 180.

**Defending it.** "Each task is a line anyone can run on a laptop with the same arguments, and the workflow adds only the runner, the browser and what to keep. Where a file is not merged yet the test says so by name and fails when that stops being true."

## ADR-177: A number from a runner carries its environment id and its own variation

**Context.** A GitHub runner is a virtual machine on hardware that other jobs share. Its neighbours change from run to run, so does the CPU model behind it and the image, and the harness was written for a machine that is otherwise idle (it records the load average around every batch and warns when it was high). A baseline recorded there is a statement about that class of machine, and a comparison with a workstation's number would be a comparison of two different things (ADR-004, ADR-126).

**Decision.** The environment id is the code's own: `detectEnvId()` builds `gha-<RUNNER_OS>-<RUNNER_ARCH>`, which is **`gha-linux-x64`** for `ubuntu-24.04` and **`gha-macos-arm64`** for `macos-15`, and the workflow does not set `PB_ENV_ID`: an override is only needed where the code would name a machine wrongly, and the test pins both ids. Everything a task writes is filed under it (`perf/baselines/gha-linux-x64/…`), so a runner's numbers cannot be mistaken for `local-darwin-arm64` or `docker-linux-arm64`. Every artifact carries `reports/measure-machine.txt`, written before the task and completed after it: the environment id as the code computes it, the commit and ref, the CPU model and count, the memory, the OS and the runner image version, `uname -a`, the load average before and after, and the versions of Node, npm, Playwright and ffmpeg (the streams come from the streams job, so ffmpeg is usually not even installed). `reports/measure-produced.txt` lists the files the task wrote, because the artifact also holds what `docs/results` and `perf/baselines` already contained. The job summary prints the record and the download command. The A/A task exists to measure the thing that matters on a runner: how often the gate raises a false alarm when its baseline was recorded on another VM, which is the situation of every pull request. The workflow does not try to make the machine quiet or to pin the hardware, and it says so.

**Alternatives considered.** A self-hosted runner (infrastructure to keep, and a different environment from the one the gate runs in). A larger hosted runner (paid, and again not the environment of the gate). Refusing to measure when the load is high (a runner is never quiet; the harness reports the load and the reader decides). Averaging several dispatches into one baseline (they may be different machines: the record shows the CPU model, and the variation inside one baseline is what the thresholds are derived from).

**Consequences.** Two environments times four profiles are eight baselines, one dispatch each, and the macOS runner is a three-CPU machine on which two workers starved each other in the merge gate (CI.md): a result there is read with that in mind. Firefox has not been run on `macos-15` in this lab. A result that arrives without its machine record is not a result, and the dispatcher is told how to read the variation before the number.

**Defending it.** "A shared VM is noisier than a quiet workstation, and I say it where the numbers are: every result is filed under the id of the machine class that produced it, comes with the machine record and the load around it, and the A/A check measures how much the noise costs the gate."
