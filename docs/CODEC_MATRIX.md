# Codec and MSE capability matrix

> Generated by `npm run codec-matrix -- --render` from the JSON files in [results/codec-matrix](results/codec-matrix). Do not edit it by hand: the next render overwrites it, and `npm run codec-matrix -- --check` fails when it is stale.

Which formats really play in the browsers the lab tests with, per environment, and what the lab does about the ones that do not. It is the evidence behind [ADR-001](DESIGN_DECISIONS.md) and the decisions in [decisions/codecs.md](decisions/codecs.md).

## How to read it

- A **case** appends one or two ffmpeg-generated tracks (test patterns, 4 s, a keyframe every 2 s) to a `MediaSource`, plays the element, and passes only when media time passes the threshold **and**, for video, frames were presented. The element is muted and the data is fetched after the SourceBuffers exist, like a player page does it (the sensitivity table shows what happens when the page behaves differently). The probe never trusts `MediaSource.isTypeSupported`: a browser can claim support and still fail to play.
- A **cell** is the verdict over all attempts of a case, as `verdict passes/attempts`: `ok 5/5` decoded in every attempt; `intermittent 2/5` decoded in some; `fail 0/5` in none. `launch failed` means the engine did not start in that environment; `—` means the case was not run.
- **Claims** are what `MediaSource.isTypeSupported` answered for every track type of the case. A cell is flagged **claims true but fails** when the engine claims support yet at least one attempt did not decode: the capability report cannot be trusted there. `claims false but plays` is the opposite disagreement. A plain `(claims false)` next to a failure is an honest "not supported".
- Every attempt runs in a fresh browser process unless the run says otherwise, so one attempt cannot influence the next (a first probe suspected state leaking between cases in Linux WebKit; fresh processes remove the question), and the attempts repeat so that an intermittent engine shows as such. A time limit exists only as a safety net: a timeout is reported as a failure at the stage it happened in, never used as a measurement.
- Failure text is the engine's own: `[stage] error`, where the stage is the step of the probe that failed (`launch`, `navigate`, `setup`, `sourceopen`, `addSourceBuffer`, `fetch`, `append`, `endOfStream`, `play`, `currentTime`, `frames`, `evaluate`), plus the media element's `MediaError` when it had one.
- Results of different environments are never merged: a number measured on a laptop says nothing about a CI runner.

## Documented gaps

Each gap is an engine in an environment where the lab cannot rely on what it streams. The symptom is the engine's own error text, the evidence is the raw data, and the consequence is computed by the same rule the test support code uses (see the next section). A suite affected by a gap is skipped with the reason shown here, never silently; a suite that fails where no gap is documented is a bug.

### Gap 1: webkit 27.2 on docker-linux-arm64: MSE playback of `cmaf-vp9-aac`, `webm-vp9-opus` is not reliable

- **Environment, engine:** docker-linux-arm64: Ubuntu 24.04.5 LTS, arm64; webkit 27.2.
- **Symptom:**
  - `cmaf-vp9-aac`: intermittent 2/5. Most frequent failure: `[play] NotSupportedError: The operation is not supported.`; media element error `MediaError 4 (MEDIA_ERR_SRC_NOT_SUPPORTED): Failed to push buffer` (3 of 5 attempts). `isTypeSupported` claims true.
  - `webm-vp9-opus`: intermittent 2/5. Most frequent failure: `[play] NotSupportedError: The operation is not supported.`; media element error `MediaError 4 (MEDIA_ERR_SRC_NOT_SUPPORTED): Failed to push buffer` (3 of 5 attempts). `isTypeSupported` claims true.
  - Same flavour under other page profiles: `unmuted` ok 5/5, `prefetch` ok 5/5. The verdict depends on how the page drives MSE ([ADR-031](decisions/codecs.md)).
  - Plain `<video src>` playback of the same files: all 4 controls ok, so the files are sound and the failure is in the MSE pipeline.
  - All 13 cases of this engine: 2 ok, 11 intermittent, 0 fail. An `ok` cell next to intermittent ones can be luck: 5 attempts are a sample, not a guarantee, which is why a flavour must pass every attempt to count as supported.
- **Evidence:** [`docker-linux-arm64.json`](results/codec-matrix/docker-linux-arm64.json): `engines.webkit.cases["cmaf-vp9-aac"]`, `engines.webkit.cases["webm-vp9-opus"]`, `engines.webkit.sensitivity`, `engines.webkit.controls`.
- **Consequence for the lab:** Specs that need VOD over DASH, VOD over HLS, live over DASH, live over HLS are skipped in this engine and environment, with the reason `no vod stream plays over dash in webkit 27.2: cmaf-vp9-aac intermittent 2/5 ([play] NotSupportedError: The operation is not supported.), isTypeSupported claims true; webm-vp9-opus intermittent 2/5 ([play] NotSupportedError: The operation is not supported.), isTypeSupported claims true (see docs/CODEC_MATRIX.md)`.

## How the lab chooses a format

Specs never hard-code a stream. The e2e support code probes the browser it runs in (or reads this evidence) and asks `pickStream(capabilities, kind, protocol)` from [src/lab/probe/capabilities.ts](../src/lab/probe/capabilities.ts). Candidates, in order:

| Kind | Order | Stream | Flavour (what the browser must decode) | Protocols |
| --- | --- | --- | --- | --- |
| VOD | first choice | `vod-cmaf` | `cmaf-vp9-aac` | DASH, HLS |
| VOD | fallback | `vod-webm` | `webm-vp9-opus` | DASH |
| Live | first choice | `live-cmaf` | `cmaf-vp9-aac` | DASH, HLS |

The first stream whose flavour decoded in **every** attempt (4 flavours are probed; an intermittent flavour is not supported, because a gate cannot be built on a coin flip) and that is served over the requested protocol wins. If none does, the spec is skipped with the reason `explainNoStream(...)` builds from the same data, which names each candidate flavour with its verdict. If a spec fails and the combination is not a documented gap above, that is a defect to fix, not a skip to add.
