# Metric definitions

A metric is a definition plus the place it is measured. These are the definitions every baseline, A/B report and readiness check in this
repository uses. They are implemented once, in `src/player/metrics.ts`, and exposed by `window.__qa.metrics()` ([`src/shared/qa.ts`](../src/shared/qa.ts)).
Changing a definition invalidates every committed baseline, so a change here must regenerate them in the same pull request.

| Metric                | Definition                                                                                                                                                                                                      | Why this way                                                                                                                          |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| **Startup time**      | Milliseconds from the `load-requested` event (just before `player.load()`) to the `firstframe` event: the first video frame presented (`requestVideoFrameCallback`; the `playing` event where the API is missing). | It is what a viewer waits for after pressing play. It excludes page load and the download of the player library, which a player team does not control per title. |
| Manifest time         | `load-requested` to `manifest-loaded`.                                                                                                                                                                          | Splits "slow origin / manifest" from "slow first segment" when startup regresses.                                                    |
| **Rebuffer event**    | A `buffering` episode (Shaka `buffering` true then false) that starts after `firstframe` and is not caused by the viewer's own seek: it does not start inside a seek window, which runs from `seeking` until the player has recovered (see "How the player applies them"). An episode that has not ended yet counts, with its duration so far, and is flagged `ongoing`. | A seek is allowed to buffer; an unprompted stall is the defect.                                                                       |
| **Rebuffer count**    | Number of rebuffer events.                                                                                                                                                                                      |                                                                                                                                       |
| **Rebuffer duration** | Sum of the rebuffer events' durations, ms.                                                                                                                                                                      |                                                                                                                                       |
| **Rebuffer ratio**    | rebuffer duration / (rebuffer duration + time in the playing state) since `firstframe`.                                                                                                                         | The standard streaming-quality ratio; comparable between sessions of different length.                                                |
| **Dropped frames**    | `video.getVideoPlaybackQuality().droppedVideoFrames` (and decoded = `totalVideoFrames`) at the end of the window; **dropped ratio** = dropped / decoded.                                                          | Available in all three engines. A CPU-throttled run shows it.                                                                         |
| **Effective fps**     | Frames presented (counted with `requestVideoFrameCallback`) divided by the media seconds that elapsed in a measurement window (`qa.measureFrames(mediaSeconds)`); content is 30 fps, so a healthy run reads about 30. | Dropped-frame counters can read zero while the compositor still skips; presentation is what the viewer sees. Measured over media time, not wall time, so a stall does not read as low fps. |
| **Bitrate switch**    | A change of the active video variant after the initial selection. Reason: `manual` (the page's own `selectVariantByHeight`), `start` (initial), or `abr` (**anything Shaka does by itself**: its adaptation, and also its failover away from a rung that kept failing). | Counts quality changes; a flapping ABR shows as a high switch count. A failover is told apart by the `error` events that precede it, not by the reason. |
| **Live latency**      | Distance from the playhead to the live edge, ms: the end of the newest segment the origin has published (`presentationTimeline.getSegmentAvailabilityEnd()`, in the player's clock) minus `currentTime`. It equals `seekRange().end + presentation delay - currentTime`: see "How the player applies them" for why it is not `seekRange().end - currentTime`. A healthy stream reads about the presentation delay (6 s for the lab's manifests, reported as `live.presentationDelayMs`). Reported as the current, maximum (since the first frame) and (in readiness runs) p95 over the window. | The number a live-event owner is paged about.                                                                                         |
| **Stall recovery**    | From `buffering-start` to the next `playing`, during an injected origin stall.                                                                                                                                   |                                                                                                                                       |
| **Flake rate**        | Per test: runs in which the test failed and then passed on a retry, divided by the runs in which it executed. Failure rate: runs in which it failed after all retries, divided by the runs executed.               | A retried pass is not a pass; it is the cost the team pays for a test it cannot trust.                                               |

## How the player applies them

The definitions above are implemented as pure functions of the event timeline (`src/player/metrics.ts`); this section is where a definition needed a precise reading.

- **Scope.** A measurement describes the **latest load**: the events from the most recent `load-requested`. A page that loads twice reports the second load. `errors` is the exception: it lists every error since the page booted.
- **What Shaka's `buffering` means.** With `streaming.rebufferingGoal` at its default of 0 (configurations A and B), Shaka 5.3.3 derives `buffering` from the media element's own events: `seeking` and `waiting` start an episode; `playing`, `canplaythrough`, `seeked`, or a `timeupdate` that advanced by more than 10 ms end it. Two consequences. Shaka starts in the buffering state, so every load has an episode that starts before the first frame (it is startup, not a rebuffer). And **every seek** opens an episode at `seeking` and closes it at `seeked`, even inside the buffered range. With a non-zero goal Shaka polls the buffer instead and pauses playback itself, so a rebuffer would mean something else: that is why configuration B leaves the goal at 0.
- **Seek windows.** A seek window opens at `seeking`. It closes at the first of: a `playing` after `seeked` (the element has resumed); the `buffering-end` after `seeked` (Shaka says the player has recovered); `seeked` itself when no episode is open at that moment. The last rule is the reason the window cannot simply "end at the first `playing` after `seeked`": a seek inside the buffered range never takes the element out of the playable state, so no `playing` follows it, and a window that waited for one would stay open and hide the next real stall. An episode is excluded when it **starts** inside a window, and kept when it started before one: a stall that began first is a stall, and a stall caused by the seek is the seek's cost even if it ends after `playing`. A window that never closes (a seek that never completes) hides the stalls after it; the `seeking` without a `seeked` is in the timeline. The window cannot tell the viewer's seeks from the seeks the player makes for itself (a gap jump, recovery after falling out of the DVR window): the element reports both as `seeking`, so a stall that starts in either is excluded. Catch-up jumps to the live edge are separate events (`live-edge-seek`, counted in `live.edgeSeeks`).
- **Rebuffer ratio.** The denominator's playing time is the time between `playing` (or the first frame, if later) and the next `paused`, `ended`, `seeking`, `buffering-start` or `unloaded`, resuming at `seeked` or `buffering-end` when the element was playing. Time before the first frame, paused time, seek time and every buffering episode (including the seek-caused ones, which are excluded from the numerator too) are not playing time. The ratio is 0 when the denominator is 0, and 1 when the player stalled from the first frame and never played.
- **Live latency.** Shaka's `player.seekRange().end` for a live presentation is **not** the live edge: it is the newest published point minus the presentation delay (`getSeekRangeEnd()` subtracts `getDelay()`), because that is where Shaka starts the playhead (`startTime` Infinity is clamped to it) and tries to stay. `seekRange().end - currentTime` therefore reads about 0 on a healthy stream and measures only the drift from Shaka's own target, which an owner would not be paged on and which the readiness limits in `src/shared/criteria.ts` (target = the presentation delay, limits above it) do not use. This definition is the distance to the edge itself, which is that drift plus the delay. Shaka's own live-sync (`streaming.liveSync`, disabled in A and B) holds a target latency by changing the playback rate; the player page never enables it, so latency here is observed, not corrected (a readiness candidate enables it from outside, through `qa.configure()` on a page that was opened without a manifest and has not loaded yet, because Shaka reads the option when it loads, and this latency is the number that shows whether it works: [ADR-153](decisions/readiness.md)). `latencyMaxMs` counts samples from the first frame on; samples are taken on `timeupdate` and when a snapshot is requested.
- **Startup with `autoplay=0`.** `firstframe` is the first presented frame, whether or not playback was requested: an engine that paints the first frame of a paused video reports it at load, one that does not reports it when playback starts.
- **Decoded, dropped and presented frames.** `decoded` is `totalVideoFrames`, which counts every frame the browser displayed **or dropped** (Media Playback Quality: the total video frame count is incremented when a frame is displayed and when one is dropped; Firefox's `GetTotalFrames()` is its presented plus its dropped frames), so the dropped frames are part of decoded, the dropped ratio is dropped over decoded, and a decoded frame is either presented or dropped: `presented + dropped` equals `decoded` up to the decoder's lead over the presentation (a few frames) and the frames before the first frame callback (`presented` counts from that callback, `decoded` from the load). Comparing `presented` with `decoded` alone fails a page that dropped frames. `presented` is read from the last frame callback, which a starved page runs late. The browser resets its counters when the media element is reset (the media element load algorithm, which a reset of the MediaSource runs): a run or a window that spans a reset compares nothing.
- **A stall that never ends** is reported with its duration so far (`now` of the snapshot minus its start) and `ongoing: true`; a stall still open when the viewer unloads ends at the unload.

## Summaries

- Repeated runs report **median and p90** (and the run count). The mean hides the tail: a title that sometimes takes four times as long is what members complain about. The percentile is **Hyndman and Fan type 7** (linear interpolation between order statistics, the default of R, NumPy and spreadsheets); where lower is worse (the effective fps) the tail is the **p10**, since the p90 of a frame rate is its best runs. A summary also carries the min, the max, the median absolute deviation and the coefficient of variation ([ADR-121](decisions/perf.md)).
- Baselines are per environment (`detectEnvId()`), per profile (`chromium`, `chromium-cpu4x`, `firefox`, `webkit`) and per scenario.
- Regression rule (see ADR-004 and [ADR-123 to ADR-125](decisions/perf.md)): a metric regresses when its median is worse than the baseline's by more than the relative threshold **and** the absolute floor, or when its tail (p90, or p10 for the frame rate) is worse by more than the (wider) tail threshold and the same floor; rebuffer count, duration and ratio and the dropped-frame ratio use absolute budgets. A first failure is re-measured in a fresh batch and the build fails only if the regression reproduces.

## Readiness measures

The live-event readiness checks (TEST_STRATEGY.md section 8, [decisions/readiness.md](decisions/readiness.md)) apply the definitions above and add a few that are computed from series of them, in `src/lab/readiness` and not in the hook; they use the live latency, the rebuffer episodes and the frame counters exactly as defined here.

| Measure | Definition |
| --- | --- |
| **Start time of a join** | `startupMs` of a fresh live session in a fresh browser context; the worst of the sampled joins is judged. A warm-up join is made first, with the same configuration, and is recorded and left out (the first page of a browser process pays for the browser, not for the player: ADR-120). |
| **Latency over a window** | `live.latencyMs` read once per second of media time from the first frame, and the player's own `latencyMaxMs`; the p95 (type 7, as in Summaries) and the largest are judged. |
| **Stall recovery, as judged** | `buffering-start` to the next `playing`, on the page's clock, for the stall that an injected origin outage causes (the origin's own `live.stalled` is read true when the player runs dry); the worst of the repeated runs is judged. A run in which the outage never stalled the player is `INCONCLUSIVE`. |
| **Latency restored** | Wall-clock time from that `playing` until `latencyMs` is within the maximum and **stays** there for 5 s. A player that never gets there is censored: the value is the length of the observation, flagged as a lower bound. The same time is also read **relative to the session's own level** (the median of three reads, one per media second, before the outage): until `latencyMs` is within one segment of that level and stays there for 5 s. That second reading decides nothing; the first is the criterion. |
| **Manifest gap** | The time between two consecutive requests of the manifest (DASH) or of the audio media playlist (HLS) at the origin, by arrival, outside injected faults. |
| **Latency drift** | The change that the Theil-Sen slope (the median of the slopes between every two latency reads) makes over the length of a soak after its warm-up, with the level it starts from (the median of the intercepts); stretches between injected faults share one slope and have a level each. The least-squares change over the same stretches is reported next to it, and a note is printed when the two differ by more than the limit or would give different verdicts. |
| **Unrecovered stall** | A `buffering` episode longer than the stall-recovery limit or still open, or a media clock that stood still for longer than that limit while the player was not paused. |
| **JS heap growth** | Chromium only: the JS heap in use after a forced collection (DevTools protocol), the median of the last readings minus the median of the first readings after the warm-up. |

## What the numbers do not claim

They are laboratory measurements on localhost with software decoding and synthetic content. They compare builds and configurations under identical
conditions. They are not production quality-of-experience numbers and are not comparable between environments.
