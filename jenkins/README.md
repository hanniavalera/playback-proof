# The merge gate in Jenkins, on a laptop

The same merge-gate stages as `.github/workflows/ci.yml`, run by a Jenkins controller and a Linux agent that you start with
one `docker compose up`. It exists so that "the suites run as merge gates in Jenkins" is something anyone can start and look at,
not a sentence: the pipeline definition ([`Jenkinsfile`](../Jenkinsfile)), the controller configured as code, an agent built on the
Playwright image, and the evidence of real builds in [`docs/results/jenkins`](../docs/results/jenkins). The decisions behind it are
ADR-115 to ADR-119 in [docs/decisions/ci-jenkins.md](../docs/decisions/ci-jenkins.md), and they say what this setup does not prove.

## Bring it up

You need Docker with Compose v2 (Docker Desktop on a Mac is enough) and about 6 GB of memory for the containers. Everything below is
run from the repository root.

```sh
bash jenkins/init-env.sh          # writes .env with a random admin password (never printed, never committed)
docker compose up -d --build      # builds the two images, starts the controller, then the agent
```

The first build of the images pulls the Jenkins and Playwright images and downloads the plugins; later ones come from the cache.
The controller is ready when `docker compose ps` says `healthy` (about a minute). The agent connects by itself a few seconds later.

- **URL:** <http://localhost:4700> (bound to `127.0.0.1` only; the compose project uses the host ports 4700 to 4709 and publishes
  only this one).
- **User:** `admin`. **Password:** the value of `JENKINS_ADMIN_PASSWORD` in `.env`, generated by `init-env.sh`. It is not in any
  file that is committed, and the evidence tool never writes it anywhere. To use another user name, set `JENKINS_ADMIN_ID` in `.env`
  before the first start.
- **What it builds:** the repository mounted read-only at `/repo`, branch `main`, as the job `playback-proof`. The repository is the
  directory the compose file is in; `PB_REPO` in `.env` points the job at another clone or bare repository, and `PB_BRANCH` at another
  branch. A git worktree cannot be mounted as it is (its `.git` is a file that points outside the directory), so run a worktree's
  commits through a clone: `git clone --bare --single-branch --branch <branch> . ../clone.git`, then `PB_REPO=../clone.git` and
  `PB_BRANCH=<branch>`, and fetch into the clone before each build.
- **How many engines run at once:** `AGENT_EXECUTORS` in `.env` (default 2: two of the four engines run while two wait; with 1 they run
  one after the other, which is what ADR-116 measured it against). Change it, run `docker compose up -d`, and the controller is
  recreated with the new value.

Check that it is what the documentation says it is: the controller has no executors, the agent has two, and anonymous users get
nothing.

```sh
curl -s -o /dev/null -w '%{http_code}\n' http://localhost:4700/api/json   # 403: nobody gets in without the password
docker compose logs agent | tail -3                                       # "Connected"
```

## Run a build and read it

Press **Build Now** on the job, or let the evidence tool do it and wait (it needs the password, which it reads from `.env`):

```sh
npx tsx tools/jenkins-evidence.ts --trigger --label "what this run is for"
```

In the UI the **Stage View** of the job shows the stages and their durations; `Merge gate` has one column per engine. The console
log has timestamps; **Build Artifacts** has `reports/<engine>/playwright.json`, `reports/<engine>/html/index.html` (Playwright's own
report) and, for a failing test, `test-results/**` with the failure attachments of
[docs/CONTRACTS.md](../docs/CONTRACTS.md) section 7.2 (`qa-events.json`, `request-log.json`, the screenshot and the trace).

`tools/jenkins-evidence.ts` collects what a reviewer wants without opening Jenkins: the result, every stage with its duration (and how
long it waited for an executor), the versions of Jenkins, the plugins and the tools on the agent, the tests per engine, the failure
if there is one, and a console excerpt cut down to the stage markers and the summary of each gate. It writes
`docs/results/jenkins/build-<n>.json` and `build-<n>-console.txt`, redacted twice (by the values it knows and by the shape of a
credential) and refuses to write a file that still contains the password. It records the agents as they are when it runs
(`collectedAt`), so run it right after the build; the workspaces the build used are read from the build's own log (two of them mean
two executors were busy at once). `npx tsx tools/jenkins-evidence.ts --help` lists the options
(`--build <n>`, `--expect FAILURE` for a run that is meant to be red, `--dry-run`).

## How it maps to GitHub Actions

The stage names are the `npm run gate:*` scripts, so that the two systems run the same checks (`tests/unit/jenkins` checks that the
Jenkinsfile only calls scripts and projects that exist).

| Gate                           | GitHub Actions job                       | Jenkins stage (`Jenkinsfile`)                    | What runs                                                         |
| ------------------------------ | ---------------------------------------- | ------------------------------------------------ | ----------------------------------------------------------------- |
| setup                          | `npm ci` in every job                    | `Checks` > `Install`                             | `npm ci`, and the versions of the tools on the agent              |
| `gate:static`                  | `static`                                 | `Checks` > `Static`                              | `npm run gate:static`                                             |
| `gate:unit`                    | `unit`                                   | `Checks` > `Unit`                                | `npm run gate:unit`                                               |
| streams                        | restored from the Actions cache          | `Checks` > `Streams`                             | `npm run generate:streams`, into the shared cache volume          |
| `gate:merge`, Chromium         | the merge job of the engine              | `Merge gate` > `chromium`                        | `npm run gate:merge -- --project=chromium`                        |
| `gate:merge`, Firefox          | the merge job of the engine              | `Merge gate` > `firefox`                         | `npm run gate:merge -- --project=firefox`                         |
| `gate:merge`, throttled Chrome | the merge job of the project             | `Merge gate` > `chromium-cpu4x`                  | `npm run gate:merge -- --project=chromium-cpu4x`                  |
| `gate:merge`, WebKit           | the **macOS** job (the WebKit that ships) | `Merge gate` > `webkit` (Linux, **experimental**) | `npm run gate:merge -- --project=webkit`                         |
| `gate:flake`                   | `flake` (the judge) and `flake-record` (a push to `main`) | `Flake`, after `Merge gate`      | `npm run gate:flake -- --store file --runs reports/flake`, plus `--record` for a build of `main` (ADR-174) |
| `gate:perf`                    | `perf (chromium)` and `perf (chromium-cpu4x)` | `Perf`, after `Merge gate`                  | `npm run gate:perf -- --paired --control-ref "$CONTROL_REF" --profile chromium,chromium-cpu4x`: the control is `HEAD^1` on `main`, and `HEAD` itself (an A/A) on any other branch |
| `gate:triage`                  | `triage` (`if: failure()`, not a required check) | `Triage`, last, only when the build is not green | `npm run gate:triage -- --from artifacts --out reports/triage` |

The GitHub jobs are defined by the other half of the setup, in `.github/workflows`; the rows are the intent of
[TEST_STRATEGY.md](../TEST_STRATEGY.md) section 6.1, and the jobs that do not exist there yet are marked by their absence from that
directory, not by this table.

**The `Flake` stage.** The four engines run in workspaces of their own, so each one stashes its `reports/flake/run*.json` before its
workspace is wiped, and `Flake` unstashes them side by side under `reports/flake/<engine>/` (the layout of GitHub's download step) and
judges them against the history of this environment, `jenkins-linux-arm64`: a file on the volume `flake-history`, mounted at
`/history` and named to the gate by `PB_FLAKE_HISTORY_DIR`. It runs when an engine is red (the engines' `gate:merge` is wrapped in
`catchError`, which marks the engine and the build red without skipping the stages after it). **A build of `main` is recorded** in that
history, whatever its result, as the gate does by design; a build of any other branch (`PB_BRANCH`, the negative run below) is judged
and forgotten. With a handful of builds the gate says "not enough data": a verdict on a rate needs 20 builds of an engine, which a
laptop rarely has. What the stage shows at once is the plumbing and the rules that need no history (an expired quarantine, an invalid
list, no run file at all). See ADR-174 in [docs/decisions/ci-flake.md](../docs/decisions/ci-flake.md), whose amendment says what the
real builds proved of it. To see the history: `docker compose exec agent ls -l /history`.

**The `Perf` and `Triage` stages.** `Perf` runs alone, after the engines, because a measurement needs the machine to itself
(ADR-179): it builds the control (`HEAD^1` on `main`, `HEAD` itself on another branch) next to the head and judges the head against it,
the same command as the GitHub legs, in both profiles. `Triage` is the last stage and runs only when the build is not green: it
unstashes the Playwright reports of the four engines and clusters their failures; it decides nothing and exits 0 whatever it finds.
Both run after a red engine (`catchError`), so a red build still has them. What they showed in real builds is below.

Three things these builds found that are not about the pipeline. **Two unit tests failed while the machine was loaded.** Build 2 failed
in `tests/unit/probe/media.test.ts` ("generates the same bytes every time": the first of two generations of the probe media produced a
different VP8 file), and build 5 failed in `tests/unit/server/static.test.ts` ("releases the file of every download that the client
abandons": 84 open descriptors counted where 120 were expected). Both passed in builds 3, 4 and 6. Build 2 ran four Vitest workers on an
agent with a quota of three CPUs, and its file passed three times alone on the idle agent and failed again under eight busy loops
([ADR-119](../docs/decisions/ci-jenkins.md)); build 5 failed while the host had a load average of about 18 on 12 cores. The second one is
likely the helper defect fixed in pull request #22 (the
helper that waits for pending file operations did not count the close of a file handle, so the baseline was taken while closes were
still queued); that was not checked for build 5, whose message (84 descriptors where 120 were expected) is not the one of the failures
on GitHub ([`docs/results/flake/README.md`](../docs/results/flake/README.md), section 5). The first has a likely cause: that
commit still encoded VP8 with libvpx's `-deadline realtime`, whose output depends on how busy the machine is (four different hashes in
four runs at a load average of about 20), and the recipe was replaced the same evening ([ADR-037](../docs/decisions/codecs.md), the
amendment under its Consequences), though this was not traced into libvpx. A later mismatch of the same test, on an HEVC clip on a GitHub
runner, has no known cause (same section 5). **Two more unit tests
depended on the environment of the agent, not on its load.** Build 7 failed in `tests/unit/measure/paired-real.test.ts`, which expects
the control of the paired gate to get the checkout's own stream cache while the agent sets `PB_CACHE_DIR`, which the control honours
on purpose, and in `tests/unit/triage/committed-files.test.ts`, which looks for the name of the machine's user in the committed files
while the user of the agent is `jenkins`, a word that these documents use. Both are fixed in pull request #26 (test code only: the
first test no longer inherits the variable, the second takes the account of a CI service for no one's name), and build 8 is the re-run.
A GitHub runner has neither the variable nor that user, which is why the second CI system found what the first could not.
**PB-ENV-001 has nothing to compare with**: the committed codec matrix has no result for `jenkins-linux-arm64`, so the `environment`
annotation of each engine in the JSON reports says `no committed probe result for jenkins-linux-arm64`, and Linux WebKit runs because
of the `RUN_SPECS_IN_LINUX_WEBKIT` override.

### The stages after the merge gate

Build 7 was meant to be the first run of the whole pipeline and stopped in `Unit` (above), so every stage after it is `NOT_EXECUTED` in
its evidence, not a second failure. **Build 8**, the same pipeline on `main` at `d333c1f`, ran all of them and was green in 18 minutes
(1082 s), inside the 60-minute timeout of the build:

- **`Perf` ran in Jenkins for the first time and passed, in both profiles** (743 s, two thirds of the build). It created the control,
  the first parent of the commit (`4f794701c8ac`), in a checkout of its own on the same agent, linked the node modules (the lock files
  are the same), built the control's player page, measured the control and then the head, and judged the head against it: `chromium`
  startup 42.3 ms for the control and 41.7 ms for the head (-1.4 %), 30 fps for both, no dropped frame, no rebuffer; `chromium-cpu4x`
  startup 134.9 and 133.9 ms (-0.7 %); exit code 0 for both. The change between the two commits was two tests, so this shows that the
  stage runs and passes. **No regression was injected in Jenkins**: that the paired gate fails on one is shown on GitHub
  ([`paired-sensitivity.md`](../docs/results/perf/paired-sensitivity.md)), not here. The agent's CPU model is `unknown` in the gate's
  report: a Linux arm64 container in Docker Desktop's VM exposes none.
- **`Flake` ran and passed** (7 s). It laid the run files of the four engines side by side (`4 runs in this build`: stash and unstash
  work across the parallel workspaces), judged them against the history on the `flake-history` volume and, because the branch is
  `main`, recorded them: `/history/jenkins-linux-arm64.jsonl` holds the four runs of build 8 (run id `jenkins-playback-proof-8`). With
  one build in the history every verdict is `not-enough-data`: a rate is judged from 20 builds, which a laptop rarely has.
- **`Triage` did not run**, as designed: its condition is a build that is not green.

**Build 9**, on a throwaway branch of a copy of the repository ([the negative run](#the-negative-run), below), showed what a red build
does to the stages after it. `Merge gate` went red in `chromium`, `firefox` and `webkit`; then `Perf` ran anyway and passed (the
control of a branch other than `main` is its own `HEAD`: an A/A); `Flake` judged the four runs of the build together with the four of
build 8 in the history (`4 runs in this build, 8 runs judged`), passed (a failed test is the business of the merge gate, and every
verdict is still `not-enough-data`) and **recorded nothing**: the file still had the four lines of build 8. `Triage` ran, because the
build was red, and read the Playwright reports of
the four engines: **3 failures in 4 reports became 1 cluster** (PB-VOD-002, in three engines), category `unknown`, rule
`no-rule-matched`, class "Needs a person": the rule table has no rule for a false assertion about the request log, and it says so
instead of guessing.

**Build 10**, a second build of `main` on the same commit as build 8, was green again (1071.6 s) and answered what one build cannot.
`Flake` **appended** its four runs to the file (eight lines, the run ids `jenkins-playback-proof-8` and `jenkins-playback-proof-10`; the
file had survived the recreation of the containers in between) and judged the build against the eight runs (`4 runs in this build,
8 runs judged`; two builds are too few for a rate, so every verdict was `not-enough-data` again). `Perf` passed again in both
profiles: `chromium` startup 39.05 ms for the control and 40.6 ms for the head (+4.0 %), `chromium-cpu4x` 142.1 and 129.4 ms (-9.0 %).
The two commits differ in two test files only, so that is the same code measured twice, and the control of build 10 (39.05 ms) is 8 %
faster than the control of build 8 (42.3 ms) at the same commit: on a shared laptop a number from another build is not comparable,
which is why the head is judged against a control measured minutes before it on the same machine.

What these builds do not show: that `Perf` fails on a regression in Jenkins (see above); a rate judged by the flake gate (the history
of `main` is two builds deep, and a rate is judged from 20); a triage cluster with a root cause (the one cluster it made is of a
made-up failure, and is `unknown`); the CPU model of the agent.

### The negative run

A gate that has never failed is not known to work. Build 6 is a run on a **throwaway branch of a copy of the repository** (the real
checkout is never touched) in which one expectation of `tests/e2e/vod-start.spec.ts` was made false on purpose: the HLS check asserts
that the player requested at least one media playlist (`toBeGreaterThan(0)`), and the branch asserts that it requested none
(`toBe(0)`). The result is what the setup is for: `Install`, `Static`, `Unit` and `Streams` green, then `Merge gate` red, in the three
engines that run PB-VOD-002 (`chromium`, `firefox`, `webkit`), green in the throttled project, which does not; every failing test ran
twice (one retry, as in CI), and the archived `reports/<engine>/playwright.json` carries the six diagnostics of
[docs/CONTRACTS.md](../docs/CONTRACTS.md) section 7.2 for both attempts (`qa-events.json`, `qa-metrics.json`, `qa-info.json`,
`page-console.json`, `session-detail.json`, `request-log.json`), next to the screenshot, the error context and the trace in
`test-results/`. [`build-6.json`](../docs/results/jenkins/build-6.json) says `failure.stage: chromium`, `group: Merge gate` and
`asExpected: true`, which the evidence tool computes: a build that is red anywhere else (build 5) is `asExpected: false`. Build 9 repeated
the run on a copy of `main` at `d333c1f` (the branch commit is `7a51c8a`), now that the stages after the merge gate exist:
[`build-9.json`](../docs/results/jenkins/build-9.json) says the same, and what `Perf`, `Flake` and `Triage` did with the red build is
in the section above.

To repeat it, from the repository root (`<copy>` is a scratch bare repository, which is also where `PB_REPO` points):

```sh
git clone --bare --single-branch --branch main . ../<copy>.git                 # a copy; nothing below touches this checkout
git clone ../<copy>.git ../<copy>-work && cd ../<copy>-work && git checkout -b negative/false-expectation
# edit tests/e2e/vod-start.spec.ts: in expectStartsAndPlays, .toBeGreaterThan(0) -> .toBe(0) for the HLS playlists
git commit -am "make an expectation false on purpose" && git push origin negative/false-expectation && cd -
# in .env: PB_REPO=../<copy>.git and PB_BRANCH=negative/false-expectation, then recreate the controller so that the job reads them
# (or without touching .env: PB_REPO=../<copy>.git PB_BRANCH=negative/false-expectation docker compose up -d; a later
# `docker compose up -d` without them points the job back at main)
docker compose up -d
npx tsx tools/jenkins-evidence.ts --trigger --expect FAILURE --expect-stage "Merge gate" --label "negative run"
# restore: remove both lines from .env, docker compose up -d, and delete ../<copy>.git and ../<copy>-work
```

## Tear it down

```sh
docker compose down          # stops and removes the containers; keeps the volumes (Jenkins home, streams, flake history, npm cache)
docker compose down -v       # also removes the volumes: the next start is a cold start (the streams are generated again, the flake history is empty)
```

`docker compose ps` and `docker ps` should then list nothing of the project `playback-proof-jenkins`. `.env` stays (it is yours);
delete it to get a new password the next time.

## What is where

| Path                                     | What it is                                                                                           |
| ---------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `Jenkinsfile`                            | The pipeline. Declarative; only `sh 'npm run ...'` lines do work.                                    |
| `docker-compose.yml`, `.env.example`     | The stack: controller, agent and five named volumes. `.env` is created by `init-env.sh` and ignored by git. |
| `jenkins/controller/Dockerfile`          | The LTS controller with the plugins of `plugins.txt` installed by `jenkins-plugin-cli`.              |
| `jenkins/controller/plugins.txt`         | Every plugin, dependencies included, pinned.                                                         |
| `jenkins/controller/casc.yaml`           | Configuration as Code: the admin user, no executors on the controller, the agent node, the job.      |
| `jenkins/controller/init.groovy.d/`      | The one start-up script: it leaves the agent's connection secret in a volume the agent reads.        |
| `jenkins/agent/Dockerfile`, `entrypoint.sh` | The agent: the Playwright image of the pinned version, plus Java and ffmpeg; connects over WebSocket. |
| `jenkins/init-env.sh`                    | Creates `.env` with a random password.                                                               |
| `tools/jenkins-evidence.ts`              | Triggers a build and writes the evidence of it.                                                      |
| `docs/results/jenkins/`                  | The evidence of the builds this setup ran.                                                           |

## What it does not cover

- **macOS.** The GitHub workflow runs WebKit on a macOS runner, the WebKit that ships to people. A Linux container cannot be a
  macOS agent, and there is no pretend one: the `webkit` stage here is Linux WebKit, an experimental engine
  ([docs/CONTRACTS.md](../docs/CONTRACTS.md) section 7.3). A real macOS agent would join with the label `macos` and one more stage.
- **Triggers.** Nothing starts a build by itself: no webhook, no polling, no pull-request integration. The job reads a local
  repository and a branch; a real SCM, its credentials and its notifications are not set up.
- **Production concerns.** One controller, one agent, one admin, plain HTTP on the loopback interface, no backup of the Jenkins home,
  no agent autoscaling. It is a lab for the pipeline definition, the stage parity and the failure behaviour (ADR-119), not a CI
  service.
- **Environment evidence.** The environment id of a build here is `jenkins-linux-arm64`. No codec matrix is committed for it, so the
  specs run without a documented gap, and no performance baseline is committed for it, and none is needed: the `Perf` stage is paired
  and measures its control on this agent, minutes before the head. What it cannot say is what the agent is: a Linux arm64 container
  in Docker Desktop's VM on a Mac exposes no CPU model, so the gate prints `this machine: unknown` and the evidence names the
  machine only as that. The flake history of this id is the one on the `flake-history` volume, filled by the builds of `main` that
  ran here and by nothing else.

## If something does not start

- `docker compose ps` shows the controller `unhealthy`: `docker compose logs jenkins | grep -i -E 'severe|exception'`. A mistake in
  `casc.yaml` stops the controller at start and says which key.
- The agent loops on "waiting for the controller": the controller is still starting, or its start failed (see above).
- The agent is `offline` after you recreated the controller with a fresh volume: restart it, `docker compose restart agent` (the
  connection secret is derived from the controller's own key, so a new volume means a new secret).
- A build waits for "Waiting for next available executor": the agent is offline, or the label does not match.
- `port is already allocated`: something else uses 4700; stop it (the project keeps to 4700 to 4709 on purpose).
